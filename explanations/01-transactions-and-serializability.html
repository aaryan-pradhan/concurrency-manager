Prerequisite 1

Transactions, schedules and serializability

What a database transaction is, what can go wrong when two of them overlap, and the precise test (an acyclic precedence graph) that decides whether an overlapping run is still correct. Every later page measures the project against this test.

Usesnothing. This is the first page.
docs/02-databases-and-transactions.md
"Isolation — transactions running at the same time don't interfere with each other, even though they're physically overlapping. This project is entirely about Isolation. […] There's no actual data being read or written — the simulation only cares about the locking behavior, not the values."

Two phrases set the scope of this page. "Isolation" is one letter of ACID (section 2), and its formal meaning is serializability (sections 5–7). "No actual data" means the project never stores a value, so everything below is about the order in which transactions touch items, not about what they compute.

1. Transactions and their operations

A transaction is a sequence of reads and writes on data items that the system treats as one unit: either all of its effects happen or none do. We write its operations in a compact notation used in every database textbook:

\[ r_i(x) \quad w_i(x) \quad c_i \quad a_i \]

\(r_i(x)\) means transaction \(T_i\) reads item \(x\). \(w_i(x)\) means \(T_i\) writes \(x\). \(c_i\) is its commit (its effects become permanent) and \(a_i\) its abort (its effects are undone). An item is any named unit of data: a row, a page, or in this project just a letter such as N.

Worked example · a transfer

Moving 100 from account A to account B is one transaction \(T_1\): \(r_1(A)\,w_1(A)\,r_1(B)\,w_1(B)\,c_1\). If the system crashed after \(w_1(A)\) but before \(w_1(B)\), 100 would vanish. Treating the four operations as one unit is what prevents that.

The project's test files use the same idea with different spelling: R314(N) is \(r_{314}(N)\), W314(N) is \(w_{314}(N)\) and C314 is \(c_{314}\).

AAtomicity: all of a transaction's writes happen, or none doundo log / rollback of written values

In the code · isolation, with no durability

The engine stores no values, keeps no undo log and writes nothing that recovery could replay (the .log files are human-readable traces). "Abort" releases locks and marks the transaction ABORTED. The benchmark harness adds integer values and installs a transaction's writes only at commit, which makes each transaction's effects all-or-nothing in memory, but nothing survives a crash. So the project is about the I of ACID, at the level of lock scheduling. The A exists only in the benchmark harness, and there's no D. The docs say so directly: "This project does not deal with durability at all — everything is in memory."

3. Schedules

When several transactions run at once, their operations interleave. A schedule is the single time-ordered list of all operations from all transactions, keeping each transaction's own operations in their original order. A serial schedule runs whole transactions back to back with no interleaving.

\[ \#\{\text{serial schedules of } n \text{ transactions}\} = n! \]

Each serial schedule is an ordering of the \(n\) transactions. Serial schedules are correct by definition if each transaction is correct on its own, but they use one transaction's worth of work at a time.

Worked example

With \(n = 3\): \(3! = 3 \times 2 \times 1 = 6\) serial orders (123, 132, 213, 231, 312, 321). With \(n = 10\): \(10! = 3{,}628{,}800\). The project's large test files have \(n = 1{,}000\), so "is this schedule equivalent to some serial order?" can't be answered by trying the orders one by one. Section 7 gives a test that runs in linear time.

4. What goes wrong without control: the anomalies

If the system allows any interleaving, some schedules produce results that no serial schedule could. The three classic ones:

  • Lost update: two transactions read the same value, both write a new value computed from it, and the second write silently overwrites the first.
  • Dirty read: a transaction reads a value written by another transaction that later aborts, so it acted on data that never officially existed.
  • Unrepeatable read: a transaction reads the same item twice and sees two different committed values because another transaction wrote in between.
Worked example · lost update

Stock count \(x = 10\). \(T_1\) sells 3, \(T_2\) sells 4.

r₁(x)=10   r₂(x)=10   w₁(x)=10−3=7   w₂(x)=10−4=6   c₁   c₂

Final \(x = 6\). Both serial orders give \(10 - 3 - 4 = 3\). Three units of sales were lost because \(T_2\) computed its write from a value that \(T_1\) had already made stale.

5. Conflicting operations

Whether swapping two adjacent operations can change the outcome depends only on three facts about them. Two operations conflict when all three hold:

\[ \text{conflict}(o_i, o_j) \iff i \ne j \;\wedge\; \text{item}(o_i) = \text{item}(o_j) \;\wedge\; \big(o_i \text{ is a write} \,\vee\, o_j \text{ is a write}\big) \]

Different transactions, same item, and at least one of the two is a write. Two reads of the same item never conflict, because reading changes nothing.

6. Conflict-serializability

Two schedules are conflict-equivalent if one can be turned into the other by repeatedly swapping adjacent non-conflicting operations, or equivalently, if every pair of conflicting operations appears in the same order in both. A schedule is conflict-serializable if it is conflict-equivalent to some serial schedule.

Conflict-serializability is the working definition of "isolation is correct" used by locking systems, and by the rest of these pages. It's slightly stricter than the most general notion (view-serializability), but it can be checked efficiently, which is what matters here.

7. The precedence graph test

The precedence graph \(P(S)\) of a schedule \(S\) has one node per committed transaction and a directed edge \(T_i \to T_j\) whenever some operation of \(T_i\) conflicts with a later operation of \(T_j\).

\[ S \text{ is conflict-serializable} \iff P(S) \text{ has no directed cycle} \]

If \(P(S)\) is acyclic, any topological order of its nodes is an equivalent serial order. If it has a cycle \(T_i \to \cdots \to T_i\), then \(T_i\) would have to come before itself in any equivalent serial order, which is impossible. Building the graph and checking for a cycle takes \(O(V + E)\) time, for \(V\) transactions and \(E\) edges.

Worked example A · serializable

S₁ = r₁(A) w₁(A) r₂(A) w₂(A) r₁(B) w₁(B) c₁ c₂

Conflicting pairs on A: \(r_1(A)\) before \(w_2(A)\), \(w_1(A)\) before \(r_2(A)\), \(w_1(A)\) before \(w_2(A)\). All give \(T_1 \to T_2\). B is touched only by \(T_1\). The graph is the single edge \(T_1 \to T_2\), which is acyclic, so \(S_1\) is equivalent to the serial order \(T_1, T_2\).

Worked example B · not serializable (this exact shape appears in the project's logs)

S₂ = r₁(N) w₂(N) c₂ w₁(N) c₁

\(r_1(N)\) before \(w_2(N)\) gives \(T_1 \to T_2\). \(w_2(N)\) before \(w_1(N)\) gives \(T_2 \to T_1\). That's a cycle, so no serial order is equivalent. In data terms it's a lost update: \(T_1\) writes N based on a read that \(T_2\)'s committed write had already made stale.

8. Aborts: recoverable, cascadeless and strict schedules

Serializability assumes every transaction commits. Aborts add a second family of requirements, each stronger than the one before:

  • Recoverable: if \(T_j\) reads something \(T_i\) wrote, \(T_j\) commits only after \(T_i\) commits. Otherwise a committed transaction could depend on an aborted one.
  • Cascadeless (avoids cascading aborts): transactions only read values written by already-committed transactions. Otherwise one abort forces every reader of its writes to abort too, and their readers, and so on.
  • Strict: no transaction reads or writes an item until the last transaction that wrote it has committed or aborted. This makes undo simple: restoring the old value can't clobber anyone else's write.
Worked example · a cascading abort

w₁(x) r₂(x) w₂(y) r₃(y) a₁

\(T_2\) read \(T_1\)'s uncommitted \(x\), and \(T_3\) read \(T_2\)'s \(y\). When \(T_1\) aborts, \(T_2\) must abort, and then \(T_3\) must too. A strict schedule would have made \(T_2\) wait for \(c_1\) or \(a_1\) before reading \(x\).

Page 3 shows that holding locks until commit ("strict 2PL") produces exactly these strict schedules.
