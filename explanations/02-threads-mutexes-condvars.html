Threads, mutexes and condition variables in C++

The operating-system tools the engine is built from: threads, the data races they cause, mutexes that stop them, condition variables for waiting, and the C++ object-lifetime rule behind the project's startup crash.

Usesthe lost-update anomaly from page 1, section 4, which has the same shape as a data race.
docs/03-concurrency-threads-and-race-conditions.md
"Important distinction: these mutexes are an implementation detail used to keep the C++ objects themselves from corrupting their own internal data. They are completely different from the transaction locks (shared/exclusive locks on resource IDs) that are this project's actual subject matter. A mutex protects a data structure in memory for a few instructions; a transaction lock protects a logical database resource for the lifetime of a transaction, potentially seconds."

This page is about the first kind of lock in that quote, the mutex. Page 3 is about the second kind. The engine needs both, and several of the bugs later on sit exactly where the two meet.

1. Processes and threads

A process is a running program with its own memory. A thread is one sequence of execution inside a process. All threads of a process share its heap and global variables, but each has its own stack. In C++, std::thread t(f, args...) starts running f on a new thread, and t.join() blocks until it finishes.

Worked example · 1,000 threads on 8 cores

The project's big test files start one thread per transaction, so 1,000 threads (plus the main thread and a background detector thread). The audit machine has 8 logical cores, so at any instant at most 8 threads are actually executing. The other \(1{,}002 - 8 = 994\) are sleeping, blocked, or waiting for the OS scheduler. More threads than cores adds scheduling overhead, and it only raises throughput when threads spend most of their time blocked on something other than each other.

2. Race conditions and data races

A race condition is a bug whose outcome depends on the timing of threads. The most common kind is a data race: two threads access the same memory at the same time, at least one of them writes, and nothing coordinates them.

Worked example · a lost increment

counter++ is three machine steps: load, add 1, store. Starting from counter = 0, with two threads:

A: load 0   B: load 0   A: store 1   B: store 1

Final value 1, not 2. It's the same pattern as the lost update on page 1, one level down.

Be careful · in C++ a data race is undefined behaviour, not just a wrong number

The C++ standard makes any data race undefined behaviour (UB): the program may do anything. For a container like std::unordered_map, an insert on one thread can trigger a rehash that frees the bucket array while another thread's find is walking it. That's a crash or silent memory corruption, not a lost count. "It didn't crash in my runs" is no evidence against UB.

3. Mutexes and critical sections

A mutex (mutual-exclusion lock) is held by at most one thread at a time. Code that runs while holding it is a critical section. C++ provides two RAII wrappers, which release the mutex automatically when they go out of scope:

std::mutex mtx;
{
    std::lock_guard<std::mutex> g(mtx);   // locked until end of scope, can't unlock early
    counter++;
}
{
    std::unique_lock<std::mutex> u(mtx);  // like lock_guard, but can unlock() early
    ...                                     // and can be handed to a condition variable
    u.unlock();
}

Database engineers call this kind of short-lived in-memory mutex a latch, and reserve "lock" for the transaction-level locks of page 3. The terms keep the two apart. A latch is held for microseconds and never across a wait for another transaction. A lock can be held for seconds.

4. Self-deadlock and the recursive mutex

A thread that tries to lock a std::mutex it already holds waits for itself forever (formally, this is undefined behaviour). A std::recursive_mutex counts how many times its owner has locked it and releases only when that count returns to zero, so a method holding it can call another method that locks it again.

In the code · one recursive mutex, and one latent self-deadlock

ResourceAllocationGraph uses a recursive_mutex because addAssignmentEdge calls removeRequestEdge, and both lock it. Logger uses a plain std::mutex, but Logger::setLogLevel and setConsoleOutput lock it and then call info(), which locks it again (src/logger.cpp:192–202). Either call would hang its thread. Nothing in the repo calls them, so it never happens in practice.

5. Condition variables

A thread that must wait until some shared state changes shouldn't spin in a loop checking. A condition variable lets it sleep until another thread signals that something changed. The predicate form is the one to use:

std::unique_lock<std::mutex> lk(mtx);
cv.wait(lk, [&]{ return ready; });   // same as: while (!ready) cv.wait(lk);

// another thread, after changing `ready` under mtx:
cv.notify_all();                       // or notify_one()
  • wait atomically releases the mutex and sleeps. When woken, it re-acquires the mutex and re-checks the predicate. It returns only once the predicate is true, with the mutex held.
  • Spurious wakeups (waking with nothing changed) are allowed, which is why the predicate is re-checked in a loop.
  • wait_for(lk, duration, pred) also gives up after the duration and returns the predicate's final value. It's the natural tool for a lock timeout.
  • notify_one wakes one waiter. notify_all wakes every thread waiting on that condition variable.

6. The thundering herd

If every waiter shares one condition variable and every state change calls notify_all, each change wakes all waiters. They then take turns re-acquiring the one mutex, re-check their predicates, and nearly all go back to sleep. This is the thundering herd.

\[ \text{wakeups} = R \times W \]

\(R\) is the number of notifications (for example, lock releases) and \(W\) is the number of threads waiting at each one. Each wakeup costs a context switch plus one pass through the critical section.

Worked example

With \(W = 500\) blocked threads and \(R = 100\) releases, that's \(100 \times 500 = 50{,}000\) wakeups, each serialized on the same mutex, even if each release could unblock only one or two of the waiters.

7. Never block while holding a mutex, and the gap that creates

If a thread keeps holding a mutex while it waits for something slow, every other thread that needs that mutex stops too. So code checks the state under the mutex, unlocks, then waits. Between the unlock and the next lock, other threads can change the state. This check-then-act gap is called TOCTOU (time of check to time of use). Code must re-validate after re-acquiring the mutex, because the world may have moved on.

A second consequence: a raw pointer read from a map under a mutex isn't protected once the mutex is released. Another thread may erase the entry and destroy the object, leaving a dangling pointer.

8. Atomics and barriers

  • std::atomic<int>: single operations like ++, load and store are indivisible, which is enough for counters and flags without a mutex. A sequence of atomic operations is not atomic as a whole.
  • std::barrier (header <barrier>, provided by the libc++ used in this audit): constructed with a count \(k\). Each thread calls arrive_and_wait(), and all \(k\) threads are released together once the \(k\)-th arrives. The project uses it so all 1,000 transaction threads start at the same instant, which maximizes contention.

9. Member initialization order, and why UB can "work" on one OS

C++ constructs a class's data members in the order they are declared in the class, whatever order the constructor's initializer list uses. If member b is declared before member a but is initialized using a, then b uses an a that doesn't exist yet. That's undefined behaviour. Clang and GCC warn about the mismatched order (-Wreorder / -Wreorder-ctor).

struct S {
    Logger& ref_user;  // declared first  -> constructed first
    Logger  log;       // declared second -> constructed second
    S() : log("x.log"), ref_user(log) {}   // list order is ignored
};
Worked example · why the same bug crashes on macOS and not (likely) on Linux

An object with static storage (a global) is zero-filled before its constructor runs. If code locks a std::mutex member before that member is constructed, the mutex's bytes are all zero. On Linux/glibc, the "unlocked mutex" initializer is itself all zeros, so the lock usually just works by luck. On macOS, a valid mutex must carry a non-zero signature, so pthread_mutex_lock returns EINVAL and libc++ throws std::system_error: mutex lock failed: Invalid argument. That's the exact message the project's harness prints at startup on macOS (Part 1, section 7).
