Prerequisite 3

Locks and two-phase locking

Shared and exclusive locks, how a lock table decides who waits, why an upgrade must keep its old lock, and a proof that the two-phase rule makes every schedule serializable, along with exactly which rule-break would void that guarantee.

Usesthe conflict rule and precedence-graph test from page 1, sections 5–7 · strict schedules and cascading aborts from page 1, section 8 · latch vs lock from page 2, section 3.
docs/05-two-phase-locking-protocol.md
"Every transaction's lifetime is split into exactly two phases: Growing phase — the transaction may acquire new locks. It may not release any lock during this phase. Shrinking phase — the transaction may release locks. It may not acquire any new lock during this phase. The moment a transaction releases its very first lock, it has permanently moved from growing to shrinking — there is no going back."

Sections 1–4 build the locks the rule talks about. Sections 5–6 state the rule precisely and prove what it buys. Section 7 separates the variants (basic, strict, rigorous) the docs and the CV refer to.

1. Shared and exclusive locks

Before reading item \(x\), a transaction takes a shared lock \(S(x)\). Before writing, it takes an exclusive lock \(X(x)\). Two locks from different transactions on the same item can be held together only if they are compatible:

Compatibility matrix (another transaction already holds ↓, request →)
held \ requestedSX
nonegrantgrant
Sgrantwait
Xwaitwait

This is the conflict table from page 1, section 5 turned into a rule. "Grant" is exactly the non-conflicting case (read with read). A transaction's own locks never block itself.

2. The lock table and the grant policy

A lock table maps each item to a list of requests, each marked granted or waiting. The table is itself shared memory, so it's protected by a latch (page 2, section 3). When a new request arrives, the system needs a grant policy:

  • FIFO / fair: grant only if the request is compatible with the granted locks and no incompatible request is queued ahead of it.
  • Compatible-with-granted only: grant whenever the request fits the granted locks, ignoring the queue. Newcomers can overtake waiters. This is called barging.
Worked example · barging starves a writer

\(T_1\) holds \(S(x)\). \(T_2\) requests \(X(x)\) and waits. \(T_3\) requests \(S(x)\): it's compatible with \(T_1\)'s S, so under barging it's granted. \(T_1\) releases, but \(T_3\) still holds S, so \(T_2\) keeps waiting. \(T_4\) arrives with \(S(x)\) and is granted before \(T_3\) releases, and so on. As long as readers overlap, \(T_2\) never runs. That's starvation: no deadlock, yet one transaction makes no progress. FIFO would have queued \(T_3\) behind \(T_2\).

3. Lock upgrades

A transaction that read \(x\) under \(S(x)\) and now wants to write it requests an upgrade to \(X(x)\). The textbook implementation keeps the S lock granted while the upgrade waits, and converts it once the transaction is the only holder.

Be careful · the S lock must stay held during the wait

If an implementation drops \(S(x)\) and joins the queue for \(X(x)\) as if it were a fresh request, another transaction can take \(X(x)\), write, and commit in the gap. The upgrader's earlier read is then stale, which is precisely schedule S₂ from page 1, section 7. Section 6 shows this also breaks the two-phase rule. Part 2, section 6 shows the project had exactly this bug, with the log evidence and the fix.

Worked example · the upgrade deadlock

\(T_1\) and \(T_2\) both hold \(S(F)\). \(T_1\) requests \(X(F)\) and must wait for \(T_2\)'s S. \(T_2\) requests \(X(F)\) and must wait for \(T_1\)'s S. Each waits for the other, forever. The project's tests/test1.txt is built around this pattern. Real systems reduce it with an intermediate update lock (U) that only one transaction may hold, but the project doesn't have one.

4. Why locking each operation isn't enough

Taking the right lock around every single read and write still allows non-serializable schedules if a transaction releases a lock and later takes another one.

Worked example

X₁(A) w₁(A) U₁(A)   X₂(A) w₂(A) X₂(B) w₂(B) U₂(A) U₂(B) c₂   X₁(B) w₁(B) U₁(B) c₁

(\(U\) means unlock.) Every write happens under an exclusive lock. But on A, \(w_1\) comes before \(w_2\), giving \(T_1 \to T_2\). On B, \(w_2\) comes before \(w_1\), giving \(T_2 \to T_1\). That's a cycle, so the schedule isn't serializable. The fault is that \(T_1\) released A and then acquired B.

5. The two-phase locking rule

Under two-phase locking (2PL), a transaction never acquires a lock after it has released any lock. Its lifetime splits into a growing phase (acquire only) and a shrinking phase (release only). The instant it acquires its last lock is its lock point, written \(\mathrm{LP}(T)\).

\[ \forall\, T:\quad \max_{\text{acquisitions } a \text{ of } T} t(a) \;\lt\; \min_{\text{releases } u \text{ of } T} t(u) \]

\(t(\cdot)\) is the time an event happens. Every acquisition of \(T\) comes before every release of \(T\). \(\mathrm{LP}(T)\) is the left-hand side.

6. Proof: 2PL schedules are conflict-serializable

Take any schedule \(S\) produced under 2PL, and any edge \(T_i \to T_j\) of its precedence graph. By definition, some operation \(o_i(x)\) conflicts with a later \(o_j(x)\). Conflicting operations need incompatible locks (section 1), so \(T_i\) must release its lock on \(x\) before \(T_j\) can acquire its own:

\[ \begin{aligned} \mathrm{LP}(T_i) &\lt t\big(\text{release}_i(x)\big) && \text{2PL for } T_i \\ t\big(\text{release}_i(x)\big) &\lt t\big(\text{acquire}_j(x)\big) && \text{incompatible locks} \\ t\big(\text{acquire}_j(x)\big) &\le \mathrm{LP}(T_j) && \text{definition of lock point} \end{aligned} \quad\Longrightarrow\quad \mathrm{LP}(T_i) \lt \mathrm{LP}(T_j) \]

So every edge points from an earlier lock point to a later one. A cycle \(T_1 \to T_2 \to \cdots \to T_k \to T_1\) would give \(\mathrm{LP}(T_1) \lt \mathrm{LP}(T_1)\), which is impossible. The graph is acyclic, and ordering the transactions by lock point gives an equivalent serial schedule. ∎

Worked example · where the proof breaks if one rule is broken

The first step, \(\mathrm{LP}(T_i) \lt t(\text{release}_i(x))\), is the only place 2PL is used. In section 4, \(T_1\) released A at step 3 (\(U_1(A)\)) and acquired B at step 11 (\(X_1(B)\)), so its "lock point" came after a release and the chain fails. An upgrade that drops \(S(N)\) and later acquires \(X(N)\) (section 3) is the same violation, just on a single item. Once any transaction does that, the theorem no longer covers the schedule.

7. Basic, strict and rigorous 2PL

VariantRule on top of 2PLWhat it adds
Basic 2PLnone: locks may be released any time after the lock point, even before commitconflict-serializable, but cascading aborts are possible
Strict 2PLexclusive locks are held until commit or abortstrict schedules, hence cascadeless (page 1, section 8)
Rigorous 2PLall locks are held until commit or abortalso orders transactions by commit time
Be careful · naming varies between textbooks

Silberschatz et al. use the three names above. Several other texts, and this project's own docs, use "strict 2PL" for "all locks held until the end", which the table calls rigorous. In an interview, say which definition you mean: "every lock is held until commit or abort."

Basic 2PL can also produce a schedule where \(T_2\) reads a value that \(T_1\) wrote and released but hasn't yet committed. If \(T_1\) then aborts, \(T_2\) must abort too. Holding exclusive locks until the end removes that possibility.

8. What 2PL does not solve: deadlock

2PL deliberately lets a transaction hold some locks while waiting for others. That's exactly the setup for a cycle of waits:

Worked example · tests/test4.txt

X₁(A)   X₂(B)   X₁(B) waits for T₂   X₂(A) waits for T₁

Both transactions follow 2PL perfectly, and neither can ever proceed. Page 4 covers how systems detect and break this.
