Prerequisite 4

Deadlocks, wait-for graphs and recovery

When 2PL transactions wait on each other in a circle, something has to give. This page covers the four families of fixes, how to find a cycle with depth-first search, why the victim must sit on the cycle, and how aging and backoff keep restarted transactions from starving.

A wait-for graph with a background detection thread […] that periodically scans for cycles and aborts the lowest-priority transaction involved."

"Periodically" brings a delay and a stale-snapshot problem, covered in section 7.

1. Deadlock and the Coffman conditions

A deadlock is a set of transactions where each is waiting for a lock held by another member of the set, so none can ever proceed on its own. It requires all four Coffman conditions at once:

ConditionMeaningUnder 2PL locking
Mutual exclusiona resource can't be shared freelyX locks exclude everyone, S excludes X
Hold and waithold some resources while waiting for morethe growing phase does exactly this
No preemptionresources can't be taken awaytrue, until the system aborts a transaction
Circular waita cycle of waitersdepends on the access order

Breaking any one condition makes deadlock impossible. Aborting a victim is a forced, after-the-fact preemption.

2. Four ways to handle deadlock

FamilyIdeaCost
Preventionmake a condition impossible: lock items in a fixed global order, or take every lock up front (conservative 2PL)needs the access set in advance, and restricts programs

Timeoutsabort any transaction that waits longer than \(\tau\)\(\tau\) is either too long (slow recovery) or too short (false aborts)

Worked example · wait-die never starves anyone

Timestamps are start times: \(\mathrm{TS}(T_1) = 5\) (older) and \(\mathrm{TS}(T_2) = 10\). If \(T_1\) requests a lock \(T_2\) holds, \(T_1\) is older, so it waits. If \(T_2\) requests a lock \(T_1\) holds, \(T_2\) is younger, so it dies (aborts) and restarts keeping \(\mathrm{TS} = 10\). As older transactions finish, \(T_2\) eventually becomes the oldest and can then only wait, never die. Keeping the original timestamp is the textbook form of aging (section 8).

3. Resource allocation graphs

A resource allocation graph (RAG) has two kinds of node, transactions and resources. An assignment edge \(R \to T\) means \(T\) holds \(R\). A request edge \(T \to R\) means \(T\) is waiting for \(R\). A claim edge (drawn dashed) means \(T\) may request \(R\) later. Claim edges are only needed by deadlock avoidance algorithms such as the Banker's algorithm.

When each resource has a single instance, the rule is simple: a cycle in the RAG means a deadlock, and a deadlock means a cycle.

Worked example · test4 as a RAG

\(A \to T_1\) (T₁ holds A), \(T_1 \to B\) (T₁ wants B), \(B \to T_2\), \(T_2 \to A\). Following the arrows: \(A \to T_1 \to B \to T_2 \to A\), a cycle.

4. Wait-for graphs

A wait-for graph (WFG) drops the resource nodes. It has an edge \(T_a \to T_b\) when \(T_a\) is waiting for a lock that \(T_b\) holds in an incompatible mode. It's built by scanning the lock table:

for each item x:
    for each waiting request (Ta, mode) on x:
        for each granted request (Tb, mode') on x with Tb != Ta and incompatible(mode, mode'):
            add edge Ta -> Tb

A cycle in the WFG is a deadlock. Under a FIFO grant policy (page 3, section 2), a waiter is also blocked by incompatible requests queued ahead of it, and those need edges too. Under barging, only holders block.

Worked example · tests/test5.txt

After \(X_1(A), X_2(B), X_3(C)\), the requests \(X_1(B), X_2(C), X_3(A)\) all wait. Edges: \(T_1 \to T_2\) (B), \(T_2 \to T_3\) (C), \(T_3 \to T_1\) (A). That's a 3-cycle.

Be careful · the WFG isn't the precedence graph

The precedence graph (page 1, section 7) records the order of conflicting operations that already happened, and its cycles mean non-serializable. The WFG records who is currently blocked on whom, and its cycles mean deadlock. A system can have a cycle-free WFG and still produce a non-serializable schedule if its locking is wrong.

5. Finding a cycle with depth-first search

Depth-first search (DFS) follows edges as deep as possible before backtracking. For cycle detection each node has three states: unvisited, on the current path (the recursion stack, often called grey), and finished. An edge to a node that's on the current path is a back edge, and a back edge exists exactly when the graph has a cycle.

dfs(u):
    on_stack[u] = visited[u] = true
    for v in out(u):
        if not visited[v]:
            if dfs(v): return true
        else if on_stack[v]:
            cycle = stack segment from v up to u     // the actual cycle members
            return true
    on_stack[u] = false
    return false
\[ \text{time} = O(V + E) \]

Each node is entered once and each edge examined once, over all roots. \(V\) = transactions in the graph, \(E\) = wait edges.

Worked example · a cycle with a tail

Edges \(T_1 \to T_2\), \(T_2 \to T_3\), \(T_3 \to T_2\), starting from \(T_1\). The stack grows \([T_1]\), then \([T_1, T_2]\), then \([T_1, T_2, T_3]\). From \(T_3\), the edge to \(T_2\) hits a node on the stack: a back edge. The cycle is the stack segment from \(T_2\) to \(T_3\), which is \(\{T_2, T_3\}\). \(T_1\) is on the stack but not in the cycle. It's a tail: blocked by the deadlock, but not part of it.

6. Victim selection

Recovery aborts one victim, which releases its locks. The victim must be a member of the cycle \(C\): aborting anything else releases no lock that a cycle member is waiting for, so the cycle survives.

\[ \text{victim} = \operatorname*{arg\,min}_{T \in C} \; \mathrm{cost}(T) \]

Common costs: priority, work done so far (fewest operations or locks, so the cheapest redo), youngest start time, or fewest previous restarts. The minimum is taken over the cycle's members \(C\), not over every node the search happened to visit.

Worked example · picking the tail wastes an abort

In the section 5 graph with equal costs, aborting \(T_1\) releases \(T_1\)'s locks, but \(T_2\) and \(T_3\) wait only on each other. The cycle remains, so a second abort (of \(T_2\) or \(T_3\)) is still needed. Result: two aborts where one would do, and \(T_1\), which was never deadlocked, pays for it.

7. Periodic detection: delay and stale snapshots

Running detection after every lock wait is expensive, so systems often run it every \(\Delta\) milliseconds. A deadlock that forms at a random moment then waits until the next pass:

\[ \mathbb{E}[\text{wait before detection}] \approx \frac{\Delta}{2} + t_{\text{pass}}, \qquad \text{worst case} \approx \Delta + t_{\text{pass}} \]

\(t_{\text{pass}}\) is how long one build-and-search pass takes. This assumes formation times are uniformly spread over the interval.

Worked example

With \(\Delta = 100\) ms and a 5 ms pass: about \(50 + 5 = 55\) ms on average, up to about 105 ms. For that whole time, every transaction in the cycle (and every tail behind it) holds its locks while doing nothing.

If the graph is built by querying the lock table one item at a time, with the latch taken and released per item, other threads change the table during the scan (the TOCTOU gap from page 2, section 7). The resulting graph can contain edges that no longer exist and miss new ones, so a "cycle" may be a phantom deadlock and cause an unnecessary abort.

8. Starvation and aging

A transaction that is chosen as victim again and again, or keeps being overtaken, is starving (page 3, section 2). Aging raises a transaction's standing the longer it has waited or the more times it has been aborted, so it eventually wins every contest. The simplest form counts restarts:

\[ p_k = p_0 + k \]

\(p_0\) is the initial priority, \(k\) the number of restarts so far, and a lower \(p\) means "abort me first". Wait-die (section 2) achieves the same thing by keeping the original timestamp.

Worked example

All transactions start at \(p_0 = 1\). A transaction restarted three times has \(p_3 = 4\). In a cycle with two fresh transactions at priority 1, the minimum is 1, so a fresh transaction is the victim and the veteran survives. Aging only helps if victim selection actually looks at these priorities and grants aren't handed to barging newcomers.

Be careful · aging a victim choice isn't priority scheduling

"Priority scheduling" normally means the scheduler hands out the resource (the CPU, or here a lock) to the highest-priority waiter first. Using priority only to decide whom to abort is victim selection. The two terms describe different mechanisms.

9. Restarting: exponential backoff with jitter

A victim that restarts immediately often recreates the same cycle. Exponential backoff waits longer after each abort, and jitter randomizes the wait so transactions aborted together don't retry in lockstep:

\[ b(k) = \min\!\big(b_0 \cdot 2^{k},\; b_{\max}\big) \cdot (1 + \varepsilon), \qquad \varepsilon \sim \mathrm{Uniform}[-0.3,\, 0.3] \]

\(b_0\) is the base delay, \(k\) the retry count, \(b_{\max}\) the cap, and \(\varepsilon\) the ±30% jitter. Note the order: jitter applied after the cap can push a delay above \(b_{\max}\).

Worked example · b₀ = 10 ms, b_max = 1,000 ms

Before jitter: \(k = 1 \to 20\), \(2 \to 40\), \(3 \to 80\), \(4 \to 160\), \(5 \to 320\), \(6 \to 640\), \(7 \to \min(1280, 1000) = 1000\) ms. A transaction aborted 7 times has slept \(20 + 40 + 80 + 160 + 320 + 640 + 1000 = 2{,}260\) ms before jitter. With \(\varepsilon = +0.3\) the last sleep is \(1{,}300\) ms, above the cap.

Without randomness, two transactions can abort each other forever in perfect rhythm. That's livelock: everyone is busy and nobody finishes.

10. More threads can mean less throughput

Throughput is committed transactions per second. Adding concurrent transactions helps while they rarely conflict, or while each spends time blocked on something other than locks (disk, network, a user). Once they mostly contend for the same few items, extra concurrency buys lock waits, deadlock-detection delay, aborted work and backoff sleeps. Throughput then falls as concurrency rises, which is called data-contention thrashing. Whether a multi-threaded lock manager beats running the same transactions one at a time is therefore an empirical question about a specific workload, and it has to be measured.
