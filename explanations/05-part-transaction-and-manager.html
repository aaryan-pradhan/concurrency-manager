Part 1

The facade: Transaction and ConcurrencyManager

How the engine is wired together, how a transaction's state machine enforces the two phases, which 2PL variant actually runs, and three defects that commit 47e3a19 fixed in this layer: a registry with no latch, a state field two threads wrote without synchronization, and a constructor that used objects before they existed.

"Coordinates transaction management using Two-Phase Locking protocol with deadlock detection" · "This is the facade of the whole project — the one class every test harness actually talks to. It doesn't implement locking or deadlock detection itself; it owns the classes that do (LockManager, ResourceAllocationGraph, DeadlockDetector), enforces the 2PL phase rules, and manages the collection of currently-active Transaction objects."

"Enforces the 2PL phase rules" is page 3, section 5. "Deadlock detection" is page 4, sections 4–6. "Owns the classes" is where C++ construction order (page 2, section 9) matters. "Currently-active Transaction objects" are shared between threads, which is where data races (page 2, section 2) come in. Every code line quoted on this page is from main at commit 47e3a19. Where that commit changed something, a yellow box shows what was there before.

1. The architecture in one picture

One Logger (not drawn) is shared by every box. The repo has two working drivers. The text-schedule harness uses a single global ConcurrencyManager cm("deadlock_test.log", 100); (tests/test_deadlock_detection.cpp:305), with a 100 ms detection interval. The benchmark creates a fresh ConcurrencyManager for every run, with a 10 ms interval and the log level set to WARNING (tests/benchmark.cpp:168). Both are covered in Part 4.

2. Transaction: a four-state record with an atomic state

// include/transaction.h:19-39 (abridged)
enum class TransactionState { GROWING, SHRINKING, COMMITTED, ABORTED };

class Transaction {
    int txnId;
    std::atomic<TransactionState> state;   // written by the owning thread and the deadlock detector
    std::set<int> locksHeld;               // touched only by the owning thread
    std::chrono::system_clock::time_point startTime;
    std::string metadata;
    int priority;                          // used only to choose deadlock victims
};

A new transaction starts in GROWING. Its first lock release calls beginShrinking(), which moves it to SHRINKING (src/transaction.cpp:24-42). ConcurrencyManager::acquireLock refuses any transaction that isn't GROWING (src/concurrency_manager.cpp:135). Those two checks together are the 2PL rule from page 3, section 5: once you release, you can never acquire again.

Two threads can try to end the same transaction at the same moment. The owning thread calls commit(), and the deadlock detector's thread may call abort() because it picked this transaction as a victim. Exactly one of them must win. The code gets that guarantee with compare-and-swap (CAS): state.compare_exchange_weak(expected, desired) atomically checks whether the current value equals expected. If it does, it stores desired and returns true. If not, it copies the current value into expected and returns false. The "weak" form may also fail spuriously, which is why it sits in a loop.

// src/transaction.cpp:44-64
bool Transaction::commit() {
    TransactionState s = state.load();
    while (s == TransactionState::GROWING || s == TransactionState::SHRINKING) {
        if (state.compare_exchange_weak(s, TransactionState::COMMITTED)) return true;
    }
    return false;
}
bool Transaction::abort() {
    TransactionState s = state.load();
    while (s != TransactionState::COMMITTED) {
        if (s == TransactionState::ABORTED || state.compare_exchange_weak(s, TransactionState::ABORTED)) return true;
    }
    return false;
}
Worked example · commit and abort race

Both threads load GROWING. Case 1: the detector's CAS runs first and stores ABORTED. The owner's CAS then fails, and s becomes ABORTED, which ends the while loop, so commit() returns false and the transaction restarts. Case 2: the owner's CAS runs first and stores COMMITTED. The detector's CAS fails, and s becomes COMMITTED, which ends its loop, so abort() returns false and the detector logs that the victim "already finished". There's no interleaving in which both return true.

commit 47e3a19 · bug hit and fixed · a racing state field

Before: state was a plain TransactionState. The detector thread wrote it (txn->abort()) while worker threads read it, with no mutex in common. That's a data race, so the behaviour was undefined (page 2, section 2). commit() and abort() each checked the state and then set it in two separate steps, so both could succeed. After: std::atomic<TransactionState> with the CAS loops above. tests/test_correctness.cpp:110-117 checks the sequential cases: abort then commit fails, and commit then abort fails.

priority (default 1) is read only by the deadlock detector, and a lower number is aborted first. locksHeld is a per-transaction copy of which resources it holds. It's updated only by the owning thread, through ConcurrencyManager, when LockManager::acquireLock returns true.

3. The registry: latched, and holding shared_ptrs

// include/transaction.h:136-146 · src/transaction.cpp:105-134 (abridged)
static std::unordered_map<txn_id_t, std::shared_ptr<Transaction>> active_transactions_;
static std::mutex registry_mutex_;

static void RegisterTransaction(const std::shared_ptr<Transaction>& txn);          // locks registry_mutex_
static void UnregisterTransaction(txn_id_t id, const Transaction* expected = nullptr); // locks it
static std::shared_ptr<Transaction> GetTransaction(txn_id_t id);                     // locks it, returns a copy

LockManager and DeadlockDetector use this registry to look up a transaction's state and priority by ID. Three things make it safe to share:

  • One mutex guards every insert, erase and lookup.
  • shared_ptr is a reference-counted pointer: the object is destroyed only when the last copy goes away. GetTransaction returns a copy, so a caller keeps the object alive even if its owner erases the map entry a microsecond later. A dangling pointer (page 2, section 7) can't happen.
  • The expected argument removes an entry only if it still points to that exact object. Cleanup for an old transaction can't delete a new transaction that has since registered under the same ID.

registry_mutex_ is a leaf lock: code holding it never acquires any other lock. So LockManager can call GetTransaction while holding its own mutex without creating a lock-ordering deadlock.

commit 47e3a19 · bug hit and fixed · an unlatched map of raw pointers

Before: std::unordered_map<txn_id_t, Transaction*>, with no mutex. Each Transaction registered itself in its constructor and unregistered in its destructor. Inserts and erases ran under ConcurrencyManager's mutex, lookups under LockManager's mutex or none, and no single mutex covered both. A restart erased and re-inserted entries while other threads called find, which was undefined behaviour (a rehash during a lookup can crash), and a lookup could return a pointer to a destroyed object. After: the latched shared_ptr registry above. Registration moved out of the constructor and into ConcurrencyManager, which registers only once the object is owned by a shared_ptr (src/transaction.cpp:10-11).

In the code · an ID doesn't name one attempt

The registry is keyed by ID alone. After a restart, the same ID refers to a different Transaction object. Code that remembers only the ID can't tell the old attempt from the new one. Part 3, section 6 shows the one place where that still causes a bug.

4. beginTransaction, and restarting under the same ID

// src/concurrency_manager.cpp:55-119 (abridged)
int ConcurrencyManager::beginTransaction(const std::string& metadata, int requestedTxnId, int priority) {
    std::lock_guard<std::mutex> lock(mtx);
    if (requestedTxnId == -1) txnId = nextTxnId++;                      // brand new
    else if (existing txn with that ID is ABORTED) {                    // restart
        lockManager.releaseAllLocks(txnId);                             // line 84
        Transaction::UnregisterTransaction(txnId, txn.get());
        transactions.erase(txnId);
    } else if (it exists and isn't ABORTED) return -1;
    auto txn = std::make_shared<Transaction>(txnId, metadata, priority);
    transactions[txnId] = txn;
    Transaction::RegisterTransaction(txn);
    return txnId;
}

Both harnesses restart an aborted transaction by calling beginTransaction(..., txnId, priority) with its old ID and a priority one higher (Part 4, sections 4 and 6). Line 84 clears out anything the old attempt still holds, so it can't hand its locks to the new one.

Worked example · file number ≠ runtime ID

In the text harness, IDs come from nextTxnId++ in the order threads get past the start barrier, not from the START T<n> number in the file. In one pre-fix audit run of tests/test.txt, file transaction T314 ran as ID 985, T525 as 957 and T916 as 958, per the TxnNum/TxnID columns of transaction_metrics.txt. That assignment code hasn't changed. Logs use runtime IDs, so tracing a file transaction through a log needs this mapping first.

5. acquireLock: the phase check, then delegation

// src/concurrency_manager.cpp:121-152 (abridged)
std::shared_ptr<Transaction> txn;
{   std::lock_guard<std::mutex> lock(mtx);
    txn = getTransaction(txnId);
    if (!txn) return false;
    if (txn->getState() != TransactionState::GROWING) return false;   // 2PL
}
bool acquired = lockManager.acquireLock(txnId, resourceId, lockType, wait);   // may sleep
if (acquired) txn->acquireLock(resourceId);
return acquired;

The phase check happens under ConcurrencyManager's mutex. The possibly long wait inside LockManager happens without it. If the facade held its mutex while waiting, one blocked transaction would stop every other transaction from beginning or committing (page 2, section 7).

The state check and the lock request are a check-then-act pair, so the detector can abort the transaction in between. LockManager re-checks under its own mutex (src/lock_manager.cpp:320), and its wait predicate checks again (Part 2, section 4). An aborted transaction is therefore never granted a lock once its ABORTED state is visible.

commit 47e3a19 · bug hit and fixed · a raw pointer outliving its mutex

Before: Transaction* txn was read under the mutex and used after it was released, possibly after a long wait. Any other thread erasing that transaction would have left it dangling. After: a shared_ptr copy, which keeps the object alive for as long as this call holds it.

6. Commit and abort, and which 2PL variant actually runs

// src/concurrency_manager.cpp:180-216 (abridged)
bool ConcurrencyManager::commitTransaction(int txnId, const std::function<void()>& beforeRelease) {
    ... look up txn under mtx ...
    bool committed = txn->commit();              // commit point: CAS to COMMITTED
    if (committed) {
        if (beforeRelease) beforeRelease();      // install buffered writes, all locks still held
        lockManager.releaseAllLocks(txnId);      // then release every lock at once
        Transaction::UnregisterTransaction(txnId, txn.get());  transactions.erase(txnId);
    }
    return committed;
}

The order matters. The CAS comes first, so once a transaction's writes start being installed, the detector can no longer abort it (abort() returns false on a committed transaction). The writes are installed before any lock is released, so no other transaction can read an item until its new value is fully in place. The benchmark uses the beforeRelease hook for exactly this (Part 4, section 6). abortTransaction (lines 218–250) does the same without the hook: CAS to ABORTED, release everything, unregister.

The API also offers releaseLock, which the text language exposes as RELEASE T<n>(item). So which 2PL variant runs depends on the driver:

So on every measured workload the behaviour is rigorous 2PL: shared and exclusive locks are both held until commit or abort (page 3, section 7). The project's docs call this "strict 2PL", as several textbooks do. Rigorous implies strict, so "strict 2PL" is accurate under either naming. The API alone is only basic 2PL, because releaseLock allows an early release. Before commit 47e3a19, a waiting S→X upgrade also gave up its S lock mid-transaction, which broke 2PL for that transaction. Part 2, section 6 covers that bug and its fix.

7. Construction order: the startup crash

// include/concurrency_manager.h:22-36 (current)
// NOTE: members are constructed in declaration order, not initializer-list order.
// logger must exist before rag, and both before lockManager, which logs and
// stores references to them in its constructor.
Logger logger;
ResourceAllocationGraph rag;
LockManager lockManager;
std::unique_ptr<DeadlockDetector> deadlockDetector;
commit 47e3a19 · bug hit and fixed · members used before they existed

Before: the declaration order was lockManager, logger, deadlockDetector, rag, while the initializer list said logger(...), rag(logger), lockManager(logger, rag). C++ ignores the list order (page 2, section 9), so lockManager was built first, holding references to a logger and rag that were still raw memory. Its constructor immediately called logger.info(...), which locked the unconstructed Logger's mutex. Clang warned about it: warning: field 'rag' will be initialized after field 'lockManager' [-Wreorder-ctor].

Audit result (macOS, Apple clang 17): every test file exited with code 134 at startup: libc++abi: terminating due to uncaught exception of type std::__1::system_error: mutex lock failed: Invalid argument. With only the declarations reordered, every file ran to completion.

After: declarations reordered, with the NOTE comment above, and the makefile now builds with -Wall -Wextra. The make test run recorded on the fix branch (2026-09-11) built and ran every test target.

The original author most likely ran on Linux, where a zero-filled global mutex happens to look unlocked (page 2, section 9). That's an inference, because Linux wasn't tested. Either way, the program's behaviour was undefined until this fix. docs/09 and docs/14 describe the intended order (logger → rag → lockManager), which the code now actually follows.

8. What the facade doesn't provide

  • No data inside the engine. A "read" is a shared lock and a "write" is an exclusive lock. The engine stores no values. The benchmark harness keeps one integer per item and buffers each transaction's writes until commit (Part 4, section 6). That's all-or-nothing installation in memory, done by the harness, not the engine.
  • No durability. There's no undo log, redo log or write-ahead log, and nothing is written to disk that recovery could replay. The .log files are human-readable traces. A crash loses every in-flight and committed effect (page 1, section 2).
  • No consistency rules. The engine enforces no constraints. That's the application's job.
  • No phantom protection. Locks are taken on item IDs. A phantom is a row that appears when a transaction repeats a range query ("all items with value > 10") because another transaction inserted it in between. Item locks can't prevent that, because the new item didn't exist to be locked. Real systems use predicate, range or next-key locks. Every workload here uses a fixed set of item IDs, so the question never comes up in the measurements.
  • Isolation tests do exist now: tests/test_correctness.cpp (16 checks, all passing in the make test run recorded on 2026-09-11) and the benchmark's per-run serializability and lost-update checks (Part 4, section 7).
