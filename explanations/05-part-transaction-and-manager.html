Part 1

The facade: Transaction and ConcurrencyManager

How the engine is wired together, how a transaction's state machine enforces the two phases, which 2PL variant actually runs, and two defects that sit below every result: a shared registry with no latch, and a constructor that uses objects before they exist.

Usestransactions and ACID from page 1, section 2 · data races and UB from page 2, section 2 · dangling pointers from page 2, section 7 · member initialization order from page 2, section 9 · the 2PL rule and variants from page 3, sections 5–7 · victims and restarts from page 4, section 6.
include/concurrency_manager.h · class comment, and docs/14-module-concurrency-manager.md
"Coordinates transaction management using Two-Phase Locking protocol with deadlock detection" · "This is the facade of the whole project — the one class every test harness actually talks to. It doesn't implement locking or deadlock detection itself; it owns the classes that do (LockManager, ResourceAllocationGraph, DeadlockDetector), enforces the 2PL phase rules, and manages the collection of currently-active Transaction objects."

"Enforces the 2PL phase rules" is page 3, section 5. "Deadlock detection" is page 4, sections 4–6. "Owns the classes" is where C++ construction order (page 2, section 9) matters. "Currently-active Transaction objects" are shared across threads, which is where data races (page 2, section 2) come in.

1. The architecture in one picture

A single Logger (not drawn) is shared by every box. One ConcurrencyManager object is a global in the working harness: ConcurrencyManager cm("deadlock_test.log", 100); (tests/test_deadlock_detection.cpp:303).

2. Transaction: a four-state record

enum class TransactionState { GROWING, SHRINKING, COMMITTED, ABORTED };

class Transaction {
    int txnId;  TransactionState state;  std::set<int> locksHeld;
    std::chrono::system_clock::time_point startTime;  std::string metadata;  int priority;
    ...
};

A new transaction starts GROWING. Transaction::releaseLock flips it to SHRINKING on its first release, and ConcurrencyManager::acquireLock refuses any transaction that isn't GROWING. Together those two checks are the 2PL rule from page 3, section 5:

// src/transaction.cpp:30-51
bool Transaction::releaseLock(int resourceId) {
    if (locksHeld.find(resourceId) == locksHeld.end()) return false;
    // In strict 2PL we only release locks after commit/abort,
    // but we implement the general case here
    if (state == TransactionState::GROWING) beginShrinking();
    ...
    locksHeld.erase(resourceId);
    return true;
}

priority (default 1) is used only by the deadlock detector to pick a victim, and a lower number is aborted first. locksHeld is a mirror of the lock table, updated only when LockManager::acquireLock returns true.

In the code · the phase flip depends on an unreliable mirror

The flip to SHRINKING happens only if resourceId is in locksHeld. Part 2, section 4 shows that a lock granted after waiting is reported as false, so it never enters locksHeld. An early RELEASE of such a lock frees it in the lock table but leaves the transaction GROWING, free to acquire more locks. None of the 1,000-transaction test files use RELEASE, so this never fires in the measured runs.

3. The static registry

// src/transaction.cpp:110-131
std::unordered_map<txn_id_t, Transaction*> Transaction::active_transactions_;
void Transaction::RegisterTransaction(Transaction* txn) { active_transactions_[txn->getId()] = txn; }
void Transaction::UnregisterTransaction(txn_id_t id)   { active_transactions_.erase(id); }
Transaction* Transaction::GetTransaction(txn_id_t id)  { auto it = active_transactions_.find(id); ... }

Every Transaction registers itself in its constructor and unregisters in its destructor, so that LockManager and DeadlockDetector can look up a transaction's state and priority by ID.

In the code · a data race on a hash map (UB)

Three different mutexes are involved, but none of them protects this map. Inserts and erases happen inside ConcurrencyManager's mutex (in beginTransaction, and the destructor runs when transactions.erase is called). Lookups happen inside LockManager's mutex (the wait predicate, acquireLock) and on the detector thread with no LockManager mutex held (DFS, BuildWaitForGraph). A restart erases and re-inserts entries while other threads call find. By page 2, section 2 that's undefined behaviour, and a rehash during a find can crash. Separately, Transaction::state is written by the detector thread (txn->abort()) and read by worker threads with no common mutex, which is another data race.

ThreadSanitizer couldn't confirm this on the audit machine: it failed to flag even a deliberate two-thread race there. These findings come from reading the code.

4. beginTransaction, and restarting under the same ID

// src/concurrency_manager.cpp:55-114 (abridged)
int ConcurrencyManager::beginTransaction(const std::string& metadata, int requestedTxnId, int priority) {
    std::lock_guard<std::mutex> lock(mtx);
    if (requestedTxnId == -1) txnId = nextTxnId++;              // new
    else if (existing txn is ABORTED) transactions.erase(txnId); // restart: replace it
    else if (existing txn is active/committed) return -1;
    transactions[txnId] = std::make_unique<Transaction>(txnId, metadata, priority);
    return txnId;
}

The harness restarts a deadlock victim by calling beginTransaction(..., txnId, priority) with its old ID and a priority one higher (Part 4, section 4).

Worked example · file number ≠ runtime ID

IDs come from nextTxnId++ in the order threads pass the barrier, not from the START T<n> number in the file. In one audit run of tests/test.txt, file transaction T314 ran as ID 985, T525 as 957 and T916 as 958 (from the TxnNum/TxnID columns of transaction_metrics.txt). Logs use runtime IDs, so tracing a file transaction through a log needs this mapping first.

5. acquireLock: the phase check, then delegation

// src/concurrency_manager.cpp:116-147 (abridged)
Transaction* txn;
{   std::lock_guard<std::mutex> lock(mtx);
    txn = getTransaction(txnId);
    if (!txn) return false;
    if (txn->getState() != TransactionState::GROWING) return false;   // 2PL
}
bool acquired = lockManager.acquireLock(txnId, resourceId, lockType, wait);
if (acquired) txn->acquireLock(resourceId);
return acquired;
In the code · a raw pointer outlives its mutex

txn is read under ConcurrencyManager::mtx and used after the mutex is released, possibly after a long wait inside lockManager.acquireLock. Only the owning thread erases its own transaction (on commit, abort or restart), so in the harness that pointer stays alive. But the detector's txn->abort() and the harness's lookup race on state (section 3), and any second caller that aborted this ID would leave txn dangling (page 2, section 7).

6. Commit and abort, and which 2PL variant actually runs

// src/concurrency_manager.cpp:175-233 (abridged)
bool ConcurrencyManager::commitTransaction(int txnId) {
    ... if (txn->commit()) { lockManager.releaseAllLocks(txnId); transactions.erase(txnId); }
}
bool ConcurrencyManager::abortTransaction(int txnId, const std::string& reason) {
    txn->abort(); lockManager.releaseAllLocks(txnId); transactions.erase(txnId); return true;
}

Commit and abort each release every lock at once, at the end. The API also offers releaseLock, which the test language exposes as RELEASE T<n>(item). Which variant runs therefore depends on the workload:

RELEASE operations in each test file
FileTransactionsRELEASE linesLocking behaviour
tests/test.txt1,0000all locks held to commit/abort*
tests/dead_test.txt1,0000all locks held to commit/abort
test1/4/5/6.txt2–30all locks held to commit/abort*

So in every measured run the intended behaviour is rigorous 2PL, which is "strict 2PL" in the docs' naming (page 3, section 7). The asterisk: when a transaction upgrades S→X and has to wait, the lock manager drops the S lock first (Part 2, section 6). That's a release before commit, followed by an acquisition, so it isn't 2PL of any variant for that transaction. The project's own README describes it as "Basic Two-Phase Locking (2PL) protocol (not strict 2PL)", which is true of the API, since RELEASE allows early release.

7. The constructor uses members that don't exist yet

// include/concurrency_manager.h:20-40 — declaration order decides construction order
class ConcurrencyManager {
    LockManager lockManager;                            // 1st: constructed first
    Logger logger;                                      // 2nd
    std::unique_ptr<DeadlockDetector> deadlockDetector; // 3rd
    ResourceAllocationGraph rag;                        // 4th
    ...
// src/concurrency_manager.cpp:6-10 — the list order below is ignored
ConcurrencyManager::ConcurrencyManager(...) : logger(logFilePath, false), rag(logger), lockManager(logger, rag), nextTxnId(1)

lockManager is built first, with references to logger and rag, which are still raw memory. Its constructor immediately runs logger.info("Lock Manager initialized ..."), which locks the unconstructed Logger's mutex. That's the UB from page 2, section 9. Clang says so at compile time: warning: field 'rag' will be initialized after field 'lockManager' [-Wreorder-ctor].

Result · audit build on macOS (Apple clang 17)

Unmodified repo: every test file (test1, test4, test5, test6) exits with code 134 at startup: libc++abi: terminating due to uncaught exception of type std::__1::system_error: mutex lock failed: Invalid argument.
Same code, with only the member declarations reordered (logger, rag, then lockManager): all files run to completion.

What this supports. The bug is real and deterministic on macOS. Because the global cm is zero-filled before construction and glibc's unlocked mutex is all zeros, the original build most likely ran on Linux by luck. I couldn't test Linux, so that last point is an inference. What it doesn't. Even where it runs, the program's behaviour is undefined, and docs/09 and docs/14 are wrong to state that construction order is logger → rag → lockManager.

In the code · every later number on these pages uses the reordered build

All runs in Parts 2–4 and the results page used a scratch copy with exactly this one change. The serial baseline additionally joins each thread right after starting it. The repository itself was not modified.

8. What the facade doesn't provide

  • No data. A "read" is a shared lock and a "write" is an exclusive lock. No value is stored, read or changed (page 1, section 2).
  • No atomicity or durability machinery. Abort releases locks and sets a flag. There's no undo, redo or write-ahead log.
  • No isolation test. No test in the repo checks that the resulting schedules are serializable. The audit's log replay is described in Part 2, section 6.
  • An unimplemented method. checkForDeadlocks() is declared and called by src/2pl_test_runner.cpp but never defined, so that runner doesn't link.
