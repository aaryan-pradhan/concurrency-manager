Part 2

The LockManager: granting, waiting, upgrading

The lock table, its compatibility check, how a blocked transaction sleeps and wakes, how releases hand locks to waiters, and the snapshot the deadlock detector reads. It also covers the upgrade bug the audit found in real logs, which let committed schedules be non-serializable, and how commit 47e3a19 fixed it.

docs/11-module-lock-manager.md
"This is the busiest, most detailed class in the project — it's the actual mechanism behind everything described in Locks and Concurrency Control. […] This means: while an upgrade is pending, the transaction is not holding any lock at all on that resource for a brief window — it gave up the shared lock to ask for the stronger one."

The docs describe the pre-fix upgrade and call the window harmless. Page 3, sections 3 and 6 show why it isn't: giving up S and later taking X is a release followed by an acquisition, which breaks 2PL. Section 6 shows the audit's evidence that the window was hit in real runs, and the current code, which keeps the S lock. The docs haven't been updated.

1. Data structures

// include/lock_manager.h:18-53 (abridged)
enum class LockType { SHARED, EXCLUSIVE };
struct LockRequest { int transactionId; LockType type; bool granted; };

// resourceId -> granted and waiting requests. An upgrading transaction has two entries
// while it waits: its granted SHARED lock and an ungranted EXCLUSIVE request.
std::unordered_map<int, std::vector<LockRequest>> lockTable;
mutable std::mutex mtx;            // one latch for the whole table
std::condition_variable cv;        // one condition variable for every waiter
std::set<int> waitingTransactions;
ResourceAllocationGraph &rag;

There's a single global latch and a single condition variable for every resource. Every acquire, release and detector snapshot in the process serializes on mtx, and every release wakes every waiter, whatever resource each one is waiting for. Most of the performance story in the results comes from those two lines.

2. isCompatible: the matrix, with the queue ignored

// src/lock_manager.cpp:17-37 (abridged)
if (request.type == LockType::SHARED)
    return none_of(requests, [](const LockRequest& r){ return r.granted && r.type == LockType::EXCLUSIVE; });
return none_of(requests, [&](const LockRequest& r){ return r.granted && r.transactionId != request.transactionId; });

This is the page 3, section 1 matrix exactly. S is compatible unless some granted lock is X. X is compatible only if no other transaction holds anything, so a transaction's own S lock doesn't block its upgrade.

In the code · a barging grant policy, with no priority

Only granted entries are consulted. A newly arriving S request is therefore granted at once, even if an X request has been queued for a long time. That's the writer-starvation pattern from page 3, section 2. Transaction priority plays no part in who gets a lock. It's used only when choosing a deadlock victim (Part 3, section 7).

The unlock before waiting follows page 2, section 7. If a thread slept holding mtx, the whole engine and the detector would stop with it. The first row is checked under mtx because the detector always marks a victim ABORTED before it takes mtx to release that victim's locks. Once a thread holds mtx and sees the state, no aborted transaction can slip past the check.

4. waitForLock: three reasons to wake

// src/lock_manager.cpp:263-306 (abridged)
std::unique_lock<std::mutex> lock(mtx);
auto canProceed = [&]() {
    if (isAbortedInternal(txnId)) return true;                        // (a) chosen as a victim
    long index = pendingRequestIndexInternal(txnId, resourceId);
    if (index < 0) return true;                                       // (b) a releaser already granted it
    return isCompatible(resourceId, lockTable[resourceId][index]);   // (c) grantable now
};
cv.wait(lock, canProceed);
long index = pendingRequestIndexInternal(txnId, resourceId);
if (isAbortedInternal(txnId)) { erase the pending request; return false; }
if (index >= 0) { grantInternal(resourceId, index); return true; }   // (c): grant it myself
return holdsSufficientInternal(txnId, resourceId, lockType);          // (b): confirm and report true

A waiter sleeps on the shared cv and re-checks its predicate every time it's woken, whether by a real change or a spurious wakeup (page 2, section 5). The predicate is true in three cases: (a) the transaction was aborted, (b) some releasing thread already granted the request, so it's no longer pending, or (c) the request has become grantable. Case (b) happens often, because releases hand locks to waiters directly (section 5).

Worked example · tests/test_correctness.cpp:47-62

T201 takes X on R7. T202 asks for S on R7, which is incompatible, so it queues and sleeps. T201 releases. releaseLock calls grantWaitersInternal, which sets T202's request to granted, then calls notify_all. T202 wakes: it isn't aborted, it has no pending request, so the predicate is true through (b). After the wait, index < 0, so it returns holdsSufficientInternal(202, 7, SHARED), which is true. Both checks in that test passed in the make test run recorded on 2026-09-11.

commit 47e3a19 · bug hit and fixed · a granted wait reported as failure

Before: after waking, the code searched only for an ungranted request. In case (b) it found none and fell through to return false. The lock was held in the table, but the caller was told it wasn't, so locksHeld missed the resource and the harness counted a "lock failure". On dead_test.txt, one pre-fix run recorded 6,911 lock failures against 6,701 restarts. Isolation wasn't affected, because other transactions check the table, which was correct. After: case (b) confirms the grant and returns true.

5. Releasing: grant waiters, then wake everyone

// src/lock_manager.cpp:96-124 (grantWaitersInternal, abridged)
bool granted = true;
while (granted) {
    granted = false;
    // pass 1: pending upgrades (the requester already holds S here)
    for (i in requests) if (isUpgrade(i) && isCompatible(i)) { grantInternal(i); granted = true; break; }
    // pass 2: any pending request, in vector (arrival) order
    for (i in requests) if (!granted && !requests[i].granted && isCompatible(i)) { grantInternal(i); granted = true; break; }
}

// src/lock_manager.cpp:412-430 (releaseLock, abridged)
requests.erase(it);  rag.removeAssignmentEdge(resourceId, txnId);
if (requests.empty()) lockTable.erase(resourceId); else grantWaitersInternal(resourceId);
notifyWaitingTransactions();   // cv.notify_all()

Each release hands the resource to every waiter that has become compatible, one grant at a time, re-scanning after each grant. Pending upgrades go first, because their holder already has S on the item: granting a fresh request ahead of an upgrade could let a new writer in between the upgrader's read and its write. Every grant goes through grantInternal (lines 73–94), which also updates the RAG, so the graph stays in step with the table. releaseAllLocks (lines 435–491), called on every commit and abort, removes both the transaction's granted locks and its pending requests from every queue, then does the same per touched resource. It always notifies, because the transaction being aborted may itself be asleep and must wake up to see that.

Worked example · a writer can still be skipped

R has granted S for T1 and T4, and pending requests [T2 wants X, T3 wants S], in that order. T4 releases. Pass 1 finds no upgrade. Pass 2 tries T2's X, which still conflicts with T1's S, so it's skipped. T3's S is compatible, so it's granted. T2 now waits for both T1 and T3. If readers keep overlapping, T2 never runs. Arrival order is respected only among requests that are compatible at the moment of the scan.

In the code · one condition variable for the whole table

Every release wakes every waiting thread in the process, including threads waiting on unrelated resources. Each one then re-acquires the one mtx just to re-check its predicate. That's the \(R \times W\) herd from page 2, section 6. As a hypothetical: 10,000 releases with 100 threads waiting at each would be \(10{,}000 \times 100 = 1{,}000{,}000\) wakeups, nearly all of which go straight back to sleep. No run counted wakeups. The standard fix is one condition variable (or wait queue) per resource, or per waiting request.

commit 47e3a19 · bug hit and fixed · RAG drift

Before: releases set req.granted = true directly, without adding the RAG assignment edge, so the resource allocation graph drifted out of step with the lock table. After: every grant goes through grantInternal.

6. Upgrades keep the S lock

// src/lock_manager.cpp:209-261 (upgradeLockInternal, abridged)
bool canUpgrade = all_of(requests, [txnId](auto& r){ return !r.granted || r.transactionId == txnId; });
if (canUpgrade) { it->type = LockType::EXCLUSIVE; return GRANTED; }   // sole holder: convert in place
if (!wait)      { return DENIED; }
// Queue an EXCLUSIVE request but KEEP the granted SHARED lock.
if (pendingRequestIndexInternal(txnId, resourceId) < 0) {
    requests.push_back(LockRequest(txnId, LockType::EXCLUSIVE));
    rag.addRequestEdge(txnId, resourceId);
}
return QUEUED;                                   // caller unlocks and calls waitForLock

While an upgrade waits, the transaction holds two entries on the item: its granted S and a pending X. Its S still conflicts with every other X request, so nobody can write the item in the gap. When the other readers leave, pass 1 of section 5 grants the X, and grantInternal erases the now-redundant S entry.

Worked example · tests/test_correctness.cpp:23-44

T101 and T102 both hold S on R1. T101 asks for X: T102 still holds S, so the X is queued and T101 keeps its S. Check: holdsLock(101, 1) is true. T102 releases, and pass 1 grants T101's X. T103 then asks for X without waiting, and is refused. Check: no other transaction got X in the upgrade window. T101's call returns true, and it ends up with a single X entry. All four checks passed in the same recorded run.

A consequence: upgrade deadlocks. If T1 and T2 both hold S(F) and both ask for X(F), each pending X waits for the other's S. That's a cycle in the wait-for graph (page 3, section 3). The detector aborts one of them, and its releaseAllLocks removes both its S and its pending X, after which the survivor's upgrade is granted. tests/test1.txt is built around exactly this pattern.

commit 47e3a19 · bug hit and fixed · the upgrade gap 
// before (upgradeLockInternal, wait == true)
requests.erase(it);                                              // give up the granted SHARED lock
requests.push_back(LockRequest(txnId, LockType::EXCLUSIVE));     // queue as a fresh X request
return false;                                                    // caller waits via waitForLock

While the upgrade waited, the transaction held nothing on the item. Any other transaction could be granted X, write, commit and release. The upgrader then got X and wrote based on its earlier, now stale read. By page 3, section 6 that's a release followed by an acquisition, so the lock-point proof no longer applied.

How the old bug showed up: log replay of pre-fix runs

Every grant, upgrade and release is logged while mtx is held, so the order of lines in the engine log is the true order of lock-table changes. The audit replayed each pre-fix log with two checks: (i) were incompatible locks ever held at the same time, and (ii) for each "waiting to upgrade" event, was another transaction granted X on that resource before the upgrader got its X, with the upgrader then committing?

Conflicts on N: \(r_{314} \lt w_{525}\) gives \(T_{314} \to T_{525}\), and \(w_{525} \lt w_{314}\) gives \(T_{525} \to T_{314}\). That's a cycle, so the schedule isn't conflict-serializable (page 1, section 7). It's the lost-update shape S₂, and \(T_{916}\) forms a second cycle with \(T_{314}\) the same way.

What this supports. Before the fix, the lock table never granted incompatible locks (check i passed in every log), but the upgrade path let committed transactions form non-serializable schedules: 4 upgraders per test.txt run, out of 1,000 committed transactions (0.4%). After the fix, the regression test above passes, and the benchmark's precedence-graph check passes in every run at up to 64 threads (results, section 5). What it doesn't. The pre-fix counts come from two timing-dependent runs. The project stored no values then, so the evidence is the schedule order, not a wrong number. And the fix doesn't make the engine serializable at every scale: a separate race remains at 1,000 threads (Part 3, section 6).

7. getWaitForEdges: one snapshot for the detector

// src/lock_manager.cpp:513-531 (abridged)
std::lock_guard<std::mutex> lock(mtx);                 // one acquisition for the whole table
for (auto& [resource, requests] : lockTable)
    for (auto& waiter : requests) if (!waiter.granted)
        for (auto& holder : requests)
            if (holder.granted && holder.transactionId != waiter.transactionId
                && !(waiter.type == SHARED && holder.type == SHARED))
                edges.emplace_back(waiter.transactionId, holder.transactionId);   // waiter -> holder

An edge means "this waiter is blocked by this holder". A waiting S is blocked only by granted X locks. A waiting X is blocked by every other granted lock. That's page 4, section 4's rule, and it matches isCompatible. Because the whole scan happens under one acquisition of mtx, the edges describe a single instant.

Worked example · three resources

R1: T1 granted S, T2 granted S, T3 waiting X → edges T3→T1 and T3→T2. R2: T4 granted X, T5 waiting S → edge T5→T4. R3: T1 granted S, T2 granted S, T1 waiting X (an upgrade) → edge T1→T2 only, because T1 doesn't wait for itself. The snapshot is {T3→T1, T3→T2, T5→T4, T1→T2}. It has no cycle, so there's no deadlock yet. If T2 now asks for X on R1, the edge T2→T1 is added, and T1→T2→T1 is a deadlock.

8. The RAG, and a file write inside the critical path

LockManager keeps a ResourceAllocationGraph in step with the table by calling rag.addAssignmentEdge, addRequestEdge, removeAssignmentEdge and clearTransaction while holding mtx. The text harness calls cm.logResourceAllocationGraph(...) after every operation of every transaction, and that runs:

// src/resource_manager.cpp:211-231
void ResourceAllocationGraph::logToFile(const std::string& info) const {
    std::lock_guard<std::recursive_mutex> lock(mtx);                 // RAG latch held...
    std::ofstream ragLogFile = std::ofstream("rag_log.txt", std::ios::app); // ...across open,
    ... ragLogFile << toString();  ragLogFile.flush();                // whole-graph write, flush
}
In the code · lock-table operations can queue behind disk I/O (text harness)

A thread inside LockManager holds mtx and needs the RAG latch. A harness thread may be holding that RAG latch while it opens the log file and writes out the whole graph. So in the text harness, every lock-table operation can end up waiting on a file write. One pre-fix test.txt run produced a rag_log.txt of 108,518,195 bytes. The benchmark never calls logResourceAllocationGraph, and it runs the logger at WARNING, so its numbers don't include this cost. Two smaller costs remain even there: LockManager builds its INFO message strings under mtx before the logger discards them, and Logger::log flushes every line it does write while holding its own mutex (src/logger.cpp:48-58).

9. What the history shows
