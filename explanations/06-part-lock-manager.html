Part 2

The LockManager: granting, waiting, upgrading

The lock table, its compatibility check, how a blocked transaction sleeps and wakes, and the upgrade path that gives up a shared lock mid-transaction. The audit replayed the logs and found committed schedules that aren't serializable, and this page shows one of them line by line.

Usesthe precedence-graph test and schedule S₂ from page 1, section 7 · mutexes and condition variables from page 2, sections 3–5 · the thundering herd from page 2, section 6 · unlock-before-wait from page 2, section 7 · compatibility, barging and upgrades from page 3, sections 1–3 · the lock-point proof from page 3, section 6 · RAG edges from page 4, section 3 · the facade and the reordered build from Part 1.
docs/11-module-lock-manager.md
"This is the busiest, most detailed class in the project — it's the actual mechanism behind everything described in Locks and Concurrency Control. […] This means: while an upgrade is pending, the transaction is not holding any lock at all on that resource for a brief window — it gave up the shared lock to ask for the stronger one."

The docs notice the upgrade window but describe it as harmless. Page 3, sections 3 and 6 say otherwise: giving up S and later taking X is a release followed by an acquisition, which is outside 2PL. Section 6 below checks whether that window was actually exploited in real runs.

1. Data structures

// include/lock_manager.h:17-53
enum class LockType { SHARED, EXCLUSIVE };
struct LockRequest { int transactionId; LockType type; bool granted; };

std::unordered_map<int, std::vector<LockRequest>> lockTable;  // resource -> granted + waiting
mutable std::mutex mtx;                     // one latch for the whole table
std::condition_variable cv;                 // one condition variable for every waiter
std::set<int> waitingTransactions;
const std::chrono::milliseconds lockTimeout{5000};   // declared, never used
ResourceAllocationGraph &rag;

This is a single global latch and a single condition variable for all resources. Every acquire, release and detector query in the process serializes on mtx, and every release wakes every waiter, whatever resource it waits for.

2. isCompatible: the matrix, with the queue ignored

// src/lock_manager.cpp:124-143
if (request.type == LockType::SHARED)
    return std::none_of(..., [](const LockRequest& r){ return r.granted && r.type == LockType::EXCLUSIVE; });
return std::none_of(..., [&request](const LockRequest& r){ return r.granted && r.transactionId != request.transactionId; });

This is the page 3, section 1 matrix exactly. S is compatible unless some granted lock is X, and X is compatible only if no other transaction holds anything.

In the code · a barging grant policy, with no FIFO and no priority

Only granted entries are consulted, so a newly arriving S request is granted even when an X request has been queued for a long time (the writer-starvation example on page 3, section 2). When a lock is released, waiting requests are granted by scanning the vector in insertion order (section 5). Transaction priority plays no part in who gets a lock. It's used only when choosing a deadlock victim (Part 3).

The unlock before waiting follows page 2, section 7: if a thread slept holding mtx, the whole engine and the detector would stop.

4. waitForLock, and a success reported as failure

// src/lock_manager.cpp:18-110 (abridged)
auto canAcquireLock = [...]() {
    Transaction* txn = Transaction::GetTransaction(txnId);
    if (txn == nullptr || txn->getState() == TransactionState::ABORTED) return true;
    if (lockTable.find(resourceId) == lockTable.end()) return true;
    auto it = /* this transaction's request on resourceId */;
    if (it == requests.end() || it->granted) return true;      // (a) already granted
    return isCompatible(resourceId, *it);                       // (b) grantable now
};
std::unique_lock<std::mutex> lock(mtx);
cv.wait(lock, canAcquireLock);
if (aborted) { remove my waiting request; return false; }
auto it = find_if(..., [txnId](const LockRequest& req){ return !req.granted && req.transactionId == txnId; });
if (it != requests.end() && isCompatible(resourceId, *it)) { it->granted = true; ...; return true; }
return false;
In the code · a waiter that is granted by the releaser returns false

Releases grant waiters directly: releaseLock and releaseAllLocks set req.granted = true for every compatible waiting request before calling notify_all (section 5). The woken waiter's predicate is true through branch (a). The post-wait search then looks only for a request with !req.granted, finds none, and falls through to return false. The lock is held in the table, but the caller is told it isn't.

Consequences: (1) ConcurrencyManager skips txn->acquireLock, so locksHeld is missing that resource (Part 1, section 2). (2) The harness counts a "lock failure". (3) Isolation isn't affected by this bug, because the lock table, which is what other transactions check, is correct. The transaction goes on to its next operation while actually holding the lock, and releases it at commit via releaseAllLocks, which scans the table.

Result · tests/test4.txt, reordered build

The transaction that was not aborted: Restarts 0 · Locks Acq 1 · Locks Fail 1 · Committed. It took its first X lock immediately, waited for its second, was pre-granted when the victim's locks were released, got false, and committed anyway. tests/test6.txt (no conflicts, so no waits) shows 0 failures. On dead_test.txt, run 1 recorded 6,911 lock failures against 6,701 restarts.

What this supports. The "Locks Fail" column in transaction_metrics.txt mixes real failures (aborted while waiting) with successful waits, so it can't be read as a failure rate. What it doesn't. It isn't evidence of an isolation bug. That's section 6.

5. Releasing: pre-grant, then wake everyone

// src/lock_manager.cpp:405-428 (releaseLock) — releaseAllLocks does the same per resource
requests.erase(it);
rag.removeAssignmentEdge(resourceId, txnId);
for (auto& req : requests)
    if (!req.granted && isCompatible(resourceId, req)) req.granted = true;   // vector order
notifyWaitingTransactions();                                              // cv.notify_all()

releaseAllLocks, called on every commit and abort, first strips the transaction's own waiting requests from every queue (the "CRITICAL FIX" comment at line 437, needed when a victim is aborted mid-wait). It then releases each granted lock the same way.

In the code · one condition variable for the whole table

Every release wakes every waiting thread in the process, including threads waiting on unrelated resources, and each re-checks its predicate under the one mtx. That's the \(R \times W\) herd from page 2, section 6. dead_test.txt run 1 logged \(R = 16{,}402\) lock releases. If, hypothetically, 100 threads were waiting on average, that would be about \(16{,}402 \times 100 \approx 1.64\) million wakeups. The audit didn't measure \(W\). The pre-grant path also sets granted without adding the RAG assignment edge, so the RAG drifts out of step with the table.

6. The upgrade gap breaks serializability

// src/lock_manager.cpp:252-283 (upgradeLockInternal, abridged)
bool canUpgrade = all_of(requests, [txnId](auto& r){ return !r.granted || r.transactionId == txnId; });
if (canUpgrade)      { it->type = LockType::EXCLUSIVE; return true; }   // in place: fine
else if (!wait)      { return false; }
else {
    requests.erase(it);                                  // give up the granted SHARED lock
    requests.push_back(LockRequest(txnId, LockType::EXCLUSIVE));   // queue as a fresh X request
    return false;                                        // caller now waits via waitForLock
}

While the upgrade waits, the transaction holds nothing on the item. Any other transaction can be granted X on it, write, commit and release. The upgrader then gets X and writes based on its earlier, now stale read. By page 3, section 6 that's a release before an acquisition, so the lock-point proof no longer applies.

Did it happen? Log replay

Every grant, upgrade and release is logged while mtx is held, so the order of lines in deadlock_test.log is the true order of lock-table changes. The audit replayed each log with two checks: (i) were incompatible locks ever held together, and (ii) for each "waiting to upgrade" event, was another transaction granted X on that resource before the upgrader got its X, followed by the upgrader committing?

Conflicts on N: \(r_{314} \lt w_{525}\) gives \(T_{314} \to T_{525}\), and \(w_{525} \lt w_{314}\) gives \(T_{525} \to T_{314}\). That's a cycle, so the schedule isn't conflict-serializable (page 1, section 7). It's the lost-update shape S₂, and \(T_{916}\) forms a second cycle with \(T_{314}\) the same way. Line numbers are from the audit's log file, and they differ between runs.

What this supports. The lock table never granted incompatible locks (check i passed in every log), but the upgrade path let committed transactions form non-serializable schedules: 4 upgraders per test.txt run, out of 1,000 committed transactions (0.4%). The claim "guarantees serializability" is contradicted by the project's own workload. What it doesn't. dead_test.txt never touches the same item twice in one transaction, so it has no upgrades and no such cases. The project stores no values, so no wrong number was ever computed. The evidence is the schedule order. The counts are from two runs, and they depend on timing.

In the code · the fix

Keep the S entry granted. Record a pending-upgrade flag, or queue an X request with the S still held. Grant the X once every other granted lock is gone, preferring upgrade requests over new ones. Two concurrent upgraders then deadlock (page 3, section 3), which the detector already handles.

7. The RAG, and a file write inside the critical path

LockManager keeps a ResourceAllocationGraph in step with the table by calling rag.addAssignmentEdge, addRequestEdge, removeAssignmentEdge and clearTransaction while holding mtx. The harness calls cm.logResourceAllocationGraph(...) after every operation of every transaction, which runs:

// src/resource_manager.cpp:211-231
void ResourceAllocationGraph::logToFile(const std::string& info) const {
    std::lock_guard<std::recursive_mutex> lock(mtx);                 // RAG latch held...
    std::ofstream ragLogFile = std::ofstream("rag_log.txt", std::ios::app); // ...across open,
    ... ragLogFile << toString();  ragLogFile.flush();                // whole-graph write, flush
}
In the code · lock-table operations queue behind disk I/O

A thread inside LockManager holds mtx and needs the RAG latch. A harness thread holds the RAG latch while opening the log file and writing out the entire graph. So every lock-table operation can end up waiting on a file write. One test.txt run produced a rag_log.txt of 108,518,195 bytes. Logger also flushes every line under its own mutex. These are likely throughput costs, but the audit didn't measure them one at a time (see the results page).

8. From timeouts to detection: what the history shows

git · commit 15e65d5 "victim selection and performance metrics done" (2025-04-12)

Before: bool success = cv.wait_for(lock, lockTimeout, canAcquireLock);, and on timeout it logged "timed out waiting for lock" and gave up, which was the README's "5-second timeout prevents indefinite waiting". After: cv.wait(lock, canAcquireLock); with no timeout, followed by an abort check ("aborted while waiting for lock"), because deadlocks are now broken by the detector's victim abort. The lockTimeout constant and the README text were left behind, which is why they no longer describe the code.

git · commit 0b53d06 "Bug fixed" (2025-04-11)

The RAG's shared static std::ofstream ragLogFile (opened with truncation) was removed. Each logToFile call now opens rag_log.txt in append mode, and initLogFile became a normal member function. The commit doesn't say which bug it fixed. A side effect: src/2pl_test_runner.cpp still calls ResourceAllocationGraph::initLogFile(...) as if it were static, which is one of the two reasons that runner no longer compiles.
