Part 3

The DeadlockDetector: wait-for graph, DFS, victim

A background thread rebuilds the wait-for graph every 100 ms, searches it with DFS and aborts the lowest-priority transaction it finds. It broke every deadlock in every audit run. A unit test against the real class shows it can abort a transaction that isn't in the cycle.

include/deadlock_detector.h · class and method comments
"DeadlockDetector - Implements a wait-for graph and cycle detection algorithm to detect and resolve deadlocks between transactions. […] Looks for a cycle using DFS algorithm. If it finds a cycle, stores the transaction id of the minimum priority transaction in the cycle in txn_id and returns true. […] Runs cycle detection in the background. Builds the wait-for graph on the fly and breaks any cycles by aborting the minimum priority transaction in each cycle."

The comment makes three promises. "Wait-for graph … on the fly" is section 2, "cycle detection … using DFS" is section 3, and "the minimum priority transaction in the cycle" is section 4. Section 4 tests that last phrase directly against the class.

1. The background thread

// src/deadlock_detector.cpp:360-377, 19-38
void DeadlockDetector::DetectionThread() {
    while (running_) {
        RunCycleDetection();
        std::unique_lock<std::mutex> lock(cv_mutex_);
        cv_.wait_for(lock, std::chrono::milliseconds(detection_interval_ms_), [this]{ return !running_; });
    }
}
// destructor: running_ = false; cv_.notify_one(); detection_thread_.join();

The detector sleeps between passes using wait_for with a predicate, so shutdown wakes it at once instead of waiting out the interval. ConcurrencyManager defaults to 200 ms and the harness passes 100 ms. By page 4, section 7, a deadlock therefore sits for about 50 ms plus one pass on average, and up to about 100 ms plus one pass, before anyone acts.

2. BuildWaitForGraph: a 10,000-ID scan, one latch grab at a time

// src/deadlock_detector.cpp:272-339 (abridged)
wait_for_graph_.clear();
for (int resource_id = 0; resource_id < 10000; resource_id++) {
    auto waiters = lock_manager_.getWaitingTransactions(resource_id);   // locks LockManager::mtx
    if (waiters.empty()) continue;
    auto holders = lock_manager_.getLockHolders(resource_id);           // locks it again
    for (auto w : waiters)  /* skip aborted */
        for (auto h : holders) if (h != w /* and not aborted */) AddEdge(w, h);   // waiter -> holder
}

Edges go from each waiter to every holder of the same resource. With barging (Part 2, section 2), holders are the only thing that can block a waiter, so this matches page 4, section 4.

In the code · three costs of scanning IDs instead of the table
  • Latch traffic: each pass takes and releases LockManager::mtx at least 10,000 times, even though the harness only ever uses resource IDs 1–26 (test.txt) or 1–12 (dead_test.txt). At roughly 10 passes per second that's at least 100,000 latch acquisitions per second, all contending with the transaction threads.
  • A hidden ceiling: a resource with ID ≥ 10,000 is never inspected, so a deadlock on it would never be broken, and (with no lock timeout, Part 2, section 8) its transactions would wait forever.
  • No consistent snapshot: the table changes between per-ID calls, so the graph can include edges that are already gone (page 4, section 7). An abort based on such an edge is a phantom-deadlock abort. The audit didn't measure how often that happens.

3. HasCycle and DFS

// src/deadlock_detector.cpp:136-175 (abridged)
std::sort(nodes.begin(), nodes.end());                    // deterministic root order
for (node : nodes) if (!visited[node]) {
    txn_id_t current_min_priority_txn = node;             // seed = the DFS root
    if (DFS(node, visited, in_stack, current_min_priority_txn)) { keep lowest across roots; cycle_found = true; }
}

// src/deadlock_detector.cpp:82-134 (abridged)
bool DFS(node, visited, in_stack, min_priority_txn) {
    visited[node] = in_stack[node] = true;
    for (neighbor : wait_for_graph_[node]) {
        if (!visited[neighbor]) {
            if (DFS(neighbor, ...)) { if (prio(node) < prio(min_priority_txn)) min_priority_txn = node; return true; }
        } else if (in_stack[neighbor]) {
            if (prio(node) < prio(min_priority_txn)) min_priority_txn = node;  return true;
        }
    }
    in_stack[node] = false;  return false;
}

This is the three-state DFS from page 4, section 5, and it's \(O(V + E)\) per call. It stops at the first back edge.

4. Victim selection: the minimum over the search path, not the cycle

Two details decide who gets aborted. The running minimum is seeded with the DFS root. As the recursion unwinds after a back edge, it compares every node on the path from the root down, including nodes before the cycle begins. The comparison is a strict <. The victim is therefore the lowest-priority node on the whole search path, tail included, and if the root ties for lowest, the root is kept.

What this supports. With equal priorities, which is every transaction's state on its first attempt (priority 1), the detector can abort a tail transaction that is merely waiting on a deadlock. By page 4, section 6 that abort doesn't break the cycle, so the loop in section 5 must abort again. Even with priorities in play, a lower-priority tail node would be chosen over the cycle members. What it doesn't. The audit didn't count how many of the 2,843–6,731 restarts per run were tail aborts, because the detector doesn't log the graph at the default INFO level. So the effect on restart counts is unquantified.

In the code · the fix

On a back edge from node to neighbor, take the stack segment from neighbor to node as the cycle, and choose the victim only among those members. Break ties deterministically, for example by the youngest start time or the fewest locks held.

5. RunCycleDetection: abort, remove, search again

// src/deadlock_detector.cpp:191-253 (abridged)
BuildWaitForGraph();
while (true) {
    txn_id_t min_priority_txn;
    if (!HasCycle(min_priority_txn)) break;
    Transaction *txn = Transaction::GetTransaction(min_priority_txn);
    if (txn != nullptr) {
        txn->abort();                                   // state = ABORTED (unsynchronized write)
        lock_manager_.releaseAllLocks(min_priority_txn); // pre-grants waiters, notify_all
        remove min_priority_txn and all edges into it from wait_for_graph_;
    } else {
        logger_.error("Failed to find transaction ...");   // node NOT removed
    }
}

Looping until no cycle remains handles several deadlocks in one pass, and it also cleans up after a wasted tail abort (section 4). The victim's own thread notices at its next check: its wait predicate returns because it's ABORTED, waitForLock returns false, and the harness restarts it (Part 4, section 4).

In the code · two latent hazards
  • A possible endless loop: if the chosen victim has already been destroyed (it committed after the graph was built), GetTransaction returns nullptr, and the node stays in the graph. HasCycle then finds the same cycle every time round. Not observed in audit runs.
  • The abort bypasses the facade: the detector sets the state and releases locks, but ConcurrencyManager isn't told, and the victim stays in its map until the harness restarts it under the same ID. If the victim was no longer waiting (a stale edge), it finds out only at its next operation.

6. Where the "aging" actually lives

The detector only reads priorities. Nothing in src/ ever changes one after beginTransaction. The raising happens in the test harness, which increments a local priority each time its transaction is aborted and passes it to the restart:

// tests/test_deadlock_detection.cpp:370-384 (READ case; WRITE is the same)
if (cm.getTransactionState(txnId) == TransactionState::ABORTED) {
    recordTxnRestart(txnNum);
    i = -1;                       // restart from the first operation
    priority++;                   // aged: less likely to be the next victim
    int backoff = calculateBackoff(priority);
    std::this_thread::sleep_for(std::chrono::milliseconds(backoff));
}

That's aging by restart count, \(p_k = 1 + k\) (page 4, section 8), applied to victim selection only. Lock grants ignore priority (Part 2, section 2), so it isn't priority scheduling, and a newcomer can still barge past an aged waiter. Section 4's search-path rule also weakens it, because an aged transaction's priority protects it only when every lower-priority node on the search path happens to be a cycle member.

7. Two graphs, one used

ResourceAllocationGraph::detectDeadlock() implements a correct DFS over request and assignment edges, returning the cycle path with resources encoded as negative numbers. Nothing calls it on a schedule. It was meant to be driven by ConcurrencyManager::checkForDeadlocks() from src/2pl_test_runner.cpp, and that method was never defined. All automatic detection comes from DeadlockDetector's separately built WFG. Because pre-granted waits don't add assignment edges (Part 2, section 5), the RAG would have drifted from the lock table anyway.
