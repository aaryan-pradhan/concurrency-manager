Part 3

The DeadlockDetector: wait-for graph, DFS, victim

A background thread takes a single-instant snapshot of who waits for whom, finds cycles with depth-first search, and aborts the lowest-priority member of each cycle. This page covers what commit 47e3a19 changed here, the one race that still breaks serializability at 1,000 threads, and what the "aging" really does.

Usescondition variables and wait_for from page 2, section 5 · WFG construction from page 4, section 4 · DFS and back edges from page 4, section 5 · victim selection from page 4, section 6 · detection delay from page 4, section 7 · starvation and aging from page 4, section 8 · CAS-based abort() from Part 1, section 2 · the registry, and that an ID doesn't name one attempt, from Part 1, section 3 · restart under the same ID from Part 1, section 4 · releaseAllLocks from Part 2, section 5 · getWaitForEdges from Part 2, section 7.
include/deadlock_detector.h · class and method comments (current)
"DeadlockDetector - Implements a wait-for graph and cycle detection algorithm to detect and resolve deadlocks between transactions. […] Looks for a cycle using DFS. If it finds one, stores in txn_id the member of that cycle with the lowest priority (ties: the highest transaction id) and returns true. Only nodes on the cycle itself are candidates, never nodes merely waiting on it. […] Runs one detection pass: builds the wait-for graph from a consistent lock-table snapshot and breaks every cycle by aborting one victim per cycle."

The comment makes four promises. "A consistent lock-table snapshot" is section 2. "Cycle detection using DFS" is section 3. "The member of that cycle with the lowest priority" is section 4. "Breaks every cycle" is section 5. Section 6 is the one situation where "breaking" a cycle damages a different transaction.

1. The background thread

// src/deadlock_detector.cpp:293-310, 20-39 (abridged)
void DeadlockDetector::DetectionThread() {
    while (running_) {
        RunCycleDetection();
        std::unique_lock<std::mutex> lock(cv_mutex_);
        cv_.wait_for(lock, std::chrono::milliseconds(detection_interval_ms_), [this]{ return !running_; });
    }
}
// destructor: { lock cv_mutex_; running_ = false; cv_.notify_one(); }  detection_thread_.join();

The detector sleeps between passes using wait_for with a predicate, so shutdown wakes it at once instead of waiting out the interval. The interval \(I\) is 200 ms by default in ConcurrencyManager, 100 ms in the text harness and 10 ms in the benchmark.

\[ t_{\text{pass}} \;\le\; \text{delay} \;\le\; I + t_{\text{pass}}, \qquad \mathbb{E}[\text{delay}] \approx \frac{I}{2} + t_{\text{pass}} \]

"Delay" is the time from a deadlock forming to its victim being aborted. \(I\) is the sleep between passes, and \(t_{\text{pass}}\) is how long one pass takes. The average assumes deadlocks form at uniformly random moments between passes. No run measured \(t_{\text{pass}}\).

Worked example · 100 ms vs 10 ms

Text harness, \(I = 100\): a deadlock waits about \(100/2 = 50\) ms on average, and up to 100 ms, plus one pass. Benchmark, \(I = 10\): about 5 ms on average, and up to 10 ms. Every one of those milliseconds, the deadlocked transactions keep holding their locks, so everyone queued behind them waits too. The cost of a shorter interval is that each pass takes the lock-table mutex and scans the whole table, which steals latch time from real transactions ten times as often.

2. BuildWaitForGraph: one snapshot of a single instant

// src/deadlock_detector.cpp:254-271 (abridged)
wait_for_graph_.clear();
for (auto [waiter_id, holder_id] : lock_manager_.getWaitForEdges()) {   // one mtx acquisition
    auto waiter = Transaction::GetTransaction(waiter_id);
    auto holder = Transaction::GetTransaction(holder_id);
    if (!waiter || waiter->getState() == ABORTED || !holder || holder->getState() == ABORTED) continue;
    AddEdgeInternal(waiter_id, holder_id);                                // waiter -> holder
}

The graph is rebuilt from scratch on every pass, from the snapshot in Part 2, section 7. Edges that involve a transaction already marked ABORTED are skipped, because that transaction's locks are about to be released anyway.

Why a cycle in this snapshot is a real deadlock. Each edge W→H means W is asleep waiting for a lock that H holds, and a sleeping transaction releases nothing. The lock manager also keeps an invariant: every code path that could make a pending request grantable (releaseLock, releaseAllLocks) grants it before unlocking mtx. So at the instant of the snapshot, no pending request was grantable. If every member of a cycle waits on the next, none of them can release, and none can proceed. The cycle can't dissolve by itself, so aborting a member is never wasted on a phantom deadlock, meaning a cycle that exists only because edges were read at different times.

commit 47e3a19 · bug hit and fixed · a 10,000-ID scan

Before: for (int resource_id = 0; resource_id < 10000; resource_id++), calling getWaitingTransactions(id) and then getLockHolders(id), each taking and releasing mtx. That caused three problems. It took at least 10,000 latch acquisitions per pass, although the text workloads only use IDs 1–26. It never inspected resource IDs ≥ 10,000, so deadlocks on them were never broken. And the table changed between calls, so the graph could mix edges from different moments, which allowed phantom deadlocks. After: one getWaitForEdges() call under a single acquisition.

3. FindCycle: DFS that keeps its path

// src/deadlock_detector.cpp:90-125 (abridged)
bool FindCycle(node, visited, in_stack, path, cycle) {
    visited[node] = in_stack[node] = true;
    path.push_back(node);
    for (neighbor : wait_for_graph_[node]) {
        if (!visited[neighbor]) {
            if (FindCycle(neighbor, visited, in_stack, path, cycle)) return true;
        } else if (in_stack[neighbor]) {                        // back edge node -> neighbor
            cycle.assign(find(path, neighbor), path.end());     // the segment neighbor..node
            return true;
        }
    }
    in_stack[node] = false;  path.pop_back();
    return false;
}
// HasCycleInternal (133-184): try unvisited roots in sorted ID order, stop at the first cycle

This is the three-state DFS from page 4, section 5, with one addition. It keeps the current root-to-node path, so on a back edge it can cut out exactly the nodes that form the cycle. Nodes earlier on the path only wait on the cycle (page 4, section 6 calls them the tail). One search is \(O(V + E)\), for \(V\) waiting or holding transactions and \(E\) wait edges. Roots are sorted, so the same graph always gives the same answer.

Worked example · the graph from tests/test_correctness.cpp:65-90

Edges T1→T2, T2→T3, T3→T2. Sorted roots are [1, 2, 3]. Start at T1: path [1]. Go to T2: path [1, 2]. Go to T3: path [1, 2, 3]. T3's neighbour T2 is visited and still on the stack, so 3→2 is a back edge. The cycle is the path from T2 onward: [2, 3]. T1 is a tail: it waits on the deadlock but isn't part of it, and aborting it would break nothing.

4. Victim selection: lowest priority within the cycle

// src/deadlock_detector.cpp:160-177 (abridged)
txn_id_t victim = cycle.front();  int victimPriority = INT_MAX;
for (txn_id_t member : cycle) {
    auto txn = Transaction::GetTransaction(member);
    int priority = txn ? txn->getPriority() : INT_MIN;          // vanished txn: drop it first
    if (priority < victimPriority || (priority == victimPriority && member > victim)) {
        victim = member;  victimPriority = priority;
    }
}

The victim is the cycle member with the lowest priority number. Ties go to the highest ID, and in both harnesses IDs are handed out in increasing order, so a tie usually picks a transaction that started later. A member that no longer exists sorts first, so it's simply removed from the graph.

Worked example · the two cases in the regression test

Equal priorities (all 1): the cycle is [2, 3], so the tie goes to the higher ID, T3. The recorded test log shows Deadlock cycle detected: T2 T3 -> victim T3 (priority: 1). T1 = 0, T2 = 5, T3 = 1: T1 has the lowest priority overall, but it's a tail, so it isn't a candidate. Among {T2 = 5, T3 = 1}, T3 is lowest, so T3 is the victim. Both checks passed in the recorded make test run.

commit 47e3a19 · bug hit and fixed · victims chosen from the whole search path

Before: the running minimum was seeded with the DFS root and updated at every node as the recursion unwound, including nodes before the cycle began. The victim was the lowest-priority node on the whole path, tail included. An audit unit test against the old class showed it:

GraphPrioritiesCycleOld victimIn cycle?
T1→T2, T2→T3, T3→T2all 1{T2, T3}T1no
sameT1=5, T2=1, T3=1{T2, T3}T3yes
T4⇄T5both 1{T4, T5}T4yes

Aborting a tail breaks no cycle (page 4, section 6), so the old loop had to abort again. Every transaction starts with priority 1, so the highlighted case was the common one. After: candidates come only from the extracted cycle.

5. RunCycleDetection: abort, release, remove, repeat

// src/deadlock_detector.cpp:186-234 (abridged)
std::lock_guard<std::mutex> run(run_mutex_);     // one pass at a time (thread or checkForDeadlocks)
std::lock_guard<std::mutex> lock(graph_mutex_);
BuildWaitForGraph();
while (HasCycleInternal(victimId)) {
    auto txn = Transaction::GetTransaction(victimId);
    if (txn != nullptr && txn->abort()) {                       // line 205: CAS to ABORTED
        logger_.warning("Aborting transaction T" + id + " ...");  // line 207
        lock_manager_.releaseAllLocks(victimId);                  // line 212
    } else {
        logger_.info("Deadlock victim T" + id + " already finished; removing it ...");
    }
    remove victimId and every edge into it from wait_for_graph_;
}

One pass breaks every cycle it can find. Each loop iteration removes at least one node, and the graph is finite, so the loop runs at most \(V\) times. The victim's worker thread finds out through its wait predicate: branch (a) of Part 2, section 4 fires, acquireLock returns false, and the harness restarts the transaction under the same ID with priority + 1. If the victim committed between the snapshot and the abort, abort() returns false (Part 1, section 2), and its locks are already being released by its own commit.

commit 47e3a19 · bug hit and fixed · a possible endless loop

Before: if the victim had already been destroyed, GetTransaction returned nullptr, the node stayed in the graph, and HasCycle found the same cycle forever. The audit never observed this. After: the node is removed whether or not the abort happened.

6. The remaining race: a late release hits the restarted transaction

Lines 205 and 212 aren't atomic together. Between them, the detector logs a warning, which takes the logger's mutex and flushes a file, and then it must win LockManager's one mutex against every worker thread. If the detector stalls there for longer than the victim takes to back off and restart, the release lands on the wrong transaction:

detector thread                              victim's worker thread (ID 17)
snapshot has cycle T17 -> T42 -> T17
T17.abort()   state = ABORTED        (205)
logger_.warning("Aborting T17 ...")  (207)   woken by some other release's notify_all,
   ... stalled: descheduled, or                sees ABORTED, acquireLock returns false
   waiting for LockManager::mtx ...            benchmark backoff: 1.4-2.6 ms
                                               beginTransaction(..., 17, ...):
                                                 releaseAllLocks(17)   old attempt's locks freed
                                                 registers a NEW Transaction with ID 17
                                               new T17 gets X on item 5, starts 1 ms of "I/O"
releaseAllLocks(17)                  (212)
   removes the NEW T17's X on item 5
   grantWaitersInternal: X on item 5 -> T42
                                               new T17 installs its write to item 5,
                                               while T42 also holds X on item 5

Two transactions now hold X on the same item at overlapping times, so their operations can interleave in both orders, and the committed schedule can contain a precedence-graph cycle. The root cause is Part 1, section 3's warning: releaseAllLocks takes an ID, and by the time it runs, that ID names a different attempt.

Result · evidence for the race (benchmark config B, 1,000 threads: 1,000 txns × 4 ops, 1,000 items, 20% writes, 1 ms per op)
  • Sweep, benchmark_results/results.csv, 5 runs: runs 1 and 3 failed the serializability check. 3 and 101 transactions respectively couldn't be placed in any serial order. The lost-update check passed in all 5.
  • Instrumented reproduction (earlier session's scratchpad: same config, -O2, 20 runs, with the repo's behaviour plus counters): 12 of 20 runs had at least one detector release that found granted locks belonging to a newer attempt (20 such locks in total), and 4 of 20 runs failed the serializability check.
  • Same reproduction, with the detector skipping the release when the registry now holds a different object for that ID: the skip triggered 20 times across 14 runs, and 0 of 20 runs failed. Median throughput was 2,475.8 txn/s with the repo's behaviour and 2,372.5 with the skip, a difference well within run-to-run noise at this thread count.
  • At 64 threads or fewer: 0 failures in the 100 recorded runs across the three benchmark configurations (results, section 5).

What this supports. The instrumentation ties the failures to this mechanism: stale releases happened in the failing runs, and removing them removed the failures. What it doesn't. 4 of 20 against 0 of 20 is small-sample evidence (results, section 9 works out the uncertainty), and why the race needs 1,000 threads to show up is an inference: with 1,000 runnable threads on 8 cores, a thread being descheduled for milliseconds is routine. The fix isn't in the repo.

In the code · the fix

Make the release name the attempt, not just the ID. Pass the aborted Transaction object (or an incarnation counter) to releaseAllLocks and skip the release if the registry now holds a different object. That's exactly what the scratch fix did. Alternatives: give every restart a fresh ID, or mark the victim aborted and release its locks inside the same LockManager critical section.

7. Where the "aging" actually lives

The detector only reads priorities. Nothing in src/ changes one after beginTransaction. The raising happens in the harnesses, which increment a local priority each time their transaction is aborted and pass it to the restart:

// tests/test_deadlock_detection.cpp:372-386 (READ; WRITE and COMMIT paths are the same)
if (cm.getTransactionState(txnId) == TransactionState::ABORTED) {
    recordTxnRestart(txnNum);  i = -1;  priority++;
    std::this_thread::sleep_for(std::chrono::milliseconds(calculateBackoff(priority)));
}
// tests/benchmark.cpp:246-250
aborts++;  attempt++;  priority++;  sleep for backoff(attempt) with jitter;

That's aging by restart count, \(p_k = 1 + k\) after \(k\) aborts (page 4, section 8), and it affects victim selection only. Lock grants ignore priority (Part 2, sections 2 and 5), so an aged transaction can still wait behind newcomers and get pulled into fresh cycles. Aging also only helps relative to the other members of a cycle. When every member has been aborted many times, one of them still has to die.

Result · priorities reached in benchmark config C (1,000 txns, 20 items, 30% writes, 1 ms per op), from benchmark_results/logs/io1ms_high_engine.log

64 threads, 5 runs: 3,629–3,979 aborts per run, and the highest priority any transaction reached per run was 10, 19, 12, 10 and 11. So in one run a single transaction was aborted 18 times. 1,000 threads, run 0: 220,943 aborts between the first and last logged abort, about 5 h 58 min apart, and the highest priority reached was 1,981: one transaction was aborted 1,980 times. Run 1 was killed after about 2 h 22 min and 175,970 aborts, with a maximum priority of 577.

What this supports. Aging did not prevent starvation under heavy contention. Some transactions were aborted hundreds to thousands of times. What it doesn't. Those 1,000-thread runs were also exposed to the section 6 race, and the log can't separate its effect. A scheme with a real guarantee keeps each transaction's original timestamp across restarts and never aborts the oldest, as wait-die and wound-wait do (page 4, section 2).

8. Two graphs, one used

ResourceAllocationGraph::detectDeadlock() implements a correct DFS over request and assignment edges. It returns the cycle path, encoding resources as negative numbers. Nothing calls it during a run. ConcurrencyManager::checkForDeadlocks(), which was undefined until 47e3a19, now runs one DeadlockDetector pass instead. All automatic detection comes from the wait-for graph on this page. The RAG is kept for tracing: it's what the text harness writes to rag_log.txt.

9. Did it work?

Result · recorded runs
  • Regression test, end to end (tests/test_correctness.cpp:93-107): two transactions, each holding one X and requesting the other's. Exactly one was aborted and the survivor committed (recorded make test run).
  • Benchmark, every completed run: all transactions committed, which the benchmark requires before it prints "all runs serializable". That covers 70 CSV rows (configs A and B), config C at 1–64 threads (35 runs), and the make test quick check (6 runs).
  • Cost under contention (config C): 8, 23, 96, 433, 1,479 and 3,844 aborts per run at 2, 4, 8, 16, 32 and 64 threads. Every one is a deadlock victim, because nothing else aborts transactions in the benchmark.
  • Config C at 1,000 threads: never finished in usable time (section 7).
  • Pre-fix text harness (not re-measured since the fix): every run finished, with 2,843–2,953 restarts on test.txt and 6,701–6,731 on dead_test.txt.

What this supports. Detection plus recovery kept every run up to 64 threads live, and every transaction eventually committed. What it doesn't. Deadlocks weren't prevented or "eliminated". They formed thousands of times and were broken by throwing work away. Recovery wasn't bounded in time at 1,000 threads, and it didn't stop individual transactions from starving.
