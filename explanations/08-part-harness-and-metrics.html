Part 4

The harness: workloads, restarts and what the metrics measure

The program that turns a text schedule into 1,000 threads, restarts deadlock victims with growing backoff, and writes transaction_metrics.txt. Every metric is defined here exactly as the code computes it, since the CV's numbers would have to come from this file.

This is the most sophisticated program in the repository, and it's the one the makefile's run target actually builds and runs (against tests/test4.txt)." · "tests/generate_diff.py […] deliberately creates small batches of transactions that each touch the same 3 items, but in alternating order […] a textbook way to manufacture circular wait conditions on purpose."

"Feature-complete" covers the restart loop (section 4) and the metrics report (section 5). "Circular wait conditions on purpose" is the Coffman condition from page 4, section 1. Section 2 checks how the generated file actually behaves.

1. The schedule language, and how it's grouped

Lines are START T<n>, R<n>(item), W<n>(item), C<n>, A<n> and RELEASE T<n>(item), with // comments. parseTestFile collects every line into a per-transaction list keyed by n. The file's global line order is thrown away, and each list runs on its own thread from top to bottom. Item names map to resource IDs 1, 2, 3, … in the order threads first touch them (getResourceId).

In the code · the item map is itself a data race

dataItemToResourceId is a global std::map and cnt a global int. Worker threads call getResourceId, which inserts into both with no mutex, right after the barrier releases all 1,000 threads at once. That's page 2, section 2's undefined behaviour in the harness itself. A corrupted map could give one item two IDs, which would silently remove the conflict between its readers and writers.

Worked example · why dead_test.txt deadlocks every batch

generate_diff.py picks 3 items per batch of 10 and sets ops_per_transaction=4, so the first 2 items are read and the rest (just 1) written. That's R, R, W, not the two reads plus two writes the name suggests. Batch 1:

T1, T3, T5, T7, T9: R(K) R(B) W(J)    T2, T4, T6, T8, T10: R(J) R(B) W(K)

Every odd transaction holds \(S(K)\) and needs \(X(J)\). Every even one holds \(S(J)\) and needs \(X(K)\). Once all ten hold their first S lock, each odd transaction waits on all five evens and vice versa: a complete bipartite wait graph with \(5 \times 5 \times 2 = 50\) edges, full of cycles. All 100 batches follow this pattern (checked by script), and they share a pool of only 12 items, so batches collide with each other too.

3. One thread per transaction, released together

// tests/test_deadlock_detection.cpp:571-592
startBarrier = std::make_shared<std::barrier<>>(numTransactions);
for (const auto &ops : transactionOperations)
    threads.emplace_back(runTransaction, txnNum, ops, 1);   // priority starts at 1
for (auto &t : threads) t.join();
std::this_thread::sleep_for(std::chrono::milliseconds(100 * 2));
writeTransactionMetricsToFile(testFile, testStartTime);

Each thread calls startBarrier->arrive_and_wait() first, so on the 1,000-transaction files 1,000 threads start their first operation together. That's the "1,000 threads" in the project's story, plus the detector and main threads. It maximizes contention on purpose, on an 8-core machine (page 2, section 1).

4. Restart with aging and backoff

After every read or write, the thread checks whether its transaction was aborted. If so, it records a restart, raises its priority, sleeps, and restarts from START under the same ID (Part 3, section 6 shows the code):

// tests/test_deadlock_detection.cpp:306-322
int calculateBackoff(int retryCount) {
    int baseBackoff = 20, maxBackoff = 5000;
    int backoff = std::min(baseBackoff * (1 << retryCount), maxBackoff);
    int jitter = (std::rand() % 60) - 30;           // -30 .. +29
    backoff = backoff * (100 + jitter) / 100;
    return std::max(backoff, 5);
}
// called as calculateBackoff(priority) right after priority++
\[ b(p) = \Big\lfloor \min\big(20 \cdot 2^{p},\ 5000\big) \cdot \tfrac{100 + j}{100} \Big\rfloor, \qquad j \in \{-30, \ldots, 29\},\quad p = 1 + k \]

\(k\) is the restart number (1 for the first restart), so the first backoff uses \(p = 2\). The argument is named retryCount but receives the priority. \(j\) comes from rand() % 60 - 30. The floor is C++ integer division.

Worked example · cost of being aborted

Low end of the \(k = 1\) row: \(80 \times 70 / 100 = 56\). High end: \(80 \times 129 / 100 = 103.2 \to 103\). Capped row: \(5000 \times 129 / 100 = 6{,}450\) ms, so the "5 second maximum" is exceeded by jitter applied after the cap (page 4, section 9).

A transaction restarted 5 times sleeps a base total of \(80 + 160 + 320 + 640 + 1280 = 2{,}480\) ms, between \(56 + 112 + 224 + 448 + 896 = 1{,}736\) and \(103 + 206 + 412 + 825 + 1{,}651 = 3{,}197\) ms with jitter. After 8 restarts the base total is \(2{,}480 + 2{,}560 + 5{,}000 + 5{,}000 = 15{,}040\) ms, and that's sleep alone, before any lock waits.

Success rate \(= 100 \times 1000 / (1000 + 2843 + 0) = 100{,}000 / 3{,}843 = 26.02\%\), printed as 26.0%. Throughput \(= 1000 / 9.31 \approx 107.4\) txn/s, printed as 107.47 (the duration is shown rounded). For test4.txt, 2 commits in 0.38 s gives 5.29 txn/s. Of that 0.38 s, 0.20 s is the fixed final sleep, so throughput on the tiny files says nothing about the engine.

Be careful · "100% commit rate" and the harness's own success rate measure different things

"Every transaction eventually committed" means \(\text{completed} / \text{transactions} = 1000/1000\). The harness's "Transaction Success Rate" on the same run is 26.0% (test.txt) or 13.0% (dead_test.txt). Anyone who opens transaction_metrics.txt sees the second number first.

What this supports. On dead_test.txt, no transaction committed before its fifth abort, and most took 6–8. With the section 4 table, 7 restarts alone mean about 10 s of base backoff (\(2{,}480 + 2{,}560 + 5{,}000 = 10{,}040\) ms), which is consistent with the 25 s average latency. On test.txt, 43–48% of transactions never restarted, while most of the rest restarted 5–6 times. What it doesn't. The audit can't split the restarts into necessary aborts, tail aborts (Part 3, section 4) and phantom-edge aborts, and it has only two runs per file.

7. A latent way to exit without committing

The harness checks for an abort only after a read or write. If the detector aborts a transaction whose wait already ended (a stale edge, Part 3, section 2) and that thread's next operation is COMMIT, then Transaction::commit() refuses because the state is ABORTED. recordTxnEnd is never called, and the thread falls off the end of its operation list uncommitted. None of the 1,000-transaction runs in the audit showed an uncommitted row (0 in 5 runs). The code doesn't prevent it.
