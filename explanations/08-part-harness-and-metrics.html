Part 4

The harnesses: workloads, restarts and what the metrics measure

Two programs drive the engine. The original text-schedule harness starts 1,000 threads at once. The benchmark added in commit 47e3a19 runs the same workload serially and with a pool of threads, then checks every run for serializability and lost updates. Every metric and check is defined here exactly as the code computes it.

2. The text schedule language, and how it's grouped

Lines are START T<n>, R<n>(item), W<n>(item), C<n>, A<n> and RELEASE T<n>(item), with // comments. parseTestFile collects every line into a list per transaction, keyed by n. The file's global line order is thrown away, and each list runs on its own thread from top to bottom. So the file doesn't dictate an interleaving: the OS scheduler and the lock manager decide it. Item names map to resource IDs 1, 2, 3, … in the order threads first touch them (getResourceId).

commit 47e3a19 · bug hit and fixed · the item map was a data race

Before: dataItemToResourceId (a global std::map) and the counter cnt were updated by up to 1,000 threads with no mutex, right after the barrier released them all at once. That's undefined behaviour, and a corrupted map could have given one item two IDs, silently removing the conflict between its readers and writers. After: getResourceId holds resourceIdMutex (tests/test_deadlock_detection.cpp:19-21, 56).

Worked example · why dead_test.txt deadlocks every batch

generate_diff.py picks 3 items per batch of 10 transactions and reads the first 2 and writes the last 1, so each transaction is R, R, W. Batch 1:

T1, T3, T5, T7, T9: R(K) R(B) W(J)    T2, T4, T6, T8, T10: R(J) R(B) W(K)

Every odd transaction holds \(S(K)\) and needs \(X(J)\). Every even one holds \(S(J)\) and needs \(X(K)\). Once all ten hold their first S lock, each odd transaction waits on all five evens and vice versa. That's a complete bipartite wait graph with \(5 \times 5 \times 2 = 50\) edges, full of cycles. All 100 batches follow this pattern, and they share a pool of only 12 items, so batches collide with each other too.

4. Text harness: 1,000 threads at once, and restart with backoff

// tests/test_deadlock_detection.cpp:582-606 (abridged)
startBarrier = std::make_shared<std::barrier<>>(numTransactions);
for (const auto& ops : transactionOperations) threads.emplace_back(runTransaction, txnNum, ops, 1);
for (auto& t : threads) t.join();
std::this_thread::sleep_for(std::chrono::milliseconds(100 * 2));   // then write metrics

Each thread calls startBarrier->arrive_and_wait() first, so on the 1,000-transaction files 1,000 worker threads start their first operation together, alongside the main thread and the detector thread. That maximizes contention on purpose, on an 8-core machine. After every read or write, the thread checks whether its transaction was aborted. If so, it records a restart, raises its priority, sleeps, and restarts from START under the same ID.

// tests/test_deadlock_detection.cpp:308-324
int calculateBackoff(int retryCount) {
    int baseBackoff = 20, maxBackoff = 5000;
    int backoff = std::min(baseBackoff * (1 << retryCount), maxBackoff);
    int jitter = (std::rand() % 60) - 30;           // -30 .. +29
    backoff = backoff * (100 + jitter) / 100;
    return std::max(backoff, 5);
}   // called as calculateBackoff(priority) right after priority++
\[ b(p) = \Big\lfloor \min\big(20 \cdot 2^{p},\ 5000\big) \cdot \tfrac{100 + j}{100} \Big\rfloor \text{ ms}, \qquad j \in \{-30, \ldots, 29\},\quad p = 1 + k \]

\(k\) is the restart number (1 for the first restart), so the first backoff uses \(p = 2\). The argument is named retryCount but receives the priority. \(j\) comes from rand() % 60 - 30, and the floor is C++ integer division.

Low end of the \(k = 1\) row: \(80 \times 70 / 100 = 56\). High end: \(80 \times 129 / 100 = 103.2 \to 103\). commit 47e3a19 · bug hit and fixed · a way to exit without committing

Before: the abort check ran only after a read or write. A transaction chosen as a victim after its last lock was granted reached COMMIT, commit() refused because the state was ABORTED, and the thread fell off the end of its operation list uncommitted. None of the 5 pre-fix 1,000-transaction runs hit it. After: a failed commit on an aborted transaction restarts it like any other victim (lines 429–437).

6. The benchmark: a pool, a serial baseline and real values

// tests/benchmark.cpp:181-253 (worker, abridged)
while ((idx = nextTxn.fetch_add(1)) < c.txns) {                 // pull the next transaction
    int txnId = -1, priority = 1, attempt = 0;
    while (true) {
        txnId = cm.beginTransaction("", txnId, priority);         // reuse the ID on retry
        for (op : workload[idx]) {
            if (!cm.acquireLock(txnId, op.item, op.write ? EXCLUSIVE : SHARED, true)) { failed = true; break; }
            local.push_back({seq.fetch_add(1), idx, op.write ? 'W' : 'R', op.item});   // lock held
            sleep_for(microseconds(c.workUs));                     // simulated I/O, lock still held
            read values[op.item] (or this txn's own earlier write); if write: buffer value + 1
        }
        if (!failed && cm.commitTransaction(txnId, install)) { commits++; break; }  // install: store buffered writes
        if (state != ABORTED) cm.abortTransaction(txnId);
        aborts++;  attempt++;  priority++;
        sleep_for(min(backoffBase << min(attempt, 20), backoffCap) * jitter(70..129) / 100);
    }
}
  • A fixed workload. generateWorkload draws every transaction's operations once, from std::mt19937 with seed 42: each operation picks an item uniformly from 1..items and is a write with probability --write-ratio. Every thread count runs the identical list of transactions.
  • A pool of T workers. Each worker pulls the next transaction index atomically. With T = 1, the transactions run one after another, which is the serial baseline: same binary, engine, workload and machine.
  • Work while holding locks. --work-us 1000 sleeps 1 ms after each lock is granted, standing in for disk or network I/O. A thread asleep here holds its locks but uses no CPU, which is the situation where extra threads can pay off.
  • Values and deferred writes. Each item holds an integer. A write stores (the latest value this transaction saw) + 1 in a private buffer. The buffer is installed through the beforeRelease hook, after the commit point but while every lock is still held (Part 1, section 6). An aborted attempt's buffer is simply thrown away.
  • Timing. The clock starts when a latch releases all workers (threads already exist) and stops when the last one joins. The checks run after the clock stops.
  • Reporting. Throughput = commits ÷ seconds per run, with 5 runs per thread count. The printed figure is the median. Speedup = median at T ÷ median at the first thread count listed (T = 1).
\[ b_k = \min\big(1000 \cdot 2^{k},\ 100{,}000\big) \cdot \frac{j}{100}\ \mu\text{s}, \qquad j \in \{70, \ldots, 129\},\ k = 1, 2, \ldots \]

\(k\) is the retry number (attempt after its increment). Base 1,000 µs and cap 100,000 µs are the defaults (tests/benchmark.cpp:57-58). \(j\) is drawn uniformly per retry, and the division is integer division in microseconds.

7. The two correctness checks

// tests/benchmark.cpp:123-161 (abridged): transactionsInCycles
for each item: sort its committed R/W events by seq
    for each pair (a before b) from different txns where a or b is a write:
        add edge a.txn -> b.txn (once)
Kahn's algorithm: repeatedly remove a transaction with no incoming edges
return numTxns - removed          // 0 means acyclic: conflict-serializable
// 274-281: lost updates
for each item: final value must equal the number of committed W events on it

Check 1, conflict-serializability. Every committed read and write gets a sequence number taken right after its lock is granted, while that lock is still held. Two conflicting operations can't both hold their locks at once, so the order of their sequence numbers is the order in which they really happened. Those pairs give page 1, section 7's precedence graph. Kahn's algorithm builds a serial order by repeatedly removing a transaction that nothing points to. If transactions are left over, the graph has a cycle. The benchmark reports how many were left: every cycle member, plus every transaction that must come after one.

Check 2, lost updates. Since every write is "value + 1", a correct run must end with each item's value equal to the number of committed writes to it. A transaction that writes an item twice increments it twice, and counts twice.

Worked example · both checks on a broken history

Suppose item 5 starts at 0, and the committed events are: T0 R(5) seq 1, T1 W(5) seq 2, T1 C seq 3, T0 W(5) seq 4, T0 C seq 5. Pairs on item 5: (T0 R, T1 W) gives T0→T1, and (T1 W, T0 W) gives T1→T0. Neither transaction has zero in-degree, so Kahn removes nothing and the result is 2: not serializable. Values: T1 read nothing before writing, so it saw 0 and installed 1. T0 read 0 at seq 1 and also installs 1. The final value is 1, but there were 2 committed writes, so that's 1 lost-update item. Correct 2PL makes this history impossible, because T1's X on item 5 would have waited for T0's S.

Be careful · what the checks can and can't show

Both checks look only at committed attempts. Check 1 tests conflict-serializability, which is the textbook sufficient condition and exactly what 2PL promises. Passing both checks in a run shows that run was serializable. It doesn't prove the engine can never produce a bad schedule: the race in Part 3, section 6 passed at 64 threads and failed at 1,000. The lost-update check is weaker than check 1. In the 1,000-thread failures it still passed while check 1 failed.

\[ P(\text{two transactions share an item}) \approx 1 - \Big(1 - \frac{4}{n}\Big)^{4} \]

\(n\) is the number of items and each transaction touches 4. The approximation treats one transaction's 4 items as distinct and the other's 4 draws as independent. Sharing an item is an upper bound on conflicting, because two reads of the same item don't conflict.

Worked example · 1,000 items vs 20 items

\(n = 1{,}000\): \(1 - 0.996^4 = 1 - 0.9841 = 0.0159\), about 1.6%. \(n = 20\): \(1 - 0.8^4 = 1 - 0.4096 = 0.5904\), about 59%. With 64 transactions running at once, each one overlaps about \(63 \times 0.0159 \approx 1.0\) others in config B, but \(63 \times 0.5904 \approx 37.2\) others in config C. That's the difference between near-linear scaling and thrashing (page 4, section 10).
