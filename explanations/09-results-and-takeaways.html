That test is necessary but weak. It shows that detection fired, not that isolation held or that concurrency paid off. This page adds those two checks.

1. How every number here was produced

Measurement conditions · read before quoting anything
  • Where: the audit machine. Apple M-series, 8 logical cores, macOS (Darwin 25.6), Apple clang 17, -std=c++23, -O0 (matching the makefile, which passes no optimization flag) unless marked -O2.
  • What code: the repo, with only the ConcurrencyManager member order fixed. The unmodified repo crashes at startup on macOS (Part 1, section 7).
  • Serial baseline: the same harness and engine, except each transaction thread is joined immediately after it starts (barrier size 1), so transactions run one at a time. The detector thread, logging and RAG file writes are unchanged.
  • Runs: two per configuration, one at -O2. The repo contains no metrics output. transaction_metrics.txt is git-ignored and was never committed, so none of these numbers existed before the audit.

3. Concurrent vs serial throughput

\[ \frac{\text{serial}}{\text{concurrent}}:\quad \frac{1802.35}{107.47} = 16.77 \quad \frac{1852.83}{96.00} = 19.30 \quad \frac{1967.67}{29.22} = 67.34 \quad \frac{1975.79}{27.12} = 72.85 \quad \frac{2305.79}{84.96} = 27.14\ (\text{-O2}) \]

Pairs are run #1 with run #1 and run #2 with run #2. Concurrent throughput is 5.2–6.0% of serial on test.txt and 1.4–1.5% on dead_test.txt.

Why. A "transaction" here does nothing except lock calls and logging, so there's no independent work for parallel threads to share out. Concurrency adds only costs: lock waits, 100 ms detection delay, thousands of aborts, and backoff sleeps of seconds per transaction (Part 4, section 4). Likely further contributors, none measured separately: tail and phantom aborts (Part 3), one global latch with process-wide notify_all (Part 2, sections 1 and 5), and RAG file writes inside the critical path (Part 2, section 7). That's data-contention thrashing (page 4, section 10) in its purest form.

Be careful · what a "speedup over single-threaded" would require

No single-threaded baseline exists in the repo, and on both of its workloads the audit's baseline is far faster. A multi-threaded speedup could only appear on a workload where each operation spends real time outside the lock manager (simulated I/O, think time) and conflicts are rare, and nothing like that was built or measured.

4. Commit rate

In all 5 concurrent 1,000-transaction runs, all 1,000 transactions committed eventually: 0 rows without a commit. That's \(1000/1000 = 100\%\) eventual commit. It came from retrying, not from avoiding aborts. The aborts were 2,843–3,075 (test.txt) and 6,701–6,731 (dead_test.txt), the harness's own success rate was 12.9–26.0%, and on dead_test.txt no transaction committed with fewer than 5 aborts (Part 4, section 6). The code also contains an unobserved path for finishing uncommitted (Part 4, section 7).

5. Isolation

Result · log replay (Part 2, section 6)

Incompatible locks held together: 0 in every log. Committed upgraders that another transaction's X lock overtook in the upgrade gap: 4 per test.txt run (2 runs), each giving a precedence-graph cycle (one traced by hand). dead_test.txt: 0, because it has no upgrades.

So the lock table enforces compatibility, but the engine doesn't guarantee serializability, and the counterexamples come from the project's own random workload. Separately, the unlatched transaction registry and state field are data races (Part 1, section 3), which are undefined behaviour even when a run finishes cleanly.

7. How much noise?

\[ \text{one transaction} = \frac{1}{1000} = 0.1 \text{ percentage points of commit rate} \]

This is the resolution of any rate over 1,000 transactions.

Worked example · run 1 vs run 2 (relative change)

test.txt throughput: \((96.00 - 107.47)/107.47 = -10.7\%\). Restarts: \((2953 - 2843)/2843 = +3.9\%\). dead_test.txt throughput: \((27.12 - 29.22)/29.22 = -7.2\%\). Restarts: \((6731 - 6701)/6701 = +0.45\%\). Serial throughput moved \(+2.8\%\) (\(1852.83/1802.35\)) and \(+0.4\%\) (\(1975.79/1967.67\)).

So concurrent throughput varies about ±10% between identical runs. A 16–73× gap is real. The -O2 run's 84.96 txn/s is 11.5% below run 2's 96.00, which is roughly one noise-width, so it doesn't show a difference.

8. What the evidence supports, and what it doesn't

Supported

  • A C++ (built as C++23) lock manager with shared/exclusive locks, upgrades and condition-variable waiting, driven by 1,000 concurrent threads per test file (Part 2, Part 4, section 3).
  • Locks held until commit/abort on every measured workload, i.e. strict/rigorous behaviour, except during upgrade waits (Part 1, section 6).
  • Background wait-for-graph deadlock detection with DFS, priority-based victim abort, restart with priority +1 and exponential backoff with jitter. Every run finished, and all 1,000 transactions committed eventually (Part 3, section 8).
  • Instrumentation: per-transaction restarts and latency, RAG trace logs, and two workload generators.

Not supported, or contradicted

  • ACID compliance: no data, undo or log. Isolation only (Part 1, section 8).
  • Guaranteed serializability: non-serializable committed schedules found (section 5).
  • Any throughput speedup over single-threaded: the same-harness serial run was 16.8–72.9× faster (section 3).
  • A high commit rate without qualification: 100% eventual, 12.9–26.0% by the harness's own metric (section 4).
  • Priority scheduling, or proven starvation prevention: priorities pick victims only, grants ignore them, and starvation wasn't measured (Part 3, section 6).
  • Eliminating deadlocks: they were detected and broken thousands of times, not prevented.

9. What would make it correct, and the comparison clean

  1. Fix the member order in ConcurrencyManager (declare logger, rag, then lockManager) and build with -Wall -Werror. Removes UB at startup.
  2. Keep the S lock during an upgrade wait. Restores 2PL, and with it serializability (Part 2, section 6).
  3. Latch or eliminate the static registry. Give Transaction an std::atomic state, look up through a mutex-protected map owned by the manager, and hold shared_ptrs. Removes data races.
  4. Choose victims from the cycle only (Part 3, section 4). Fewer aborts.
  5. Return true for pre-granted waits (Part 2, section 4). Fixes the metrics and locksHeld.
  6. Add a serializability test: replay the grant log into a precedence graph and assert that it's acyclic, as the audit did by hand.
  7. Take I/O out of the critical path (RAG snapshots off by default, buffered logging), scan the lock table instead of IDs 0–9,999, and use per-resource condition variables with a FIFO queue.
  8. Benchmark honestly: a workload with simulated per-operation work, 1/2/4/8/16/… threads, a serial baseline in the same binary, and ≥ 5 runs per point with the spread reported.
