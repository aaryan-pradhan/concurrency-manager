Explanations

Locks, Deadlocks and 1,000 Threads

A from-scratch walkthrough of the C++ Two-Phase Locking concurrency manager: from what a schedule is, to the exact line where an upgrade gives up its lock. Read in order. Each page uses only ideas the pages before it have already built.

docs/README.md · quick orientation
"This project simulates the part of a database engine that lets many transactions run at the same time without corrupting each other's data. It does this by making every transaction acquire a lock before touching a piece of data (the Two-Phase Locking protocol), and it runs a background thread that watches for deadlocks — situations where transactions are stuck waiting for each other in a circle — and kills off the least important transaction in the circle to break it."

There's no assignment brief in the repository, so each page is anchored to the project's own docs/ pages and header comments, and every statement is checked against the .cpp code. Pages 1–4 build the theory that paragraph assumes. Parts 1–4 walk through the code in the order a lock request flows through it. Where the code, docs, README and measured behaviour disagree, the page says so.

Before you start · how the numbers were obtained

The repository contains no benchmark output. Every run on these pages was made during an audit on macOS / Apple clang, using a scratch copy with one startup bug fixed (Part 1, section 7). The repo itself wasn't modified. The results page lists the full conditions.

  1. Prerequisite 1Transactions, schedules and serializability
    Operation notation, ACID and which letter this project covers, anomalies, conflicts, the precedence-graph test, and recoverable / cascadeless / strict schedules.
  2. Prerequisite 2Threads, mutexes and condition variables
    Data races as undefined behaviour, latches vs locks, recursive mutexes, condition variables, the thundering herd, TOCTOU, barriers, and member-initialization order.
  3. Prerequisite 3Locks and two-phase locking
    S/X compatibility, lock tables and barging, correct upgrades, the lock-point proof that 2PL is serializable, and basic vs strict vs rigorous.
  4. Prerequisite 4Deadlocks, wait-for graphs and recovery
    Coffman conditions, wait-die and timeouts, RAG vs WFG, DFS cycle detection and tails, victim selection, detection delay, aging, backoff with jitter, and thrashing.
  5. Part 1Transaction and ConcurrencyManager
    The component map, the state machine, the unlatched static registry, restart under the same ID, which 2PL variant runs, and the startup crash.
  6. Part 2LockManager
    Compatibility and barging, waiting and the "success reported as failure" bug, release pre-grants, and the upgrade gap with log-replay evidence of non-serializable commits.
  7. Part 3DeadlockDetector
    The 100 ms thread, the 10,000-ID scan, DFS, a unit test showing victims chosen outside the cycle, and where aging really lives.
  8. Part 4Harness, workloads and metrics
    The two 1,000-transaction workloads, the restart/backoff formula with a worked table, exact metric definitions, and restart distributions.
  9. Wrap-upAll results, and what they support
    Every run with its conditions, concurrent vs serial throughput, commit rate, isolation, fair comparisons, noise, conclusions, and a fix list.
