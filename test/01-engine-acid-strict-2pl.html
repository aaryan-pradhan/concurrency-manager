The story

E1
Prerequisites
  • Transaction: a group of reads and writes that must behave as one unit. Either all of it takes effect (commit) or none of it does (abort).
  • Concurrency control: the part of a database that decides how transactions running at the same time may interleave their operations without corrupting each other's data.
  • Lock: permission a transaction must hold before touching an item. A shared (S) lock is for reading, and many transactions can hold one on the same item. An exclusive (X) lock is for writing, and only one transaction can hold it.
  • Deadlock: two or more transactions each waiting for a lock another one holds, in a circle, so none can ever proceed.

Walk me through this project.

TestsCan you tell a structured two-minute story: problem, design, how you tested it, results, lessons?

Answer

In one line: I built the concurrency-control layer of a database in C++: a lock manager that implements two-phase locking, a background thread that detects and breaks deadlocks, and harnesses that run transactions on many threads. Later I audited it, found real correctness bugs, fixed them, and added a benchmark that checks every run for serializability.

The problem. When many transactions run at once, their reads and writes interleave, and some interleavings corrupt data. The classic case is a lost update, where two transactions read the same value and both write back a result based on it. The job is to allow only interleavings that are equivalent to running the transactions one at a time, while still getting the throughput benefit of running them together.

The design has four parts.

  • A ConcurrencyManager facade that begins, commits and aborts transactions and enforces the two-phase rule: no new locks after the first release.
  • A LockManager with shared and exclusive locks, S→X upgrades, a lock table guarded by a mutex, and condition variables for waiting.
  • A DeadlockDetector thread that periodically snapshots who is waiting for whom, runs a depth-first search for cycles, and aborts the lowest-priority transaction in each cycle.
  • Harnesses that run transactions on threads and restart aborted ones with exponential backoff.

Testing, in two stages. The original version ran text schedule files: one with 1,000 random transactions, and one with 1,000 transactions deliberately built to deadlock. Each transaction ran on its own thread, so 1,000 threads started at once. Every run finished, but "it finished" isn't evidence of correctness. So I later audited it by replaying the lock logs, and found four real problems:

  • A waiting S→X upgrade gave up its shared lock, which let about 4 of 1,000 committed transactions per run form non-serializable schedules.
  • The deadlock detector could abort a transaction that wasn't part of the cycle.
  • There were data races in shared structures.
  • The program crashed at startup on macOS because of C++ member construction order.

I fixed all four, added 16 regression checks, and wrote a benchmark that runs a fixed workload at 1, 2, 4, … threads with the 1-thread run as the baseline. It checks every run with a precedence-graph test and a lost-update test.

Results. With 1 ms of simulated I/O per operation and rare conflicts, throughput scaled 7.97× at 8 threads and 53.74× at 64 threads, and every run was serializable. With no I/O, adding threads made it slower: 0.24× at 32 threads, because one global mutex serializes everything. Under heavy contention it peaked at 2.83× with 4 threads and collapsed to 0.25× at 64. At 1,000 threads I found one remaining race that broke serializability in 2 of 5 runs, traced it to a lock release landing on a restarted transaction, and showed that a small fix removed it in a 20-run reproduction.

Two lessons. First, concurrency correctness needs an explicit check, like a precedence graph over the real history. Runs that finish can still be wrong. Second, extra threads only help when transactions spend their time waiting on something other than each other. The same engine went from 54× faster to 4× slower depending only on the workload.

Be careful

Timeline. The course project ran Mar–Jun 2025. The audit, the fixes, the benchmark and every speedup number above come from later work, committed in September 2026. If you quote those numbers, say they came from a later rework, not the original submission. Also, don't open with "ACID-compliant" or a single speedup figure. Both get picked apart (E5, T3).

Likely follow-up

"What would you do next?" Merge the fix for the 1,000-thread race, replace the single global lock-table mutex with striped per-resource latches and wait queues, and preserve each transaction's original timestamp across restarts so victim selection can guarantee progress.

E2
Prerequisites

A schedule is the order in which the operations of several transactions actually execute. A serial schedule runs one whole transaction, then the next. Throughput is committed transactions per second. Three classic anomalies appear when interleaving is uncontrolled:

  • Lost update: T1 and T2 both read x = 10. T1 writes 11, then T2 writes 11, so one increment disappears.
  • Dirty read: T2 reads a value T1 wrote but hasn't committed. If T1 then aborts, T2 used data that never existed.
  • Unrepeatable read: T1 reads x twice and gets different values, because T2 wrote x in between.

Why do you need a concurrency manager at all? Why not just run transactions one at a time?

TestsDo you understand the correctness-versus-throughput trade-off that concurrency control exists to resolve?

Answer

Serial execution is always correct, but it wastes time whenever a transaction waits on something slow, like disk, network or a user. During that wait the CPU is idle, but no other transaction may start. Running transactions concurrently fills those gaps, but uncontrolled interleaving produces lost updates, dirty reads and unrepeatable reads.

A concurrency manager gets both properties. It lets transactions overlap, but only in ways equivalent to some serial order. That property is called serializability, and two-phase locking is one way to enforce it.

My numbers show both sides of the trade-off. In the benchmark with 1 ms of simulated I/O per operation, the serial baseline did 191 transactions per second, and 64 concurrent threads did 10,273 per second, 53.74× more, with every run still serializable. But when transactions had no I/O at all, the serial run was fastest: 32 threads ran at 0.24× of one thread. With nothing to wait on, concurrency only adds coordination cost. So "why not serial?" has a real answer only when transactions spend time waiting.

Likely follow-up

"So when would you actually run serially?" When transactions are short and CPU-bound, with all data in memory. Some in-memory databases do exactly this: they partition data and run each partition's transactions serially on one core. That avoids locking overhead entirely, at the cost of making cross-partition transactions expensive.

E3
Prerequisites
  • Facade: one class that gives callers a simple interface and delegates to the components that do the work.
  • Mutex: a lock between threads (not transactions) that lets only one thread at a time run a critical section of code.
  • Condition variable: lets a thread sleep until another thread signals that shared state changed. wait releases the mutex while sleeping and re-acquires it on waking.
  • Background thread: a thread that runs a loop independently of the request path, here waking every few milliseconds.

Draw the architecture. What happens, step by step, when a transaction asks for a lock?

TestsDo you know your own system's components and the exact request path, including where it blocks?

Answer 
worker thread
  └─ ConcurrencyManager::acquireLock(txn, item, S|X)
       ├─ under CM mutex: find txn, require state == GROWING   (2PL: no locks after a release)
       └─ LockManager::acquireLock   (under the lock-table mutex)
            ├─ txn ABORTED?              → false
            ├─ already holds S/X enough? → true
            ├─ holds S, wants X          → upgrade: convert in place, or queue X keeping S
            ├─ compatible with granted?  → grant, true
            └─ otherwise                 → queue request, UNLOCK, sleep on condition variable

release / commit / abort
  └─ LockManager::releaseAllLocks → remove entries → grant compatible waiters → notify_all

DeadlockDetector thread (every 10–100 ms)
  └─ snapshot waiter→holder edges under the lock-table mutex → DFS for cycles
       → victim = lowest priority in the cycle → CAS state to ABORTED → releaseAllLocks(victim)

Transaction registry (static map + its own mutex, shared_ptr entries): state and priority by ID

The facade checks the 2PL phase under its own mutex, then calls the lock manager without holding that mutex. Otherwise one blocked transaction would stop every other transaction from beginning or committing.

The lock manager does everything under one mutex. If the request can't be granted, it appends a pending entry to that item's queue, unlocks, and sleeps on a condition variable. Sleeping while holding the mutex would freeze the whole engine.

A waiter wakes for one of three reasons: it was aborted as a deadlock victim, a releasing thread already granted its request, or the request became compatible. Releases hand locks to compatible waiters directly, pending upgrades first, then wake everyone.

The detector runs on its own thread. It takes one consistent snapshot of the wait edges, finds cycles, and aborts one victim per cycle. The victim's thread notices through its wake predicate and restarts with a higher priority.

Likely follow-up

"What's the bottleneck in that picture?" The single lock-table mutex plus one condition variable shared by all waiters. Every acquire, release and detector snapshot serializes on that mutex, and every release wakes every waiter. That's why the CPU-only benchmark got slower with more threads (see S21 and T5).

ACID

E4
Prerequisites
  • Commit: the point after which a transaction's effects are official. Abort (rollback): undoing everything the transaction did.
  • Crash: the process or machine stops without warning, and everything in memory is lost.
  • Invariant (integrity constraint): a rule the data must always satisfy, e.g. "account balances are never negative", or "debits equal credits".
  • Log: an append-only file of change records that recovery can replay after a crash.

What does ACID stand for? Define each property precisely, and say how a real database implements it.

TestsTextbook precision, and whether you know the mechanism behind each letter rather than the slogan.

Answer
LetterPrecise meaningUsual mechanism
AtomicityAll of a transaction's changes take effect, or none do, including when it aborts or the system crashes mid-way.Undo log (before-images) to roll back, or deferred updates applied only at commit.
ConsistencyA transaction that starts from a state satisfying every integrity constraint ends in a state that satisfies them too.Declared constraints (keys, foreign keys, checks) plus correct application logic. The database only guarantees the other three letters don't break it.

And isolation comes in levels. Read committed, repeatable read, snapshot isolation and serializable each allow different anomalies, so "isolated" without a level is vague.

E5
Prerequisites
  • In-memory vs persistent: data only in RAM disappears on a crash. Durability needs a record on disk.
  • Deferred update: a transaction's writes go into a private buffer and are applied to shared data only at commit. Aborting just discards the buffer, so no undo is needed.
  • Where this project keeps data: the engine itself stores no values. A "read" is just an S lock and a "write" an X lock. The benchmark harness keeps one integer per item.

Your CV says "ACID-compliant". Which of the four properties does your engine actually provide, and how?

TestsWhether you overclaim. This is one of the first things a database interviewer probes.

Answer

Honestly: isolation is the property the engine is built for. Atomicity exists only in my benchmark harness, and there's no durability. "ACID-compliant" overstates it.

  • Isolation — yes, through strict two-phase locking. Every workload I measured holds all locks until commit or abort. The benchmark checks every run with a precedence-graph test, and all 100 recorded runs at up to 64 threads passed. The caveat: at 1,000 threads a race between the deadlock detector and a restarted transaction broke serializability in 2 of 5 runs. I found the cause and tested a fix, but it isn't merged.
  • Atomicity — only in the harness. The engine has no data and no undo log: aborting a transaction releases its locks and marks it aborted. My benchmark harness adds integer values and uses deferred updates. Writes go to a private buffer, and a commit hook installs them after the commit point, while all locks are still held. An aborted attempt's buffer is thrown away, so shared data sees all of a transaction's writes or none of them. But that's in memory only.
  • Consistency — not enforced. There are no constraints. The benchmark does verify one invariant after every run: each item's final value equals the number of committed writes to it.
  • Durability — none. Nothing is written to disk that recovery could replay. The .log files are human-readable traces. A crash loses everything, and the project's own docs say so: "This project does not deal with durability at all — everything is in memory."
Be careful

Don't defend "ACID-compliant". A single follow-up ("where's your log?") ends that line of defence. Say instead: "a transaction engine that provides serializable isolation with strict two-phase locking, with all-or-nothing in-memory writes in the benchmark; durability was out of scope." Offering the limitation yourself reads as rigor, not weakness.

Likely follow-up

"Then what would it take to be ACID?" That's E6: a write-ahead log with commit records flushed before acknowledging, recovery that redoes committed work and undoes the rest, and data stored somewhere persistent.

E6
Prerequisites
  • Write-ahead logging (WAL): before a change reaches the data files, a log record describing it is appended to a log. On commit, a commit record is appended and flushed to disk.
  • fsync: the call that forces buffered file data onto stable storage. It takes milliseconds on many devices, which makes it the expensive part.
  • Redo / undo: redo re-applies a committed change that may not have reached the data files. Undo reverses an uncommitted change that did.
  • Checkpoint: a point where the data files are known to reflect the log up to some position, so recovery can start there.
  • Group commit: batching several transactions' commit records into one fsync.

How would you add durability to your engine?

TestsRecovery fundamentals, and how logging interacts with locking and throughput.

Answer

I'd add a write-ahead log, and make commit wait for the log to be flushed.

  1. Persistent data: items would live in pages on disk, cached in a buffer pool, instead of only in the harness's memory.
  2. Log before data: each write appends a record (transaction ID, item, old value, new value) before the page changes. A page may be flushed only after the log records describing its changes are on disk. That's the "write-ahead" rule.
  3. Commit: append a commit record, fsync the log, and only then report success and release the locks. Releasing locks before the commit record is durable would let another transaction read data that could vanish in a crash.
  4. Recovery: start from the last checkpoint, redo every logged change, then undo the changes of transactions with no commit record. That's the core idea of ARIES, the recovery algorithm most textbook systems follow.
  5. Performance: one fsync per commit caps throughput at the device's flush rate, so batch commits (group commit): one flush can make many commit records durable.

This would change my performance numbers. Commit would include a flush of a millisecond or more while locks are held. That's close to the regime my 1 ms simulated-I/O benchmark models, where concurrency paid off because transactions spent most of their time waiting.

Likely follow-up

"Why not just write the data pages at commit?" Random writes to many pages are slower than one sequential log append, and a crash in the middle of writing several pages would leave them inconsistent. With a log, the commit record is a single atomic point of truth.

E7
Prerequisites
  • In-place update with undo: write straight to shared data, keep the old value, and restore it on abort.
  • Deferred update: write to a private buffer, and apply it only after committing.
  • Cascading abort: if T2 read T1's uncommitted write and T1 aborts, T2 must abort too, and so on down the chain.
  • Commit point: the single atomic step after which a transaction counts as committed. Here it's a compare-and-swap of its state to COMMITTED.

In your benchmark, what happens to a transaction's writes if it's aborted halfway through?

TestsWhether you understand how atomicity and strictness interact in your own harness.

Answer

Nothing reaches shared data. Writes are buffered privately and installed only after the commit point, while the transaction still holds every lock.

Each write computes (the latest value this transaction has seen) + 1 and stores it in a per-attempt map. Later reads of the same item by the same transaction use that map, so a transaction sees its own writes. At the end, the worker calls commitTransaction(txnId, install), which runs in a fixed order:

  1. CAS the transaction's state to COMMITTED. If the deadlock detector already set it to ABORTED, the CAS fails and nothing is installed.
  2. Run install: store the buffered values into the shared array. All X locks are still held, so no one can read these items mid-install.
  3. Release all locks.

If the transaction is aborted, the buffer goes out of scope and the worker retries from scratch with the same ID and priority + 1. Because nobody ever sees uncommitted values, there are no dirty reads and no cascading aborts. And once the CAS succeeds, the detector's abort() returns false, so a transaction can never be aborted halfway through installing.

Likely follow-up

"Deferred vs in-place: trade-offs?" Deferred makes abort free and needs no undo, but reads must check the private buffer first, and large transactions need memory for their buffers. In-place makes commit cheap and reads simple, but needs an undo log and exclusive locks held to the end, or other transactions could read dirty values.

Strict 2PL

E8
Prerequisites
  • Conflicting operations: two operations from different transactions on the same item, where at least one is a write. Their relative order changes the outcome.
  • Growing phase: the period in which a transaction may acquire locks. Shrinking phase: the period after its first release, in which it may only release.
  • Lock point: the moment a transaction acquires its last lock, the end of its growing phase.

What is two-phase locking, and why does it need two phases? Isn't locking each operation enough?

TestsThe core protocol, and the classic counterexample showing that per-operation locking is not enough.

Answer

Two-phase locking (2PL) says a transaction must acquire every lock it needs before it releases any. Once it releases one lock, it can never acquire another.

Why per-operation locking isn't enough. Suppose T1 does lock-S(x) read(x) unlock(x), and only later lock-X(x) write(x). Between the unlock and the relock, T2 can lock x, write it, and commit. T1 then writes a value computed from its stale read. That's a lost update, and in precedence-graph terms T1→T2 (T1 read before T2 wrote) and T2→T1 (T2 wrote before T1 wrote) form a cycle. Each individual operation was locked, but the transaction as a whole wasn't isolated.

Why two phases fix it. With 2PL, every transaction has a lock point. If T1's operation on some item comes before T2's conflicting operation, T1 must have released that item before T2 acquired it, so T1's lock point comes before T2's. Every precedence edge therefore points from an earlier lock point to a later one, so there can't be a cycle. The serial order is simply "sorted by lock point". S3 has the full proof.

In my code: a transaction starts GROWING, its first release switches it to SHRINKING, and ConcurrencyManager::acquireLock refuses any transaction that isn't GROWING.

A real bug: my original upgrade code broke exactly this rule. A transaction holding S that wanted X dropped its S lock while waiting, which is a release followed by an acquisition, and the audit found about 4 committed non-serializable transactions per 1,000-transaction run because of it.

E9
Prerequisites
  • Recoverable schedule: a transaction commits only after every transaction whose data it read has committed.
  • Cascadeless schedule: transactions read only committed data, so one abort never forces another.
  • Strict schedule: no transaction reads or overwrites an item until the last transaction that wrote it has committed or aborted. That's what makes simple undo (restoring before-images) correct.

What's the difference between basic, strict and rigorous 2PL? Which one did you implement?

TestsPrecise definitions, whether you know that naming varies between textbooks, and whether you can say what your code does.

Answer
VariantRule on top of 2PLWhat it adds
Basicnone: release any lock once growing endsconflict-serializable, but cascading aborts are possible
Stricthold every X lock until commit or abortstrict schedules: no dirty reads or overwrites, so no cascading aborts
Rigoroushold every lock, S and X, until commit or abortalso serializable in commit order

What mine does. The API has a releaseLock call, so on its own the API only guarantees basic 2PL. But every workload I ran releases all locks at once, at commit or abort. The text schedule files contain no early releases, and the benchmark never calls releaseLock. So in every measured run it's rigorous 2PL, which implies strict. The project's docs call it "strict 2PL", as several textbooks name the all-locks-held version.

Why it matters. Under basic 2PL, a transaction could release an X lock early. Another transaction could then read the uncommitted value, and if the first one aborted, the second would have to abort as well. Holding locks to the end removes that possibility, and it also makes the upgrade question easier: the lock you hold can't disappear.

Be careful

Naming varies. Silberschatz calls "everything held to the end" rigorous, while other books call it strict. Say what you mean in words: "every lock, shared and exclusive, is held until commit or abort." Also, before the fix, a waiting upgrade dropped its S lock mid-transaction, so strictly speaking the original version wasn't even 2PL for those transactions. If asked about the original, say so.

E10
Prerequisites
  • Compare-and-swap (CAS): an atomic "if the value is still A, set it to B" operation. Two threads racing to CAS the same value can't both succeed.
  • Commit point: the single step after which a transaction counts as committed.
  • Callback (hook): a function a caller passes in, for the callee to run at a specific moment.

Show me where in the code locks are held until commit. Walk me through commitTransaction, and explain why the steps are in that order.

TestsCode-level knowledge and reasoning about ordering between commit, making changes visible, and releasing locks.

Answer 
bool ConcurrencyManager::commitTransaction(int txnId, const std::function<void()>& beforeRelease) {
    auto txn = lookup under mutex;
    bool committed = txn->commit();          // 1. CAS GROWING/SHRINKING -> COMMITTED
    if (committed) {
        if (beforeRelease) beforeRelease();  // 2. install buffered writes, all locks still held
        lockManager.releaseAllLocks(txnId);  // 3. release everything at once
        unregister and erase;                // 4. forget the transaction
    }
    return committed;
}

Step 1 comes first because the deadlock detector might choose this transaction as a victim at the same moment. Both commit and abort are CAS loops on one atomic state, so exactly one wins. If commit wins, the detector's abort returns false and it moves on. If abort wins, commit returns false and the worker retries. So no transaction ever installs writes and then gets aborted.

Step 2 comes before step 3 because while the X locks are held, no other transaction can read the items. By the time anyone can see them, they already hold the new values. If I released first and installed second, another transaction could lock the item in between, read the old value, and later write back something based on it: a lost update.

Step 3 releases all at once. There are no early releases anywhere on the measured path. That's what makes it rigorous 2PL in practice. abortTransaction follows the same shape without the hook: CAS to ABORTED, release all locks, unregister.

E11
Prerequisites
  • MVCC (multi-version concurrency control): writers create new versions instead of overwriting, so readers see a consistent snapshot without taking locks.
  • Snapshot isolation: each transaction reads from a snapshot taken at its start, and a write fails if another committed transaction wrote the same item first. It allows an anomaly called write skew: two transactions each read both items and each write a different one, together breaking a constraint neither broke alone.
  • OCC (optimistic concurrency control): run without locks, then validate at commit that nothing you read was changed. If something was, abort.

What are the downsides of strict 2PL? When would you choose something else?

TestsBreadth: can you place 2PL among the alternatives and pick one for a workload?

Answer

Strict 2PL is pessimistic. It holds locks for the whole transaction, so readers block writers, writers block readers, and deadlocks are possible. The cost shows up exactly where contention is high. In my high-contention benchmark (20 items, 30% writes, 1 ms per operation), throughput peaked at 2.83× with 4 threads and fell to 0.25× at 64 threads, with 3,844 deadlock aborts for 1,000 commits.

Alternatives, and when I'd use each:

  • MVCC with snapshot isolation for read-heavy workloads. Readers never block and are never blocked. The catch is write skew, so for true serializability you need serializable snapshot isolation, which detects dangerous read/write patterns and aborts one transaction.
  • OCC when conflicts are rare, as in my low-contention benchmark where two transactions shared an item about 1.6% of the time. It skips lock management entirely, but wastes whole transactions when validation fails, so it thrashes under high contention.
  • Timestamp ordering, or 2PL with wait-die / wound-wait when you want no deadlock detection at all. Transactions are ordered by timestamp, and conflicts either wait or abort by that order.
  • Deterministic or partitioned serial execution for short, in-memory, CPU-bound transactions. My CPU-only benchmark was fastest on one thread.

2PL remains a good default when you need serializability, writes are common, and transactions are short.

Graph-based deadlock detection

E12
Prerequisites
  • Prevention: make deadlock impossible, e.g. by acquiring locks in a global order, or with wait-die / wound-wait, which use timestamps to decide who waits and who aborts.
  • Timeout: abort any transaction that has waited longer than a fixed limit.
  • Detection: let deadlocks happen, find them by looking for a cycle in the "who waits for whom" graph, and abort one transaction per cycle.
  • Detection interval \(I\): how often the detector runs. A deadlock waits about \(I/2\) on average before it's noticed.

Why did you choose deadlock detection instead of prevention or lock timeouts?

TestsDesign trade-off reasoning, with costs on both sides.

Answer

Detection aborts a transaction only when a real deadlock exists. Prevention and timeouts both abort transactions that might have finished fine.

  • Global lock ordering needs every transaction to know all its items up front and lock them in sorted order. My text-schedule transactions touch items in arbitrary order, and in general a transaction discovers what it needs as it runs.
  • Wait-die and wound-wait never deadlock, but they abort based on age whenever a conflict occurs, even when no cycle exists. That causes more aborts when conflicts are frequent but cycles rare.
  • Timeouts are simple, but the limit is a guess. Too short, and slow-but-healthy transactions die. Too long, and a real deadlock stalls everyone queued behind it. The original code actually had a 5-second lock timeout. A commit on 2025-04-12 replaced it with detection.

The costs of detection. A deadlock sits for about half the detection interval before anyone acts (50 ms average in the text harness at 100 ms, 5 ms in the benchmark at 10 ms). Each pass also takes the lock-table mutex to snapshot the graph, and you need a victim-selection policy. Those costs were worth it for arbitrary transactions.

I'd add one nuance. In my benchmark every transaction's operations are known up front, so there, sorting the items and taking the needed lock type in that order would eliminate deadlocks entirely (T17).

E13
Prerequisites
  • Wait-for graph (WFG): one node per transaction, and an edge T1→T2 if T1 is waiting for a lock T2 holds. A cycle means a deadlock.
  • Depth-first search (DFS): explore as deep as possible along edges before backtracking. A node that's still on the current path and gets reached again closes a cycle. That edge is called a back edge.
  • Victim: the transaction aborted to break a cycle.

Explain how your deadlock detector works, in about a minute.

TestsA crisp summary before the deep dive (D10–D18 go deeper).

Answer
  1. A background thread wakes every I milliseconds: 100 ms in the text harness, 10 ms in the benchmark.
  2. Snapshot. Under one acquisition of the lock-table mutex, it lists every waiter→holder pair: a waiting S request points at every X holder, and a waiting X request at every other holder. Transactions already marked aborted are skipped. Because the snapshot is a single instant, any cycle in it is a real deadlock.
  3. Search. A DFS from each unvisited node, in sorted ID order, keeps the current path. On a back edge it cuts out exactly the nodes on the cycle, excluding "tail" transactions that merely wait on it.
  4. Victim. The cycle member with the lowest priority number. Ties go to the highest ID.
  5. Break it. CAS the victim's state to ABORTED, release all its locks (which grants waiting requests and wakes threads), remove it from the graph, and search again until there's no cycle left.
  6. Recovery. The victim's thread wakes, sees it was aborted, backs off, and restarts with priority + 1.

One search is \(O(V + E)\), and a pass with \(k\) victims runs \(k + 1\) searches.

A lock is a logical, transaction-level right to a data item, held possibly for the whole transaction and managed by a lock manager.

E16
Prerequisites
  • Lock upgrade: a transaction holding S on an item asks for X on the same item, typically read-then-write.
  • Lost update schedule: r1(N) w2(N) c2 w1(N) c1. T1 reads N, T2 overwrites and commits, then T1 writes based on its stale read.
  • Log replay: reconstructing the true order of events from a log written while the relevant mutex was held.

Tell me about the hardest bug you found in this project. How did you find it, fix it, and make sure it stays fixed?

TestsA debugging story told as isolate → cause → fix → prevention, with evidence.

Answer

The upgrade gap: my lock manager let committed transactions produce non-serializable schedules, even though it never granted two incompatible locks at the same time.

Symptom and suspicion. Every test run finished, and every transaction committed. But nothing actually checked isolation, so I audited it.

Isolate. The lock manager logs every grant, upgrade and release while holding its mutex, so the log order is the true order of lock-table changes. I replayed the logs with two checks:

  • Were incompatible locks ever held together? Never, in every log.
  • For each "waiting to upgrade" event, did another transaction get X on that item before the upgrader did, with the upgrader then committing? Yes: 4 cases per run of the 1,000-transaction random workload, in both runs.

Cause. I traced one case by hand. Transaction T314 read N, then asked to upgrade to X. The upgrade code erased its granted S lock and re-queued the request as a fresh X. In that gap, T525 got X on N, wrote, and committed, and so did T916. Then T314 got X and wrote based on its stale read: \(r_{314}(N) \lt w_{525}(N) \lt w_{314}(N)\), a precedence cycle. Dropping S and later taking X is a release followed by an acquisition, which violates 2PL itself.

Fix. Keep the S entry granted and add a pending X entry beside it. When a release happens, grant pending upgrades before any other waiter, and when the X is granted, remove the now-redundant S. A side effect: two readers who both try to upgrade now deadlock, which the detector already handles.

Prevention. A regression test holds S for two transactions, starts an upgrade, and asserts four things: the upgrader still holds S while waiting, no third transaction can get X in the window, the upgrade completes once the other reader leaves, and the upgrader ends with a single X entry. I also built serializability checks into the benchmark: a precedence graph over every committed operation, plus a lost-update invariant, on every run. All 100 recorded runs at up to 64 threads passed.

Likely follow-up

"Anything still broken?" Yes: a race at 1,000 threads where the detector's delayed lock release hits the restarted transaction, which reuses the same ID. That's S12, which is also a good story if they want a second one.

Review: Part 2, section 6

E17
Prerequisites
  • Member initialization order: C++ constructs a class's data members in the order they are declared, whatever order the constructor's initializer list uses.
  • Undefined behaviour (UB): code the standard gives no meaning to. It can crash, appear to work, or differ between platforms.
  • Zero-initialized globals: an object with static storage is filled with zero bytes before its constructor runs.

Your program crashed at startup on macOS, but apparently worked on the original machine. What was going on?

TestsC++ object lifetime, UB reasoning, and platform differences.

Answer

A member was constructed before the members it depended on, so it locked a mutex that didn't exist yet.

ConcurrencyManager declared LockManager lockManager before Logger logger and ResourceAllocationGraph rag. The initializer list was written as logger(...), rag(logger), lockManager(logger, rag), but C++ ignores that order, so lockManager was built first, holding references to raw memory. Its constructor immediately logged a message, which locked the logger's std::mutex before the mutex had been constructed. Clang even warns about it: field 'rag' will be initialized after field 'lockManager' [-Wreorder-ctor].

Why the platforms differed. The manager was a global, so its memory was zero-filled before construction. On macOS, a valid pthread_mutex carries a non-zero signature, so locking an all-zero one fails with EINVAL, and libc++ throws std::system_error: mutex lock failed: Invalid argument. That produced exit code 134 on every test file. On Linux with glibc, an unlocked mutex happens to be all zero bytes, so it most likely "worked" by luck. That's an inference, because I didn't test Linux. Either way, it was undefined behaviour.

Fix: reorder the declarations to logger, rag, lockManager, add a comment explaining why the order matters, and build with -Wall -Wextra, so this class of bug shows up as a warning.

E18
Prerequisites
  • Phantom: a row that appears in a repeated range query because another transaction inserted it in between. Locks on existing items can't stop it, because the new item didn't exist to be locked.
  • Multiple-granularity locking: locks on tables, pages and rows, with intention modes (IS, IX, SIX) that announce finer-grained locks further down.
  • Lock escalation: replacing many row locks with one table lock to save memory.
  • Isolation levels: read committed, repeatable read, snapshot, serializable.

What would a production database's concurrency control have that yours doesn't?

TestsSelf-awareness about scope, and breadth of database knowledge.

Answer
  • Durability and recovery: a write-ahead log, checkpoints and crash recovery. Mine has none (E6).
  • Phantom protection: predicate, range or next-key locks. Mine locks fixed item IDs only. All my workloads use a fixed item set, so phantoms never arise in my measurements, but a range query would expose it.
  • Lock granularity: table, page and row locks with intention modes, plus lock escalation. Mine has one flat level of items.
  • Isolation levels and MVCC: so readers don't block writers. Mine is serializable-only and fully pessimistic.
  • A scalable lock manager: a hash-partitioned lock table with a latch per bucket, and per-request wait queues. Mine uses one global mutex and one condition variable, so every release wakes every waiter, and the CPU-only benchmark got slower as threads were added.
  • Fairness and starvation guarantees: FIFO or age-aware grant queues, and victim policies that keep a transaction's original timestamp. Mine lets new readers barge ahead of queued writers, and aging didn't prevent one transaction from being aborted 1,980 times in a 1,000-thread run.
  • Update (U) locks to avoid the classic upgrade deadlock, and lock-wait timeouts as a safety net alongside detection.
