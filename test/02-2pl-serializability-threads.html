Serializability theory

S1
Prerequisites
  • Schedule: the actual interleaved order of all transactions' operations. Notation: \(r_1(x)\) means T1 reads x, \(w_2(x)\) means T2 writes x, and \(c_1\) means T1 commits.
  • Serial schedule: the transactions run one at a time, with no interleaving.
  • Conflicting operations: from different transactions, on the same item, with at least one write. \(r_1(x), w_2(x)\) conflict. \(r_1(x), r_2(x)\) don't.
  • Blind write: writing an item without reading it first.

What is serializability? What's the difference between conflict-serializability and view-serializability?

TestsPrecise definitions of the correctness criterion your CV names.

Answer

A schedule is serializable if its effect equals that of some serial schedule of the same transactions. It doesn't have to be the order they started in, just some serial order.

Conflict-serializable: you can turn the schedule into a serial one by repeatedly swapping adjacent operations that don't conflict. Equivalently, every pair of conflicting operations appears in the same order as in some serial schedule. It can be tested in linear time with a precedence graph (S2).

View-serializable: every transaction reads the same versions as in some serial schedule (each read sees the same writer), and the final write to each item is the same. It's a larger class. Every conflict-serializable schedule is view-serializable, but not vice versa. The extra schedules all involve blind writes. For example, \(r_1(x)\, w_2(x)\, w_1(x)\, w_3(x)\) is view-equivalent to T1, T2, T3, because T3's blind write overwrites everything, but it isn't conflict-serializable. Testing view-serializability is NP-complete, so systems don't do it.

What 2PL gives: conflict-serializability, and that's also exactly what my benchmark checks for.

S2
Prerequisites
  • Directed graph: nodes plus arrows between them. A cycle is a path that returns to where it started.
  • Topological sort: an ordering of nodes in which every arrow points forward. It exists exactly when the graph has no cycle. Kahn's algorithm finds one by repeatedly removing a node with no incoming arrows.

How do you test whether a schedule is conflict-serializable? Work through an example of each outcome.

TestsCan you apply the precedence-graph test by hand, quickly?

Answer

Build the precedence graph: one node per committed transaction, and an edge \(T_i \to T_j\) whenever an operation of \(T_i\) conflicts with a later operation of \(T_j\). The schedule is conflict-serializable exactly when the graph has no cycle, and any topological order is an equivalent serial order.

Serializable example: \(r_1(A)\; r_2(B)\; w_1(A)\; r_2(A)\; w_2(B)\; c_1\; c_2\). On A, \(w_1(A)\) precedes \(r_2(A)\), which gives \(T_1 \to T_2\). \(r_1(A)\) vs \(r_2(A)\) is two reads, so no edge. B is touched only by T2. The graph is just \(T_1 \to T_2\), so the schedule is equivalent to running T1 then T2.

Not serializable (lost update): \(r_1(N)\; w_2(N)\; c_2\; w_1(N)\; c_1\). \(r_1(N) \lt w_2(N)\) gives \(T_1 \to T_2\), and \(w_2(N) \lt w_1(N)\) gives \(T_2 \to T_1\). That's a cycle, so there's no equivalent serial order. That exact shape appeared in my engine's logs before the upgrade fix.

Cost: building the graph means comparing operations per item, and the cycle check or topological sort is \(O(V + E)\). My benchmark does exactly this after every run: it sorts each item's committed operations by sequence number, adds an edge for each conflicting pair, runs Kahn's algorithm, and reports how many transactions couldn't be placed.

S3
Prerequisites
  • Lock point \(\ell(T)\): the time T acquires its last lock. Under 2PL, every acquisition happens at or before \(\ell(T)\), and every release after it.
  • For two conflicting operations, at least one needs an X lock, so the two transactions can't hold their locks on that item at the same time. One must release before the other acquires.
  • Precedence-graph edges from S2.

Prove that two-phase locking guarantees conflict-serializability.

TestsWhether you understand why the protocol works, not just its rule. A favourite at strong database teams.

Answer

Claim: under 2PL, every edge in the precedence graph goes from an earlier lock point to a later one. So the graph has no cycle, and sorting transactions by lock point gives an equivalent serial order.

Proof. Take an edge \(T_i \to T_j\). It exists because some operation of \(T_i\) on item x comes before a conflicting operation of \(T_j\) on x. Conflicting locks can't be held at the same time, so \(T_i\) released its lock on x, at time \(u_i(x)\), before \(T_j\) acquired its lock on x, at time \(a_j(x)\). By the two-phase rule, \(T_i\) acquired everything before releasing anything, and \(T_j\)'s acquisition of x is no later than its last acquisition:

\[ \ell(T_i) \lt u_i(x) \lt a_j(x) \le \ell(T_j) \]

So every edge satisfies \(\ell(T_i) \lt \ell(T_j)\). A cycle \(T_1 \to T_2 \to \cdots \to T_k \to T_1\) would give \(\ell(T_1) \lt \ell(T_2) \lt \cdots \lt \ell(T_1)\), which is impossible. So the graph is acyclic, and the schedule is conflict-serializable. ∎

Where my bug fits in. The old upgrade released S and later acquired X on the same item, so that transaction had no single lock point, and the chain \(\ell(T_i) \lt u_i(x)\) broke. That's exactly how non-serializable schedules got through.

S4
Prerequisites
  • Deadlock (circular wait), starvation (a transaction that never gets to finish although the system makes progress), cascading abort (one abort forcing others), and phantom (a newly inserted row that a repeated range query sees).
  • The proof in S3 assumes the implementation really follows the rule.

So does 2PL give you correct concurrency for free? What can still go wrong?

TestsKnowing the protocol's limits, and connecting them to real bugs.

Answer
  • Deadlocks. 2PL itself causes them: holding locks while waiting is one of the four deadlock conditions. You need detection or prevention. My high-contention runs at 64 threads had about 3,844 deadlock aborts each.
  • Cascading aborts under basic 2PL, if X locks are released before commit. Strict 2PL removes that.
  • Phantoms. The proof is about the items that were locked. A range query can't lock rows that don't exist yet, so you need predicate or next-key locks.
  • Starvation. Nothing in 2PL says who gets a lock next. My grants let new readers barge ahead of queued writers, and one transaction in a 1,000-thread run was aborted 1,980 times.
  • Implementation bugs that break the rule. I had two. The old upgrade path released S before acquiring X (fixed). And a remaining race lets the detector's delayed release remove a restarted transaction's locks, so two transactions briefly both hold X on one item. That failed my serializability check in 2 of 5 runs at 1,000 threads (S12).
  • Throughput collapse. Locks held across slow work turn contention into waiting and thrashing.

Your lock manager

S5
Prerequisites
  • Shared (S) lock: reading. Any number of transactions may hold S on the same item. Exclusive (X) lock: writing. Only one holder, and no S holders alongside it.
  • Lock table: for each item, the list of lock requests, granted and waiting.
  • Barging: granting a new request because it's compatible with current holders, even though older requests are still queued.

Describe your lock compatibility matrix and your lock table's data structure.

TestsBasic lock-manager design, and whether you know your own grant policy.

Answer
requested ↓ / held →noneSX
Sgrantgrantwait
Xgrantwaitwait

One exception: a transaction's own S lock doesn't block its X request, which is how upgrades work.

The table is unordered_map<int, vector<LockRequest>>, keyed by resource ID. Each LockRequest is {transaction ID, S or X, granted flag}. Granted and waiting requests share one vector, in arrival order. An upgrading transaction temporarily has two entries: its granted S and a pending X. The whole table is protected by one mutex, with one condition variable for all waiters.

Compatibility checks only the granted entries. An S request is granted unless some granted entry is X. An X request is granted only if no other transaction holds anything. The queue is ignored, so a new reader can barge past a writer who has been waiting, and transaction priority plays no part in granting.

Likely follow-up

"Why ignore the queue?" It maximizes concurrency for readers and is simple, but writers can starve. The alternative is FIFO: a request waits if anything incompatible is queued ahead of it. FIFO is fairer, but it can make compatible readers wait for nothing.

S6
Prerequisites
  • cv.wait(lock, pred) is equivalent to while (!pred()) cv.wait(lock);. It atomically releases the mutex and sleeps, and on waking re-acquires the mutex and re-checks pred.
  • Spurious wakeup: a thread may wake without anyone notifying it, which is why the predicate is re-checked.
  • Lost wakeup: if a thread checked its condition, released the mutex, and only then started waiting, a notify in between would be missed. wait avoids this by making the release and the sleep atomic.

When a lock can't be granted, how exactly does the transaction wait, and what wakes it up?

TestsCorrect condition-variable usage, and what counts as a wake-up reason in a lock manager.

Answer

Under the lock-table mutex, acquireLock appends a pending request to the item's vector and adds a request edge to the resource graph. It then releases the mutex and calls waitForLock, which re-locks and does cv.wait(lock, canProceed). The predicate is true in three cases:

  1. The transaction was aborted (chosen as a deadlock victim). After waking, it removes its pending request and returns false.
  2. It has no pending request any more. A releasing thread already granted it. It confirms it holds the lock and returns true.
  3. Its pending request is now compatible. It grants the request itself and returns true.

Because wait is called with a predicate, spurious wakeups are harmless: it just re-checks and sleeps again. Checking the abort state inside the predicate is what lets the deadlock detector wake a victim that's asleep.

A bug I fixed here. Case 2 used to return false. The code searched only for an ungranted entry after waking, found none, and fell through. The lock really was held, but callers were told it wasn't. That didn't break isolation, because other transactions check the table, which was correct. It did inflate the "lock failures" metric: one pre-fix run showed 6,911 failures against 6,701 restarts. A regression test now checks that a waiter granted by releaseLock gets true.

S7
Prerequisites
  • notify_one wakes one waiter. notify_all wakes every thread waiting on that condition variable.
  • Writer starvation: a writer waits forever because readers keep overlapping.

When a lock is released, who gets it next?

TestsGrant policy and fairness, at the level of your own code.

Answer

The releasing thread grants every waiting request that has become compatible, pending upgrades first, then in arrival order, and then wakes all waiters.

releaseLock removes the entry, then runs grantWaitersInternal in a loop. Pass 1 looks for a pending X from a transaction that already holds S on the item (an upgrade) and grants it if compatible. Pass 2 grants the first compatible pending request in vector order. After each grant it re-scans, until nothing more can be granted. Then notify_all.

Why upgrades go first: the upgrader already holds S. Granting a fresh request before it could let a new writer slip in between the upgrader's read and its write.

Fairness gap: arrival order only applies among requests that are compatible right now. If T1 and T4 hold S, and the queue is [T2 wants X, T3 wants S], then when T4 releases, T2's X is still blocked by T1, and T3's S is granted, skipping T2. If readers keep overlapping, T2 starves.

Why notify_all: a single condition variable serves every resource, so the code can't target just the waiters of this item. Everyone wakes, re-checks, and most go back to sleep. That's correct but wasteful (S20).

S8
Prerequisites

A lock upgrade converts a held S lock into X, because the transaction read an item and now wants to write it. The textbook implementation keeps S granted while the X waits, and converts once the transaction is the only holder.

How do lock upgrades work in your implementation? I hear there was a bug.

TestsA subtle place where lock managers go wrong, and whether you can explain the failure precisely.

Answer

Now: if the transaction is the only holder, S is converted to X in place. Otherwise, it keeps its granted S and appends a pending X entry, then waits. When the other readers release, pass 1 of the grant loop gives it the X, and the old S entry is erased. While it waits, its S still blocks every other writer, so nobody can change the item between its read and its write.

Before the fix: the code erased the granted S entry and queued a fresh X request. During the wait the transaction held nothing on the item, so another transaction could take X, write and commit, and then the upgrader wrote based on a stale read: a lost update. That's also a release followed by an acquisition, so it wasn't even 2PL.

Evidence it happened: replaying the pre-fix lock logs of the 1,000-transaction random workload found 106 and 109 upgrade waits in two runs. In 4 cases per run, another transaction was granted X during the gap and the upgrader still committed, each case forming a precedence cycle (about 0.4% of commits).

Proof it's fixed: a regression test holds S for T101 and T102, starts T101's upgrade, and then checks four things: T101 still holds S, a third transaction can't get X in the window, the upgrade completes once T102 leaves, and T101 ends with exactly one X entry. All passed. The benchmark's precedence check also passed in all 100 recorded runs at up to 64 threads.

S9
Prerequisites

An update (U) lock is an intermediate mode for "I read this and may write it". U is compatible with S but not with another U, so only one transaction can be positioned to upgrade at a time.

Two transactions both hold a shared lock on the same item, and both ask to upgrade to exclusive. What happens in your system?

TestsThe classic conversion deadlock, and how your detector resolves it.

Answer

They deadlock, and the detector breaks it by aborting one of them. T1 keeps S and queues X, which is blocked by T2's S. T2 keeps S and queues X, which is blocked by T1's S. The wait-for snapshot contains T1→T2 (T1's pending X against T2's granted S) and T2→T1, which is a cycle.

On its next pass, the detector picks the member with the lower priority number, breaking ties by the higher ID. It CASes that transaction to ABORTED and calls releaseAllLocks, which removes both the victim's granted S and its pending X. The grant loop then gives the survivor its upgrade, since its X is now compatible. The victim's thread wakes, sees it was aborted, backs off, and restarts with priority + 1. The test file test1.txt is built around exactly this pattern.

Keeping S makes this deadlock possible, but dropping S (the old behaviour) avoided it only by breaking serializability. The standard way to avoid it is a U lock: a transaction that intends to write takes U instead of S, so the second would-be upgrader waits at the U request instead of forming a cycle. Or it takes X up front when the write is known in advance, which my benchmark could do because each transaction's operations are generated ahead of time.

"Guaranteeing" serializability

S10
Prerequisites
  • Sequence number: a global atomic counter, incremented for each recorded event, that gives the events a total order.
  • Invariant check: a property that must hold at the end of any correct run, e.g. "each counter equals the number of committed increments".
  • The precedence-graph test from S2.

How did you verify that your engine actually produces serializable schedules?

TestsWhether "guaranteeing" is backed by a real check, and whether you know the check's limits.

Answer

Two automatic checks on every benchmark run, plus regression tests. Before those existed, I replayed logs by hand.

  1. Precedence graph over the real history. Right after each lock is granted, while it's still held, the worker records {sequence number, transaction, R or W, item}. Conflicting operations can't hold their locks at the same time, so sequence order equals the true conflict order. After the run, for each item I sort committed events by sequence number, add an edge for each conflicting pair from different transactions, and run Kahn's algorithm. The number of transactions it can't place must be zero.
  2. Lost-update invariant. Each write stores (value seen) + 1, so at the end every item's value must equal the number of committed writes to it.
  3. Regression tests for each bug: 16 checks, covering the upgrade window, granted waits, cycle-only victims, an end-to-end deadlock, and the commit/abort race.

Results: all 100 recorded benchmark runs at 1–64 threads passed both checks, across CPU-only, low-contention and high-contention workloads. At 1,000 threads, 2 of 5 runs failed the precedence check while passing the lost-update check. That shows the graph check is the stronger of the two.

Limits: testing can show a bug exists but can't prove there isn't one. The checks only look at committed transactions. And they test conflict-serializability, which is exactly what 2PL promises, but stricter than necessary for correctness.

S11
Prerequisites
  • "Guarantee" means for every execution, not just the ones you tried.
  • Incarnation: each restart of an aborted transaction is a new attempt. In this engine it reuses the same transaction ID, but a new Transaction object.

Your CV says "guaranteeing ACID serializability across 1,000+ threads." Is serializability actually guaranteed at 1,000 threads?

TestsHonesty under pressure. The interviewer may already suspect the answer.

Answer

No. Up to 64 threads, every run I recorded was serializable. At 1,000 threads I found a race that breaks it, identified the cause, and validated a fix, but the fix isn't merged yet.

  • Evidence of failure: the low-contention benchmark (1,000 transactions, 1,000 items, 1 ms per operation) at 1,000 threads failed the precedence-graph check in 2 of 5 runs, with 3 and 101 transactions that couldn't be placed in any serial order. An instrumented reproduction failed in 4 of 20 runs.
  • Cause: the deadlock detector marks a victim aborted, then releases "all locks of transaction ID n" a moment later. If the victim has already restarted under the same ID and taken new locks, that delayed release removes the new attempt's locks and hands them to someone else. Two transactions then both hold X on one item.
  • Fix validated: skipping the release when the registry now holds a different transaction object under that ID gave 0 of 20 failures.
  • Where it holds: 100 of 100 runs at 1–64 threads passed.

Also, "ACID serializability" isn't a real term. Serializability is the I in ACID, and my engine doesn't provide the D at all (E5).

Be careful

Don't say "guaranteed". A safe version: "implements strict 2PL, verified serializable with a precedence-graph check on every benchmark run; all runs up to 64 threads passed, and at 1,000 threads I found and root-caused a remaining race." Interviewers respect a found-and-explained bug far more than a claim that collapses on the first follow-up.

Walk me through the race you found at 1,000 threads. How did you confirm it was the root cause?

TestsConcurrency debugging method: hypothesis, instrumentation, controlled experiment, and honest statistics.

Answer

The sequence. In one pass, the detector finds a cycle through T17 and:

  1. CASes T17 to ABORTED.
  2. Logs a warning, which takes the logger mutex and flushes to a file.
  3. Calls releaseAllLocks(17), which has to win the one lock-table mutex against up to 1,000 worker threads.

Between steps 1 and 3, T17's worker is woken by some other thread's notify_all. It sees ABORTED, backs off for 1.4–2.6 ms, and calls beginTransaction with ID 17. That call releases the old attempt's locks itself, registers a new transaction object with ID 17, and the new attempt starts acquiring locks. If the detector is still stalled, step 3 then removes the new T17's locks and grants them to waiters. The new T17 carries on believing it holds X, while another transaction also holds X on the same item.

Confirming it.

  1. Symptom: precedence-check failures appeared only at 1,000 threads, with the lost-update check still passing.
  2. Hypothesis from reading the code: an ID-keyed release can target the wrong attempt.
  3. Instrumentation: I passed the aborted transaction object into releaseAllLocks and counted releases where the registry held a different object that owned granted locks. With the repo's behaviour unchanged, 12 of 20 runs had at least one such stale release (20 locks in total), and 4 of 20 runs failed serializability.
  4. Controlled change: the same build, but skipping those releases. The skip fired 20 times across 14 runs, and 0 of 20 runs failed. Throughput didn't change beyond noise (2,475.8 vs 2,372.5 txn/s median).

Honest statistics: 4/20 has a 95% Wilson interval of roughly 8–42%, and 0/20 roughly 0–16%. A one-sided Fisher test gives p ≈ 0.053. The failure counts alone are suggestive, not conclusive. The stronger evidence is mechanistic: stale releases were observed, and removing exactly them removed the failures.

Proper fix: make the release name the attempt, not just the ID. Pass an incarnation number or the object, give each restart a fresh ID, or mark aborted and release inside one critical section.

S13
Prerequisites
  • Oversubscription: more runnable threads than cores. The OS scheduler time-slices them, so any single thread can wait milliseconds to run again.
  • Race window: the time interval in which a bad interleaving is possible. A bug shows up when some thread's delay is longer than that window.
  • Lock convoy: many threads queued on one mutex, each waking, running briefly and waiting again.

Why did the race appear only at 1,000 threads and never at 64?

TestsReasoning about timing windows and scheduling, and being clear about what's measured versus inferred.

Answer

The bug needs the detector to stall between marking the victim aborted and releasing its locks, for longer than the victim takes to back off (at least 1.4 ms), restart, and grab new locks. Stalls that long are rare with 64 threads and routine with 1,000.

With 1,000 threads on 8 cores, the detector thread competes for CPU time with up to 1,000 others, so being descheduled for a few milliseconds is normal. It also has to win the single lock-table mutex against a large convoy of workers, and it flushes a log line under the logger mutex in the middle of the window. At 64 threads, contention on both the CPU and the mutex is far lower, so the detector almost always finishes the release before the victim restarts.

What's measured and what's inferred: the measurement is 0 failures in 100 recorded runs at up to 64 threads, versus 2 of 5 and 4 of 20 at 1,000 threads. That the scheduling delay is the reason is an inference from how the window works. I didn't measure detector stall times. The takeaway: "didn't fail at 64 threads" never meant "correct". The window existed all along, and more threads only made it likely to be hit.

S14
Prerequisites

ABA problem: thread 1 reads a value A and plans a compare-and-swap. Thread 2 changes it to B and back to A. Thread 1's CAS then succeeds, even though the thing it refers to has changed, for example a freed and reallocated node at the same address. Standard fixes: a version counter or tagged pointer alongside the value, or deferred reclamation (hazard pointers, epochs).

Is your 1,000-thread race related to the ABA problem?

TestsWhether you can connect your bug to a known family and borrow its known fixes.

Answer

It's the same family: identity by a reused name. In ABA, a pointer value is reused for a new object. In my bug, a transaction ID is reused for a new attempt. The detector decided to release "transaction 17" when 17 meant the aborted attempt, but acted after 17 had come to mean the restarted one. It's not literally a failed CAS, though. It's a stale ID-keyed operation.

The fixes carry over directly:

  • Version or tag: pair the ID with an incarnation counter, and have releaseAllLocks(id, incarnation) do nothing if the registered attempt's counter differs. That's the equivalent of a tagged pointer.
  • Compare identity, not name: pass the Transaction object (the registry already stores shared_ptrs) and skip the release if the registry holds a different object. That's what my validated scratch fix did.
  • Never reuse the name: give every restart a fresh ID, while keeping the original timestamp for priority purposes.

Interestingly, the codebase already used this idea in one place. UnregisterTransaction(id, expected) removes an entry only if it's the expected object, which stops an old attempt's cleanup from deleting the new registration. The same guard was missing on lock release.

S16
Prerequisites
  • state.compare_exchange_weak(expected, desired): atomically, if state == expected, set it to desired and return true. Otherwise copy the current value into expected and return false. The "weak" form may fail spuriously, so it's used in a loop. The "strong" form doesn't fail spuriously.
  • Lock ordering: taking mutexes in inconsistent orders across threads can deadlock the threads themselves.

Why did you use compare-and-swap for commit and abort instead of a mutex? Walk me through the race.

TestsAtomics beyond counters: exactly-once state transitions under contention.

Answer

The owner's commit and the detector's abort race to end the same transaction, and exactly one may win. A CAS on a single atomic enum gives that cheaply, with no new lock to fit into the existing mutex order.

bool Transaction::commit() {
    TransactionState s = state.load();
    while (s == GROWING || s == SHRINKING)
        if (state.compare_exchange_weak(s, COMMITTED)) return true;
    return false;                       // someone else set ABORTED (or it already committed)
}
bool Transaction::abort() {
    TransactionState s = state.load();
    while (s != COMMITTED)
        if (s == ABORTED || state.compare_exchange_weak(s, ABORTED)) return true;
    return false;                       // it committed first
}

Both threads load GROWING.

  • If the detector's CAS lands first: the state is ABORTED. The owner's CAS fails, s becomes ABORTED, and its loop exits, so commit returns false and the worker retries.
  • If the owner lands first: the detector's CAS fails, s becomes COMMITTED, so abort returns false and the detector logs that the victim already finished.

A spurious failure just re-reads s and tries again. Neither order lets both succeed.

Why not a mutex: a per-transaction mutex would work too. But the detector calls abort while holding its graph mutex, and the owner calls commit while holding nothing, so a new mutex would add another lock-ordering rule to get right. The CAS also can't block, and its only possible delay is a retry.

Why it matters downstream: commit installs writes only after its CAS succeeds, so the detector can never abort a transaction halfway through installing.

S17
Prerequisites
  • Lock hierarchy: give every mutex a rank, and always acquire in increasing rank. That makes a cycle of threads waiting on each other's mutexes impossible.
  • Leaf lock: a mutex whose holder never acquires any other mutex, so it can always be taken last.

Your engine has several mutexes. How do you make sure the engine's own threads can't deadlock on them?

TestsWhether you applied deadlock reasoning to your implementation, not only to transactions.

Answer

Every code path takes them in one consistent order, and the lowest-level mutexes are leaves. The order is:

ConcurrencyManager::mtx
  → DeadlockDetector::run_mutex_ → graph_mutex_
      → LockManager::mtx
          → Transaction::registry_mutex_          (leaf)
          → ResourceAllocationGraph::mtx → Logger::mtx   (logger is a leaf)
  • The facade takes its mutex only for map lookups and phase checks, and releases it before calling LockManager::acquireLock, which may sleep. beginTransaction does call releaseAllLocks while holding the facade mutex, which is facade → lock table, consistent with the order.
  • The detector holds its graph mutex while calling getWaitForEdges and releaseAllLocks (graph → lock table). No lock-manager code ever calls back into the detector, so that edge is never reversed.
  • LockManager looks up transactions under its mutex. The registry mutex is a leaf: its three functions touch only the map.
  • Waiting for a transaction lock uses cv.wait, which releases the lock-table mutex while sleeping. No thread ever sleeps holding a mutex.

One self-deadlock did exist: the logger's setters locked its mutex and then called info(), which locked it again. Nothing called those setters, and the fix removed the outer lock.

1,000+ threads

S18
Prerequisites
  • Thread-per-transaction: each transaction gets its own OS thread. Thread pool: a fixed number of worker threads take transactions from a shared queue.
  • std::barrier(n): each thread calls arrive_and_wait(), and all n are released together once the last arrives.

Where do the "1,000+ threads" come from? How did you run them?

TestsWhether the number is concrete and you know exactly what it counts.

Answer
  • Text-schedule harness: thread-per-transaction. The 1,000-transaction files start 1,000 worker threads, each waiting at a std::barrier so they all begin their first operation at the same instant. Add the main thread and the detector thread, and that's 1,002 threads.
  • Benchmark: a pool of T workers pulling transaction indices from an atomic counter. At T = 1,000 with 1,000 transactions, each worker ends up running about one transaction. A std::latch starts the clock only once every thread exists.

All of this ran on an 8-core Apple M3, so at most 8 threads execute at any instant. The rest are blocked on locks, sleeping in simulated I/O or backoff, or waiting for the scheduler.

What 1,000 threads showed: they ran and completed, but the low-contention benchmark at 1,000 threads reached 13.98× over serial, less than 64 threads (53.74×), and it exposed the race in S12. On the high-contention workload, a 1,000-thread run took about 6 hours to commit 1,000 transactions.

Be careful

"1,000+ threads" is true as a count, but it isn't an achievement by itself. The interesting facts are that 64 threads was the fastest point measured, and that 1,000 threads broke serializability. Say "tested up to 1,000 concurrent threads", and have S19 ready.

Review: Part 4, sections 4 and 6

S19
Prerequisites
  • Blocked vs runnable: a thread sleeping or waiting on I/O or a lock doesn't need a core. A runnable thread does.
  • Context switch: the OS saving one thread's state and loading another's. It costs CPU time and evicts useful data from the CPU caches.
  • Thread stack: each thread reserves its own stack memory.
  • Sizing rule of thumb: \(N_{\text{threads}} \approx N_{\text{cores}} \times \left(1 + \frac{W}{C}\right)\), where \(W/C\) is the ratio of a task's waiting time to its computing time.

You have 8 cores. What does running 1,000 threads buy you, and what does it cost?

TestsOS-level reasoning about oversubscription, with your own numbers.

Answer

Threads beyond the core count help only while they're waiting on something other than the CPU and each other. Past that point they cost memory, scheduling time and lock contention.

The gain, measured: with 1 ms of simulated I/O per operation and rare conflicts, throughput scaled 7.97× at 8 threads (99.6% efficiency), 28.60× at 32 and 53.74× at 64 (84%). Sleeping threads don't need cores, so going past 8 still helped.

The costs at 1,000:

  • Each thread has its own stack and kernel structures.
  • Waking 1,000 threads and scheduling them on 8 cores adds latency to every hand-off.
  • With one lock-table mutex and a notify_all on every release, each release wakes a crowd that fights for the mutex.
  • Timing windows open up: the detector gets descheduled long enough to hit the race.

Result: 13.98×, with a 29% spread between runs and 2 of 5 runs not serializable. With no I/O at all, even 2 threads were slower than 1 (0.63×).

Sizing: \(N \approx 8 \times (1 + W/C)\). As a hypothetical, if a transaction spends 20× longer waiting than computing, that's \(8 \times 21 = 168\) threads. I didn't measure the real ratio, so in practice I'd pick the thread count from the measured curve, or adapt it at runtime (T8).

S20
Prerequisites

Thundering herd: many threads sleep on the same condition, one event wakes all of them, they all compete for the same mutex to re-check, and almost all go back to sleep. The wasted wakeups are roughly \(R \times W\): notifications times waiters.

What's a thundering herd? Does your lock manager have one?

TestsRecognizing a performance anti-pattern in your own design.

Answer

Yes. The lock manager uses one condition variable for every waiter on every resource, and every release calls notify_all. A release on item 5 wakes the threads waiting on item 900. Each one re-acquires the single lock-table mutex just to find its predicate is still false.

As a hypothetical: 10,000 releases with 100 waiters each is \(10{,}000 \times 100 = 1{,}000{,}000\) wakeups, when each release could unblock only a few waiters. I didn't count wakeups in my runs. It's a likely contributor to the CPU-only workload getting slower with more threads (0.24× at 32), alongside plain mutex contention, but I didn't isolate it.

Fixes, in increasing effort:

  1. One condition variable per resource, notified only when that resource changes.
  2. Because releases already grant waiters directly, notify only the specific threads whose requests were granted, using a condition variable per waiting request.
  3. Combine that with a striped lock table (S21), so unrelated resources don't even share a mutex.

Review: Page 2, section 6 · Part 2, section 5

S21
Prerequisites
  • Lock striping: split a table into N buckets by hash of the key, each with its own mutex, so operations on different buckets run in parallel.
  • Cache-line bouncing: a heavily shared mutex's memory ping-pongs between cores' caches, slowing every acquisition.
  • Consistent snapshot: reading a multi-part structure as it was at one instant.

Your CPU-only benchmark got slower with more threads. How would you make the lock manager scale across cores?

TestsSystems design applied to your own bottleneck, including the trade-offs a fix introduces.

Answer

The evidence: with no work per operation, throughput fell from 333,625 txn/s at 1 thread to 79,181 at 32 (0.24×). Every lock call serializes on one mutex, and every release wakes every waiter. Even against the slowest single-thread run, 32 threads reached only 0.30×.

Changes, in order of impact:

  1. Stripe the lock table: hash resource IDs into, say, 64 buckets, each with its own mutex and wait queues. Transactions on different items stop contending.
  2. Targeted wakeups: a wait queue per resource, and notify only the waiters that were just granted (S20).
  3. Get work out of the critical section: my lock manager builds log-message strings under the mutex even when the log level discards them, and the text harness writes the whole resource graph to a file while holding a mutex that lock operations also need.
  4. Cheaper request bookkeeping: reuse request objects instead of allocating them, and replace the per-transaction scans in releaseAllLocks (which walks the entire table) with a per-transaction list of held resources.

The trade-off: the deadlock detector currently takes one consistent snapshot under the single mutex. With stripes, I'd either lock all stripes in index order for the snapshot (a brief global pause), or accept a non-atomic snapshot and re-verify each cycle's edges under the relevant stripe latches before aborting, which avoids phantom deadlocks. Real systems also add lock-wait timeouts as a backstop.
