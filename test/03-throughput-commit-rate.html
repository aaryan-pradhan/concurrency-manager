Measuring throughput

T1
Prerequisites
  • Throughput: committed transactions per second.
  • Speedup: \(S(T) = \dfrac{\text{throughput with } T \text{ threads}}{\text{throughput with 1 thread}}\). Parallel efficiency: \(E(T) = S(T)/T\), where 1.0 means every thread contributed fully.
  • Median of runs: the middle value of repeated runs, which is less sensitive to one outlier than the mean.
  • Fixed seed: a random generator started from a fixed value produces the same "random" workload every time.

How did you measure throughput and speedup?

TestsBenchmark methodology: is the comparison controlled, repeated, and clearly defined?

Answer

A dedicated benchmark runs one fixed workload at several thread counts in the same binary, repeats each point 5 times, and reports the median, plus min–max and aborts.

  • Workload: N transactions of 4 operations each, generated once from a Mersenne Twister with seed 42. Each operation picks an item uniformly and is a write with a set probability. Optionally, each operation sleeps while holding its lock, to simulate I/O.
  • Execution: a pool of T workers pulls the next transaction index from an atomic counter. The clock starts when a latch releases the already-created workers and stops when the last one joins.
  • Metrics: throughput = commits ÷ seconds per run. Speedup = median at T ÷ median at 1 thread.
  • Correctness: every run is also checked for serializability and lost updates, so a fast but wrong run can't count.

Three configurations:

  • A: CPU-only, 2,000 transactions, 1,000 items, 20% writes.
  • B: 1 ms per operation, 1,000 items, 20% writes.
  • C: 1 ms per operation, 20 items, 30% writes.

Run on an 8-core Apple M3, built at -O2, with a 10 ms deadlock-detection interval.

T2
Prerequisites

A fair baseline changes only the variable you're studying, here the number of threads, and keeps code, workload, compiler flags, machine and measurement identical. A strong baseline is the best reasonable alternative. For concurrency control, that's often a version with no locking at all, because a single thread doesn't need locks.

What exactly is your "single-threaded baseline"? Is it a fair one?

TestsWhether the speedup is inflated by a weak or different baseline.

Answer

It's the same benchmark binary with one worker thread: the same workload, engine, flags and machine. So it's fair for the question "how does this engine scale with threads?"

It is not the strongest possible baseline. The single worker still goes through the full lock manager (a mutex acquisition, table updates and log-string building for every operation), and the deadlock detector thread still wakes every 10 ms. A purpose-built serial executor with no locking would be faster, especially on the CPU-only workload, and would make every speedup smaller. I didn't build one.

History: the original project had no baseline at all. When I first built one for the old text harness (the same program, joining each thread right after starting it), serial was faster than 1,000 concurrent threads, by 16.8× to 72.9×.

Be careful

Say "compared with the same engine running one worker thread". Don't call it an "optimized single-threaded implementation".

T3
Prerequisites

A speedup figure is meaningless without its conditions: work per operation, contention (how often transactions touch the same items), thread count, and hardware. The same engine can go from far above 1× to far below it just by changing the workload.

Where does the "6x throughput speedup" on your CV come from?

TestsWhether a headline number traces to a real, reproducible measurement.

Answer

Honestly, there's no recorded run in the project that produces 6× as a result, so I wouldn't quote it. Here is what I did measure, with conditions.

C: 1 ms I/O per op, 20 items (high contention)2.83× at 4 threads2.73× at 8; 0.25× at 64

Never invent how a number was measured. If 6× came from an earlier informal run you can't reproduce, say exactly that, then give the measured table. Also, these benchmark numbers come from the September 2026 rework, not the 2025 course version. T4
Prerequisites
  • I/O-bound vs CPU-bound: an I/O-bound task spends most of its time waiting, and a waiting thread doesn't use a core.
  • Contention: how often concurrent transactions need the same item in incompatible modes, which forces waits.
  • Efficiency \(E(T) = S(T)/T\) from T1.

Walk me through the low-contention I/O results. Why does throughput scale almost linearly, even past 8 cores?

TestsInterpreting a scaling curve from first principles.

Answer

Two conditions make it scale.

First, the work is waiting. Each transaction spends about 4 ms asleep in simulated I/O and only a few microseconds in the lock manager. Sleeping threads don't compete for cores, so 64 threads on 8 cores still run nearly in parallel. The serial run shows the ratio: 1,000 transactions × 4 ms is 4.0 s of sleep, against about 5.23 s total.

Second, conflicts are rare. With 1,000 items and 4 operations, two transactions share an item with probability about \(1 - (1 - 4/1000)^4 \approx 1.6\%\). At 64 threads, each transaction overlaps with about \(63 \times 0.0159 \approx 1\) other, so waits are short and there were zero deadlock aborts.

Efficiency: \(E(8) = 7.97/8 = 0.996\), and \(E(64) = 53.74/64 = 0.84\). The 16% loss at 64 threads is the single global mutex, wakeups and occasional waits starting to show.

T5
Prerequisites
  • Amdahl's law: if a fraction \(p\) of the work can run in parallel on \(N\) processors, the maximum speedup is \(S(N) = \dfrac{1}{(1 - p) + p/N}\).
  • Critical section: code under a mutex runs one thread at a time, so it counts as serial.
  • Contention overhead: when threads fight for a mutex, they pay for failed attempts, sleeping, waking and context switches, so the result can be slower than serial.

Why did your CPU-only benchmark get slower as you added threads?

TestsAmdahl's law, and the difference between "doesn't speed up" and "slows down".

Answer

Measured: 333,625 txn/s on 1 thread, then 0.63× at 2 threads, 0.43× at 4, 0.34× at 8, 0.28× at 16 and 0.24× at 32.

Why. With no simulated I/O, a transaction is four lock-manager calls. Nearly all of its time is inside the one lock-table mutex, so the parallel fraction \(p\) is close to 0. Amdahl's law then caps speedup at about 1×. For contrast, even \(p = 0.9\) on 8 cores gives only \(1/(0.1 + 0.9/8) = 1/0.2125 = 4.7\times\).

Getting slower than 1× comes from overhead Amdahl ignores. Threads collide on the mutex and have to be put to sleep and woken. Each release calls notify_all, waking every waiter. And the mutex's memory bounces between cores' caches. A single thread pays none of that.

Caveat on the baseline: the five single-thread runs rose steadily from 263k to 375k txn/s, which looks like warm-up, so the 1× reference is noisy. Even against the slowest serial run, 32 threads reached only \(79{,}181 / 263{,}431 = 0.30\times\).

Lesson: this is the curve that measures the lock manager itself, and it doesn't scale. That's what motivates striping the table and targeted wakeups (S21).

T6
Prerequisites
  • Oversubscription (more runnable threads than cores) and thread wake-up latency.
  • In the benchmark, T workers share N transactions. At T = N = 1,000, each worker runs about one transaction and then exits.

Why was throughput at 1,000 threads lower than at 64 threads?

TestsRecognizing when "more threads" changes the regime.

Answer

Measured: 2,671.8 txn/s median (13.98×) at 1,000 threads, against 10,273.0 (53.74×) at 64. The spread across runs was 2,220 to 3,004, and 45 aborts per run on average, against zero at 64 threads.

Why:

  • With 1,000 threads for 1,000 transactions, nothing is reused. The run is dominated by getting 1,000 threads scheduled on 8 cores, and each takes its turn to wake from the latch, grab the global mutex and get through its critical sections.
  • Mutex convoys: many runnable threads queue on the one lock-table mutex, and every release wakes a crowd.
  • More simultaneous transactions means more chance of overlap, so deadlocks appeared (45 aborts), each costing a restart and backoff.
  • Timing windows widened enough to break correctness: 2 of 5 runs failed serializability (S12).

So past some point, threads stop adding parallel waiting and start adding scheduling and coordination cost. For this workload the best measured point was 64. I didn't test between 64 and 1,000.

T7
Prerequisites
  • Abort (restart): all the work a transaction did so far is thrown away.
  • Data-contention thrashing: past a certain level of concurrency, adding transactions increases blocking and aborts so much that total throughput falls.

What happened to throughput under high contention? Explain the shape of the curve.

TestsUnderstanding thrashing with real numbers.

Answer
Threads1248163264
txn/s192.3342.7543.6525.7253.2104.547.9
speedup1.001.782.832.731.320.540.25
aborts / run0823964331,4793,844

Config C: 1,000 transactions, 20 items, 30% writes, 1 ms per operation. Every run was serializable.

Rise, peak, collapse. With 20 items, two transactions share an item with probability about \(1 - 0.8^4 = 59\%\). At 2–4 threads, most operations still proceed and waiting I/O is shared, so throughput rises. By 8 threads, waits chain behind lock holders who are themselves sleeping 1 ms per operation, and deadlocks multiply. At 64 threads, each transaction overlaps with about \(63 \times 0.59 \approx 37\) others. The result was 3,844 aborts for 1,000 commits: about 79% of attempts wasted, each throwing away up to 4 ms of work plus backoff.

That's data-contention thrashing: the system spends more effort on conflict than on work. Aborts grew roughly 2.6–4.5× per doubling of threads, faster than throughput could.

T8
Prerequisites
  • Admission control: cap how many transactions run at once, and queue the rest.
  • AIMD (additive increase, multiplicative decrease): the feedback rule TCP uses. Grow slowly while things are healthy, and cut sharply when a congestion signal appears.
  • Abort share = aborts ÷ (aborts + commits).

Given those curves, how would you choose the number of concurrent transactions in production?

TestsTurning measurements into an operational policy.

Answer

Cap concurrency near the measured peak for the workload, and in production, adapt it with feedback, because contention changes over time.

  • Static: from my data, the high-contention workload should run with 4–8 concurrent transactions (2.83× and 2.73×), while the low-contention I/O workload kept improving to 64. Extra requests wait in a queue instead of joining the fight for locks.
  • Adaptive: track throughput and abort share over a window. Add one concurrency slot at a time while throughput rises. When the abort share jumps, cut the limit, say by half. The signal is strong: abort share was \(23/1{,}023 = 2.2\%\) at 4 threads but \(3{,}844/4{,}844 = 79.4\%\) at 64.
  • CPU-bound portions: keep runnable threads near the core count. The CPU-only workload was fastest at 1.

Admission control fixes the symptom. Reducing lock hold times, or taking locks in order (T17), reduces the contention itself.

T9
Prerequisites
  • Relative spread: (max − min) ÷ median across repeated runs.
  • Warm-up: early runs are slower while caches, memory allocators and CPU frequency settle.
  • A difference is convincing when it's much larger than the run-to-run spread.

How noisy are your measurements? How do you know a speedup is real and not noise?

TestsMeasurement rigor.

Answer

Each point is 5 runs, and I report the median and the min–max range. Relative spreads:

  • Low-contention I/O at 1 thread: \((191.53 - 190.61)/191.15 = 0.5\%\), very stable.
  • The same workload at 1,000 threads: \((3{,}004 - 2{,}220)/2{,}672 = 29\%\).
  • High contention at 64 threads: \((52.6 - 46.2)/47.9 = 13\%\).
  • CPU-only at 1 thread: 33%. The five runs rose monotonically, 263k → 306k → 334k → 359k → 375k, so that's warm-up rather than random noise.

Which conclusions survive the noise: 53.74× vs 1× at 0.5% spread is unambiguous. 2.83× vs 2.73× (4 vs 8 threads under high contention) is within noise: the 8-thread range 518.8–567.1 overlaps the 4-thread range 534.5–551.6. So I'd say "peaks around 4–8 threads", not "4 is best". The CPU-only baseline is the least trustworthy number, but even against its slowest run, 32 threads is 0.30×.

What I'd improve: discard a warm-up run, run more repetitions, alternate thread counts in random order instead of running them in sequence, and report confidence intervals.

T10
Prerequisites
  • Timer granularity: sleep_for(1ms) guarantees at least 1 ms, and the OS may wake the thread later.
  • Real storage I/O queues at the device and competes for buffer-pool latches. A sleep competes for nothing.

You simulated I/O with a 1 ms sleep while holding locks. What are the pitfalls of that?

TestsWhether you know how representative your benchmark is.

Answer
  • It's a best case for concurrency. A sleeping thread uses no CPU and no shared device, so 64 sleepers really can run in parallel. Real disk or network I/O has limited parallelism, queueing, and contention on buffers and log flushes, so 53.74× is an optimistic upper bound for that workload shape.
  • Sleeps overshoot. The serial run took 5.22–5.25 s for 4.0 s of requested sleep. For run 0, \(5.2269 - 4.0 = 1.23\) s over 1,000 transactions is 1.23 ms per transaction of overhead, part of it sleeps overshooting and part the engine. I didn't separate the two.
  • Holding locks during the sleep is a deliberate choice. It models transactions that do slow work mid-transaction, which is the case where lock hold time hurts. Doing the I/O before taking locks would give very different contention results.
  • No CPU work per operation, so it doesn't model query execution, and it hides the CPU-side bottleneck that the CPU-only workload exposes.

So I present the I/O results as "scaling when transactions spend most of their time waiting", and always pair them with the CPU-only and high-contention results.

Commit rate under contention

T12
Prerequisites
  • Eventual commit rate: the fraction of transactions that commit at some point, counting all retries.
  • Per-attempt success rate: commits ÷ (commits + aborts). Every abort-and-retry counts as a failed attempt.
  • Retry loop: an aborted transaction restarts until it commits.

What does "100% transaction commit rate" mean in your system, and how is it achieved?

TestsWhether the metric measures the engine, or is guaranteed by the harness.

Answer

It means every transaction eventually committed, and that's guaranteed by the retry loop, not earned by the engine. Both harnesses restart an aborted transaction, with backoff, until it commits, and a benchmark run can't finish unless every transaction has committed. So in every completed run the eventual commit rate is 100% by construction.

The informative numbers are the per-attempt ones:

  • High contention at 4 threads: 23 aborts per 1,000 commits, so 2.2% of attempts wasted.
  • High contention at 64 threads: 3,844 aborts, so \(3{,}844 / 4{,}844 = 79.4\%\) of attempts wasted.
  • Original harness on the deadlock-heavy file (pre-fix): 6,701 restarts for 1,000 commits. Its own "Transaction Success Rate" metric printed 13.0%.
  • High contention at 1,000 threads: the run didn't complete in usable time, about 6 hours for run 0.
Be careful

"100% commit rate under high contention" invites the question "how many aborts?", and the answer undoes the claim. Say instead: "every transaction eventually committed through detection and restart; under heavy contention that cost up to 3.8 aborts per commit at 64 threads, which is why throughput peaked at 4–8 threads."

T13
Prerequisites

If transaction A touches 4 distinct items out of \(n\), and transaction B makes 4 independent uniform picks, the chance B misses all of A's items is \((1 - 4/n)^4\). So the chance they share at least one item is about \(1 - (1 - 4/n)^4\). That's an upper bound on actually conflicting, because two reads of the same item don't conflict.

What does "high contention" mean quantitatively in your experiments?

TestsWhether "high contention" is defined, or just a label.

Answer \[ P(\text{share an item}) \approx 1 - \Big(1 - \frac{4}{n}\Big)^{4} \]

Low contention, \(n = 1{,}000\): \(1 - 0.996^4 = 1 - 0.9841 = 0.0159\), about 1.6%. At 64 threads, each transaction overlaps about \(63 \times 0.0159 \approx 1.0\) others.

High contention, \(n = 20\): \(1 - 0.8^4 = 1 - 0.4096 = 0.5904\), about 59%, with 30% writes. At 64 threads, about \(63 \times 0.59 \approx 37\) others.

The original deadlock-heavy file was contention by construction. Batches of 10 transactions over 3 items, half reading K then writing J and half reading J then writing K, so once each holds its first S lock, every odd transaction waits on every even one. That's a complete bipartite wait graph with 50 edges, drawing on a pool of just 12 items.

So when I say "high contention", I mean the 20-item configuration: more than half of all transaction pairs touch a common item.

T14
Prerequisites
  • Latency: time from a transaction's first start to its commit, including waits, restarts and backoff sleeps.
  • Tail latency: the slowest transactions (max, p99), which is what users notice.

What did the 100% commit rate cost in wasted work and latency?

TestsWhether you look past the headline metric at its cost.

Answer
  • Wasted work in the benchmark: at 64 threads under high contention, 3,844 aborted attempts for 1,000 commits. Each aborted attempt may already have done up to 4 ms of simulated I/O while holding locks, which also blocked others.
  • Latency in the original harness (pre-fix, deadlock-heavy file): average 25,087 ms from first start to commit, maximum 33,909 ms, for transactions that do three lock operations. No transaction committed with fewer than 5 restarts, and most needed 6–8. Backoff alone explains much of it: base sleeps of 80, 160, 320, 640, 1,280, 2,560 and 5,000 ms sum to 10,040 ms after 7 restarts, before any lock waits.
  • Extreme case: high contention at 1,000 threads. About 6 hours and 220,943 aborts to commit 1,000 transactions, and one transaction was aborted 1,980 times.

The benchmark measured throughput, not per-transaction latency, so I can't quote p99 for the fixed engine. That's a gap I'd close (T18).

T15
Prerequisites
  • Exponential backoff: after the k-th failure, wait roughly \(b \cdot 2^k\), up to a cap.
  • Jitter: random variation in the wait, so that transactions which failed together don't all retry at the same moment.

Why do you restart aborted transactions with exponential backoff and jitter? What are the actual formulas?

TestsRetry design, and the trade-off between latency and repeated collisions.

Answer

An immediate restart recreates the same conflict with the same transactions, so they deadlock again. Waiting longer as failures repeat reduces pressure while contention lasts, and randomness spreads out retries so they don't re-collide in lockstep.

Benchmark:

\[ b_k = \min\big(1000 \cdot 2^{k},\ 100{,}000\big) \cdot \frac{j}{100}\ \mu\text{s}, \quad j \in \{70, \ldots, 129\} \]

First retry: 2 ms × (0.70 to 1.29), so 1.4–2.58 ms. From the 7th retry on, the base is capped at 100 ms, so 70–129 ms.

Original text harness:

\[ b(p) = \Big\lfloor \min\big(20 \cdot 2^{p},\ 5000\big) \cdot \tfrac{100 + j}{100} \Big\rfloor \text{ ms}, \quad j \in \{-30, \ldots, 29\} \]

Here \(p\) is the priority after incrementing, 2 on the first restart, so the first backoff is 56–103 ms and the capped one 3,500–6,450 ms. Jitter is applied after the cap, so the "5-second maximum" is exceeded by up to 29%.

Trade-off: longer backoff means fewer repeat deadlocks but higher latency and idle time. The old harness's multi-second sleeps are a big part of why its average latency reached 25 seconds, which is one reason the benchmark uses a 1 ms base and a 100 ms cap.

T16
Prerequisites
  • Deadlock: threads are blocked, and nothing moves.
  • Livelock: threads keep running and changing state, like repeatedly aborting and retrying, but make little or no progress.
  • Starvation: the system as a whole progresses, but a particular transaction doesn't.

What's livelock? Did you see it?

TestsProgress properties, identified in your own data.

Answer

Livelock is activity without progress. In lock-based systems it usually looks like transactions repeatedly deadlocking, aborting and retrying into the same conflicts.

Close to it, yes. The high-contention workload at 1,000 threads (20 items, 30% writes) logged 220,943 deadlock aborts over about 5 h 58 min to commit 1,000 transactions, roughly 221 aborts per commit. The second run was killed after about 2 h 22 min and 175,970 aborts. The system technically progressed, and run 0 finished, so strictly it's severe thrashing plus starvation rather than a pure livelock. In practice, it was unusable.

Mitigations:

  • Admission control, so far fewer transactions compete at once (T8).
  • Backoff that grows enough to actually thin out the competitors.
  • Victim policies with a progress guarantee, such as keeping the original timestamp and never aborting the oldest (D5).
  • Removing deadlocks altogether by acquiring locks in a fixed order when the item set is known (T17).

Review: Part 3, section 7

T17
Prerequisites
  • Ordered acquisition: if every transaction locks items in the same global order (say, ascending ID), there can't be a circular wait, so there are no deadlocks.
  • Conservative (static) 2PL: acquire every lock at the start.
  • Wound-wait: an older transaction that needs a younger one's lock aborts it, and a younger one waits for an older one.

How would you reduce the number of aborts under high contention?

TestsEngineering options, grounded in the workload's structure.

Answer
  1. Remove deadlocks structurally. In my benchmark, every transaction's operations are generated before it runs. I could sort its items and take each item's strongest needed lock, X if any operation writes it, in ascending order. No circular wait means zero deadlock aborts. It also removes upgrade deadlocks, because read-then-write takes X up front. The cost is holding some locks longer than needed.
  2. Shorten lock hold time. Do slow work (the 1 ms "I/O") before acquiring locks, or outside the transaction, so conflicts overlap less.
  3. Limit concurrency to the measured peak, about 4–8 here (T8).
  4. Use update locks for read-then-write, to avoid conversion deadlocks without taking X early.
  5. Better victims: abort the transaction that has done the least work, and keep original timestamps so old transactions stop being re-victimized.
  6. Change the concurrency-control scheme for the workload: MVCC so reads never block, or wound-wait to avoid detection delay.

I'd start with option 1 in the benchmark, because it's simple, provably deadlock-free for that harness, and directly testable with the existing serializability checks.

T18
Prerequisites
  • Throughput: work completed per unit of time. Latency: time for one unit of work.
  • Percentiles: p50 is the median, p99 is the value 99% of transactions beat.
  • Techniques that raise throughput, like batching and queueing, often increase latency.

Throughput and latency: which did you optimize, and what would you add to the benchmark?

TestsWhether you know what your numbers leave out.

Answer

The benchmark measures throughput only. The original harness recorded per-transaction latency, but on the old engine.

They can diverge sharply. Under high contention, a few long-starved transactions barely move average throughput, but they dominate tail latency. In the old harness, the average latency was 25 s with a maximum of 34 s. And a transaction aborted 1,980 times would have an enormous individual latency, even if the run's throughput looked tolerable at lower thread counts.

What I'd add:

  • Record start time on the first attempt and end time at commit, per transaction.
  • Report p50, p99 and max latency, plus a histogram of aborts per transaction (a direct starvation metric).
  • Report time spent waiting for locks versus doing work.
  • Report the abort share per point.

Then the admission-control choice in T8 could target "maximize throughput subject to p99 under X ms", which is how production systems are actually tuned.
