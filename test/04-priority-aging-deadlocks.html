Starvation, priority, aging

D1
Prerequisites

Progress properties describe whether work gets done. Safety says nothing bad happens, like a non-serializable result. Liveness says something good eventually happens, like a transaction committing. Deadlock, livelock and starvation are three different liveness failures.

What is starvation, and how is it different from deadlock and livelock? Give an example of each from your system.

TestsPrecise vocabulary, tied to concrete cases.

Answer
DefinitionIn my system
Deadlocka set of transactions each blocked waiting for a lock another holds, in a cycle. Nobody in the set moves.two readers of F both request X(F) (the upgrade deadlock); the alternating R(K)…W(J) / R(J)…W(K) batches
Livelocktransactions keep acting, aborting and retrying, but the group makes little or no progresshigh contention at 1,000 threads: about 221 aborts per commit over roughly 6 hours
Starvationthe system progresses, but one transaction is repeatedly passed over or aborted and never, or very late, finishesa writer skipped while new readers barge in; one transaction aborted 1,980 times while others committed

The key difference: deadlock is a stable blocked state that needs an external action (an abort) to break. Livelock and starvation involve constant activity, so detecting a cycle doesn't reveal them. Fixing them takes fairness or ordering rules.

D2
Prerequisites
  • Priority scheduling (OS sense): the scheduler always runs the highest-priority ready thread.
  • In a lock manager, "priority" could affect three different decisions: who gets a lock first when it's released, who waits versus who aborts on a conflict, and who is chosen as the victim to break a deadlock.

What does "priority scheduling" mean in your engine? Where exactly is priority used?

TestsWhether the term on the CV matches what the code does.

Answer

Priority is used in exactly one place: choosing the deadlock victim. It's not used to schedule threads or to decide who gets a lock.

  • Victim selection: when the detector finds a cycle, it aborts the member with the lowest priority number, breaking ties by the highest ID.
  • Lock grants ignore it. A new request is granted if it's compatible with current holders, even ahead of queued waiters (barging). On release, pending upgrades are granted first, then other waiters in arrival order. Priority never enters either rule.
  • Threads aren't prioritized. The OS schedules all worker threads equally.

So an accurate name is priority-based victim selection. A high-priority transaction can still wait behind a low-priority one indefinitely, as long as no deadlock cycle forms.

Be careful

Don't describe it as "priority scheduling". An interviewer with an OS background will ask about the ready queue or preemption. Say: "deadlock victims are chosen by priority, and a transaction's priority rises each time it's aborted."

D3
Prerequisites

Aging: gradually raise the priority of work that has waited or failed a lot, so it eventually wins against newer work. It's the textbook remedy for starvation in priority schemes.

How is aging implemented? Show me where in the code.

TestsCode-level accuracy about where the mechanism lives.

Answer

Aging lives in the harnesses, not in the engine. Every time a transaction is aborted, its thread increments a local priority and passes it to the restart.

// tests/benchmark.cpp (retry path)
aborts++;  attempt++;  priority++;
sleep_for(backoff(attempt));
txnId = cm.beginTransaction("", txnId, priority);     // same ID, priority + 1

// tests/test_deadlock_detection.cpp (after each read/write, and on a failed commit)
if (cm.getTransactionState(txnId) == TransactionState::ABORTED) {
    recordTxnRestart(txnNum);  i = -1;  priority++;
    sleep_for(milliseconds(calculateBackoff(priority)));
}

After \(k\) aborts, a transaction's priority is \(p_k = 1 + k\). beginTransaction stores it in the new Transaction object, and the detector reads it through the registry when choosing a victim: lowest number is aborted first. Nothing inside src/ ever changes a priority after creation, and nothing ages a transaction for time spent waiting. Only aborts count.

D4
Prerequisites
  • A useful starvation metric is the maximum number of times any single transaction was aborted in a run. In the benchmark that's the maximum priority reached, minus 1.
  • Victim rule from D2: lowest priority in the cycle is aborted.

Did aging actually prevent starvation? What's your evidence?

TestsWhether "to prevent starvation" was measured.

Answer

No. Under heavy contention some transactions were aborted many times, and in the worst case one transaction was aborted 1,980 times.

Evidence from the benchmark's engine log for the high-contention workload (20 items, 30% writes, 1 ms per operation), which records every victim with its priority:

  • 64 threads, 5 runs: the highest priority reached per run was 10, 19, 12, 10 and 11. So in one run a single transaction was aborted 18 times.
  • 1,000 threads, run 0: 220,943 aborts over about 6 hours, and a maximum priority of 1,981. One transaction was aborted 1,980 times.

Why aging didn't guarantee progress:

  1. Priority only matters relative to the other members of a cycle. Under heavy contention everyone gets aborted and aged, so a cycle of old transactions still has to sacrifice one old transaction.
  2. Lock grants ignore priority. An aged transaction can wait behind newcomers, which gives it more chances to end up in new cycles.
  3. Priority is reset for each new transaction, so it measures repeated failure, not age in time.

Caveat: those 1,000-thread runs were also exposed to the stale-release race, and the log can't separate its effect.

Be careful

Don't claim aging "prevents starvation". Say: "victim priority increases with each abort to reduce repeated victimization; I measured that it didn't prevent starvation under extreme contention, with one transaction aborted 1,980 times, and the fix is timestamp-based victim selection."

D5
Prerequisites
  • Timestamp: a number assigned when a transaction first starts. A smaller timestamp means older.
  • Wait-die: if an older transaction requests a lock held by a younger one, it waits. If a younger one requests a lock held by an older one, the younger one dies (aborts and restarts).
  • Wound-wait: if an older transaction requests a lock held by a younger one, it wounds (aborts) the younger one. If a younger one requests a lock held by an older one, it waits.
  • In both schemes, a restarted transaction keeps its original timestamp.

How would you actually guarantee that no transaction starves?

TestsKnowing schemes with provable progress, and why they work.

Answer

Order transactions by their original start time, keep that timestamp across restarts, and never abort the oldest active transaction.

Wound-wait. A younger transaction only ever waits for an older one, so every wait edge points from younger to older. Such a graph can't have a cycle, so there are no deadlocks and no detector is needed. The oldest active transaction is never wounded, because nobody is older, so it only waits for holders that are either wounded or finish. It therefore finishes. Then the next-oldest becomes the oldest, and so on. Since a restart keeps its timestamp, every transaction eventually becomes the oldest and commits. Spanner uses wound-wait for its read-write transactions.

Wait-die gives the same guarantee with the opposite choice. Older transactions wait, and younger ones abort themselves. It tends to cause more aborts of young transactions, but never interrupts one that is already holding locks.

Keeping detection: change the victim rule to "youngest by original start time" instead of "lowest attempt count", and carry the first-start timestamp through restarts. To also prevent grant starvation, switch from barging to FIFO queues, so a waiting writer blocks newer readers.

Trade-off: timestamp schemes abort on some conflicts that would never have become deadlocks, so the abort count can rise at moderate contention.

D6
Prerequisites

Priority inversion: a high-priority task needs a resource held by a low-priority task, and medium-priority tasks keep the low-priority one from running, so the high-priority task effectively waits behind everyone. The well-known case is NASA's Mars Pathfinder in 1997. Priority inheritance fixes it by temporarily raising the holder's priority to that of the highest waiter.

What is priority inversion? Could something like it happen in your lock manager?

TestsAn OS concept, transferred to a database setting.

Answer

An analogous effect, yes. A high-priority (much-aborted) transaction that requests X on an item held by a low-priority transaction simply waits, because priority doesn't affect grants. While it waits, other low-priority transactions can keep acquiring compatible locks (barging), stretching the wait. If a cycle then forms, the old transaction is protected only if a lower-priority member exists. Otherwise it's aborted yet again.

It's not identical to the OS case. Threads aren't preempted by priority, so "medium-priority tasks running" doesn't apply directly. What's the same is that a high-priority piece of work is blocked by low-priority holders, with nothing to speed them up.

Remedies in lock managers:

  • Wound the lower-priority holder (wound-wait), the database version of "the important one gets the resource now".
  • Priority-ordered grant queues, so waiting high-priority requests are served before newcomers.
  • An inheritance-like boost that makes the holder of a lock a high-priority waiter needs the least likely victim, so it finishes and releases sooner.

Deadlock theory

D7
Prerequisites

The Coffman conditions (1971) are necessary for deadlock. If any one of them is removed, deadlock can't occur:

  1. Mutual exclusion: a resource can be held by only one party at a time.
  2. Hold and wait: a party holds resources while waiting for more.
  3. No preemption: resources can't be taken away, only released voluntarily.
  4. Circular wait: a cycle of parties, each waiting for the next.

What are the four conditions for deadlock? Which of them hold in your system, and could you remove any?

TestsDeadlock theory applied to a lock manager.

Answer

All four hold.

  1. Mutual exclusion: X locks are exclusive, and S excludes X.
  2. Hold and wait: 2PL's growing phase means a transaction keeps every lock it has while it waits for the next one, and strict 2PL keeps them to commit.
  3. No preemption: the lock manager never takes a granted lock away. The detector's abort is recovery after a deadlock exists: it effectively preempts all of the victim's locks.
  4. Circular wait: transactions touch items in arbitrary order. dead_test.txt makes this happen on purpose: half of each batch reads K and later writes J, and half read J and later write K.

Removing one:

  • Circular wait is the practical target: lock items in a global order, which my benchmark could do because its operations are known in advance (T17).
  • Hold and wait goes away with conservative 2PL, acquiring every lock up front, which needs the whole item set in advance and hurts concurrency.
  • No preemption is relaxed by wound-wait, which lets an older transaction take a younger one's locks by aborting it.
  • Mutual exclusion can't go for writes, though MVCC removes it between readers and writers.

D8
Prerequisites
  • Prevention: structurally break a Coffman condition, e.g. with lock ordering, wait-die or wound-wait.
  • Avoidance: grant a request only if the system stays in a "safe" state. The Banker's algorithm does this, but needs each party's maximum resource claim in advance.
  • Detection and recovery: allow deadlocks, find cycles, abort victims.
  • Timeout: assume any long wait is a deadlock, and abort it.

I chose detection because my transactions touch items in arbitrary order, and detection aborts only when a cycle really exists. The project actually started with a 5-second lock timeout and replaced it with detection in April 2025. The measured price is visible under contention: thousands of detected deadlocks at 64 threads, each costing a victim's work.

D9
Prerequisites

Eliminate means make impossible, which is prevention. Detect and resolve means deadlocks still form, and are broken afterwards by aborting a transaction.

Your CV says you "eliminated deadlocks via cycle detection". Did you?

TestsPrecision in wording. Detection can't eliminate anything.

Answer

No. Detection doesn't eliminate deadlocks. It lets them happen and then breaks them. What I can say is that no run ever hung on one.

  • High-contention benchmark: 8, 23, 96, 433, 1,479 and 3,844 deadlock-victim aborts per run at 2, 4, 8, 16, 32 and 64 threads. In the benchmark nothing else aborts transactions, so each is a broken deadlock.
  • Original harness, pre-fix: 2,843–2,953 restarts per run on the random file, and 6,701–6,731 on the deadlock-heavy file.
  • Every one of those runs completed, and every transaction eventually committed. So detection plus recovery kept the system live. The exception was 1,000 threads under high contention, which took about 6 hours.

Eliminating them would take prevention, such as ordered lock acquisition or wound-wait (D5, D7).

Be careful

Say "detected and resolved deadlocks with cycle detection on a wait-for graph", never "eliminated". If you want a result, use: "every run up to 64 threads completed, with all transactions committed, despite up to 3,844 deadlocks per run."

The wait-for graph

D10
Prerequisites
  • Wait-for graph (WFG): nodes are transactions, and an edge W→H means W waits for a lock that H holds.
  • For single-instance resources like item locks, a cycle in the WFG means a deadlock.
  • Compatibility: a waiting S is blocked only by X holders. A waiting X is blocked by any other holder.

What is a wait-for graph, and how does your detector build it? Walk through an example.

TestsCorrect edge construction, including shared locks and upgrades.

Answer

Each pass, the detector calls LockManager::getWaitForEdges(). Under one acquisition of the lock-table mutex, it walks every resource's request list and emits an edge from each pending request to each granted request of a different transaction, unless both are shared. The detector then drops edges whose waiter or holder is already marked aborted, and rebuilds its adjacency list from scratch.

Example.

  • R1: T1 and T2 hold S, and T3 waits for X. That gives T3→T1 and T3→T2.
  • R2: T4 holds X, and T5 waits for S. That gives T5→T4.
  • R3: T1 and T2 hold S, and T1 waits for X (an upgrade). That gives T1→T2 only: T1's own S isn't an edge.

The graph {T3→T1, T3→T2, T5→T4, T1→T2} has no cycle, so no deadlock. If T2 now also asks to upgrade on R3, the edge T2→T1 appears, and T1→T2→T1 is a deadlock.

Cost: the scan is proportional to the lock table's size, and it holds the global mutex for that whole time. That's a trade-off against the detection interval (D17).

D11
Prerequisites
  • Consistent snapshot: every part of the data read as of the same instant.
  • Phantom deadlock: a cycle that appears only because edges were read at different times. At no single moment did the cycle actually exist. Aborting for it wastes a transaction.

Why does it matter that the graph is taken under a single mutex acquisition? What did the old code do?

TestsReasoning about consistency of monitoring data under concurrency.

Answer

Old code: for every resource ID from 0 to 9,999, it called getWaitingTransactions(id) and getLockHolders(id), each taking and releasing the mutex. That caused three problems:

  • At least 10,000 mutex acquisitions per pass, even though the workloads use 12–26 items.
  • Resources with ID ≥ 10,000 were never inspected, so a deadlock there would never be broken, and with no timeout it would hang forever.
  • The table changed between calls, so the graph could mix edges from different moments. That allows phantom deadlocks: say T1→T2 was read before T2 got its lock, and T2→T1 after T1 had moved on.

New code: one pass over the table under one acquisition. Every edge describes the same instant.

Why a cycle is then real: an edge means the waiter is asleep, and sleeping transactions release nothing. The lock manager also never leaves a grantable request ungranted when it releases the mutex, since every release path grants compatible waiters first. So at that instant, every member of the cycle is genuinely stuck, and the cycle can't dissolve by itself. The abort is never wasted on a phantom.

Trade-off: the single acquisition holds the global mutex for the whole scan, briefly blocking every transaction. With a striped table you'd either lock all stripes in order, or re-verify a found cycle's edges before aborting.

D12
Prerequisites

A resource allocation graph (RAG) has two kinds of nodes, transactions and resources. A request edge T→R means T waits for R. An assignment edge R→T means R is held by T. A WFG is a RAG with the resource nodes collapsed away. With multi-instance resources (e.g. 3 identical printers), a RAG cycle is necessary for deadlock but not sufficient.

Your project has both a resource allocation graph and a wait-for graph. What's the difference, and which one detects deadlocks?

TestsGraph models, and knowing your own codebase's structure.

Answer

The wait-for graph detects deadlocks. The resource allocation graph is kept in step with the lock table and used for tracing.

  • RAG: LockManager adds request and assignment edges as it queues and grants. The text harness writes the whole graph to rag_log.txt after every operation, which is useful for visualising who holds and wants what. It even has a correct DFS, detectDeadlock(), but nothing calls it during runs.
  • WFG: the DeadlockDetector builds it fresh each pass from the lock-table snapshot, and runs cycle detection and victim selection on it.

Why the WFG for detection: each lock is a single-instance resource, so a cycle means a deadlock in either graph. The WFG is smaller (transactions only), and victim selection needs transactions anyway. A RAG pays off with multi-instance resources, where you must reason about available units, because a cycle alone doesn't prove deadlock.

History: the RAG and its log used to drift out of step with the table, because some grants skipped the assignment edge. Now every grant goes through one function that updates both.

Cycle detection and recovery

D13
Prerequisites
  • DFS states: unvisited; on the current recursion stack ("in progress"); finished.
  • Back edge: an edge to a node that's still on the stack. In a directed graph, one exists exactly when there's a cycle.
  • \(V\) = number of nodes, \(E\) = number of edges.

Write out your cycle-detection algorithm, give its complexity, and show how you extract the exact cycle.

TestsA standard graph algorithm, adapted to the need to know cycle members.

Answer 
bool FindCycle(node, visited, inStack, path, cycle):
    visited[node] = inStack[node] = true
    path.push_back(node)
    for nb in graph[node]:
        if !visited[nb]:
            if FindCycle(nb, visited, inStack, path, cycle): return true
        else if inStack[nb]:                              // back edge node -> nb
            cycle = path[ index of nb .. end ]            // exactly the cycle members
            return true
    inStack[node] = false
    path.pop_back()
    return false

HasCycle(victim):
    for root in sorted(nodes): if !visited[root] and FindCycle(root, ...):
        victim = argmin over cycle of (priority, then highest id)
        return true
    return false

Complexity: each node is visited once and each edge examined once, so one search is \(O(V + E)\). A detection pass that breaks \(k\) cycles runs \(k + 1\) searches, \(O(k(V + E))\), because it removes the victim and searches again.

Extracting the cycle: the path holds the current chain from the root. When a back edge node→nb appears, the cycle is the segment from nb to node. Earlier nodes on the path only wait on the cycle.

Example: edges T1→T2, T2→T3, T3→T2. The path grows [1], [1, 2], [1, 2, 3], then 3→2 is a back edge, so the cycle is [2, 3]. T1 isn't in it.

Why sorted roots: determinism. The same graph always yields the same victim, which makes tests reproducible. Recursion depth is at most \(V\), which is fine for about 1,000 transactions. For much larger graphs I'd switch to an explicit stack.

D14
Prerequisites
  • Kahn's algorithm: repeatedly remove nodes with in-degree 0. If nodes remain, there's a cycle, but the remaining set also includes nodes merely downstream of a cycle.
  • Tarjan's algorithm: finds strongly connected components (SCCs) in \(O(V + E)\). An SCC with more than one node contains at least one cycle.
  • Union-find: detects cycles in undirected graphs.

Why DFS? Why not Kahn's topological sort, Tarjan's SCC algorithm, or union-find?

TestsChoosing an algorithm by what the output must contain.

Answer

Victim selection needs the members of a specific cycle, and DFS with a path gives exactly that at the same \(O(V + E)\) cost.

  • Kahn tells you a cycle exists, but its leftover set includes tail transactions that wait on the cycle without being part of it. Choosing a victim from that set is exactly the bug my old detector had: it could abort a tail, which breaks nothing. (My benchmark uses Kahn for the serializability check, where "how many can't be ordered" is precisely the question.)
  • Tarjan is a strong alternative. One pass gives every SCC, so you can pick one victim per non-trivial SCC. But an SCC can contain several overlapping cycles, and removing one node may not break them all. You'd still have to re-run on that component, so the loop looks the same as mine.
  • Union-find doesn't handle directed cycles. A→B and C→B share B, but that isn't a cycle.

D15
Prerequisites
  • Aborting a node that's not on the cycle leaves the cycle intact.
  • Common victim criteria: least work done, fewest locks held, youngest (latest start), fewest previous restarts, or an explicit priority.

How do you choose a deadlock victim? What was wrong with the old version, and how did you prove it?

TestsVictim policy design, and a concrete bug with a test.

Answer

Now: among the members of the extracted cycle, abort the one with the lowest priority number, breaking ties by the highest ID. A transaction that no longer exists sorts first, so it's simply dropped.

The old bug: the running minimum was seeded with the DFS root and updated at every node while the recursion unwound, including nodes before the cycle began. So the victim was the lowest-priority node on the whole search path. Since every transaction starts at priority 1, with ties kept on the root, a tail node was often chosen.

Proof: a unit test against the old class, with graph T1→T2, T2→T3, T3→T2 and all priorities equal, returned T1, which isn't in the cycle {T2, T3}. Aborting T1 breaks nothing, so the loop had to abort again, wasting work. The regression test now checks that same graph returns a cycle member (T3), and that with T1 = 0, T2 = 5, T3 = 1, the lower-priority tail T1 is still not chosen, but T3 is. All three checks passed.

What I'd improve: use "youngest by original start time" (D5) for a progress guarantee, or "least work done", measured as locks held or operations completed, to minimize wasted work.

D16
Prerequisites
  • The CAS-based abort(): it succeeds unless the transaction already committed.
  • The waiter's wake predicate, which includes "I was aborted".
  • Restart under the same ID, with priority + 1 and backoff.

Once a victim is chosen, what happens, step by step? How does the victim's own thread find out?

TestsThe cross-thread recovery path, end to end.

Answer
  1. Detector thread: txn->abort() CASes the state to ABORTED. If the victim committed in the meantime, the CAS fails, and the detector just removes the node.
  2. Detector thread: logs a warning, then calls releaseAllLocks(victim). Under the lock-table mutex, that removes the victim's granted and pending requests from every resource, clears its graph edges, grants any waiters that are now compatible (upgrades first), and calls notify_all.
  3. Detector thread: removes the victim and all edges into it from the wait-for graph, then searches again. The loop ends when no cycle remains, and it runs at most \(V\) times, since each iteration removes a node.
  4. Victim's thread: it was asleep in cv.wait. The notify wakes it, and its predicate is true because it's aborted. It removes any pending request of its own and acquireLock returns false.
  5. Harness: sees ABORTED, increments priority, sleeps for the backoff, then calls beginTransaction(…, sameId, priority). That releases anything still held under the ID and registers a fresh transaction object. The benchmark also discards the attempt's buffered writes.
  6. Other waiters that were granted in step 2 wake with their predicate true (their request is no longer pending) and continue.

The known flaw in this sequence: step 2's release is keyed by ID and runs after a gap. If step 5 completes first, the release hits the restarted transaction's new locks. That's the 1,000-thread race in S12, and it's fixed by making the release check the object identity.

D17
Prerequisites

If deadlocks form at uniformly random times and the detector runs every \(I\) milliseconds, a deadlock waits between 0 and \(I\) before the next pass starts, \(I/2\) on average, plus the pass time:

\[ \mathbb{E}[\text{delay}] \approx \frac{I}{2} + t_{\text{pass}} \]

Throughout that delay, the deadlocked transactions keep their locks, blocking everyone queued behind them.

How often should the detector run? What's the trade-off, and what do real systems do?

TestsTuning with a model, not a guess.

Answer

Shorter intervals resolve deadlocks sooner, but take the global mutex more often for the snapshot.

  • Text harness, \(I = 100\) ms: about 50 ms average and up to 100 ms of dead time per deadlock, plus the pass.
  • Benchmark, \(I = 10\) ms: about 5 ms average and up to 10 ms. When transactions do 1 ms of work per operation and deadlocks happen thousands of times per run, a 5 ms average stall per deadlock is significant, so short intervals make sense there.
  • Cost: each pass holds the lock-table mutex for a full scan, and every transaction's lock calls queue behind it. I didn't measure the pass time.

Alternatives:

  • Detect on wait: when a request blocks, search only from that transaction. There's no periodic cost when nothing waits, and the delay is zero. MySQL's InnoDB checks for deadlocks when a lock request has to wait, and allows turning that off in favour of a lock-wait timeout at very high concurrency.
  • Adaptive: run the detector only when some waiter has waited longer than a threshold.
  • Timeout as a backstop: in case detection misses something, or in distributed settings.

D18
Prerequisites
  • A graph can contain several cycles, disjoint or sharing nodes.
  • Between taking a snapshot and acting on it, transactions keep running. A chosen victim may commit, or may already have been aborted.

What if there are several deadlocks at once, or the victim commits between the snapshot and your abort?

TestsEdge cases in the recovery loop.

Answer

Several cycles: RunCycleDetection loops. Find a cycle, abort one victim, remove it from the graph, search again, until the graph is acyclic. Disjoint cycles each lose one member. If cycles share a node and that node is the victim, one abort breaks both. The loop terminates because every iteration removes a node.

Victim committed in the meantime: this can't happen for a transaction that's genuinely in a cycle, because it's asleep waiting. It could happen if its wait ended while the detector was busy with an earlier victim in the same pass, since an earlier release may have granted it. Then abort()'s CAS finds COMMITTED and returns false. The detector logs "already finished" and still removes the node. The old code didn't remove the node when the lookup failed, so it could have looped on the same cycle forever. That's fixed.

Victim already gone: if the registry lookup returns null, its priority counts as the minimum, so it's picked and simply removed from the graph.

Victim already aborted by someone else: the snapshot builder skips edges involving aborted transactions, and abort() on an aborted transaction just returns true.

Victim already restarted: the dangerous case, the 1,000-thread race (S12).

Review: Part 3, section 5

D19
Prerequisites
  • Distributed transaction: touches data on several nodes, each with its own lock manager.
  • Global deadlock: a cycle that crosses nodes. Each node's local wait-for graph looks acyclic.
  • Edge chasing (Chandy–Misra–Haas): a blocked transaction sends a probe along its wait edges. Nodes forward it along their own edges, and if it returns to the initiator, there's a cycle.

How would deadlock detection change if the lock manager were distributed across machines?

TestsSystem design: extending a single-node design to a distributed one.

Answer

My detector relies on one consistent snapshot of one lock table. Distributed, there's no single table and no instantaneous global snapshot, so the options change.

  1. Centralized global graph: each node periodically sends its local wait edges to a coordinator, which merges them and searches for cycles. It's simple, but the pieces are from different times, so phantom deadlocks come back unless the coordinator re-verifies edges before aborting. The coordinator is also a bottleneck.
  2. Edge chasing: a transaction blocked for a while sends a probe tagged with its ID to the holder's node, which forwards it along that holder's wait edges. The probe returning to the initiator proves a cycle. There's no global snapshot and it scales well, but it takes messages, and two initiators might pick overlapping victims.
  3. Prevention with global timestamps: wound-wait or wait-die needs no graph at all, only comparable timestamps. Spanner uses wound-wait for this reason.
  4. Timeouts: abort after waiting too long. That's crude, but common in practice as the primary mechanism or a backstop, because it needs no cross-node coordination.

For a real system I'd pick wound-wait with preserved timestamps plus a generous timeout. That also fixes the starvation problem I measured, and avoids the stale-release class of bug, because no asynchronous detector acts on stale information.
